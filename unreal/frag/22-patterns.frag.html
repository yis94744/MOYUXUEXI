一、Subsystem：UE 的管理器机制 ★★

Subsystem 是 Unreal 提供的"生命周期管理"机制——它解决了"全局管理器怎么放"的问题。

类型生命周期用途
UGameInstanceSubsystem整个游戏会话存档、账号、全局配置
UWorldSubsystem每个关卡关卡相关的系统
ULocalPlayerSubsystem每个本地玩家玩家设置、UI 偏好
UEditorSubsystem编辑器会话编辑器工具
Subsystem 替代了传统的"单例" 传统做法（不推荐）：
class UMyManager : public UObject {
  static UMyManager* Instance; // 手写单例
};
问题：
· 生命周期要自己管
· 容易忘记清理（→ 状态残留，Lua 站页 15 的老问题）
· 多世界（PIE）时冲突

Subsystem 做法：
class UMySystem : public UGameInstanceSubsystem {
  virtual void Initialize(FSubsystemCollectionBase& C) override;
  virtual void Deinitialize() override;
};
// 获取
GetGameInstance()->GetSubsystem<UMySystem>();

优势：
· 引擎管理生命周期（自动初始化与销毁）
· 天然支持 PIE（每个世界独立）
· 依赖注入友好

结论：需要"全局管理器"时，优先用 Subsystem，不要手写单例。
不要把一切都做成 Subsystem 常见过度使用：
· 把每个功能都做成一个 Subsystem→ 启动时全部初始化，启动变慢
· 让 Subsystem 互相依赖→ 初始化顺序问题

判断标准：
· 真正需要"全局唯一 + 生命周期跟随游戏"的 → Subsystem
· 只是一个功能模块 → 普通类，按需创建
· 只在一个关卡用 → WorldSubsystem 或直接放在关卡里

启动性能提醒：Subsystem 的 Initialize 会阻塞启动——不要在里面做耗时操作（比如加载大数据）。

二、组件化的三条原则

原则做法反例
单一职责一个组件一件事Health 组件同时管 UI
可独立测试能不依赖 Owner 最好组件里到处 GetOwner()
用接口解耦通过接口通信直接 Cast 到具体类
避免 Tick能不用就不用每个组件都开 Tick
Cast 的性能与耦合问题 常见写法：
if (AMyEnemy* E = Cast<AMyEnemy>(Other)) {
  E->TakeDamage(...);
}
问题：
· 强耦合——必须知道具体类型
· 无法处理"实现了同样能力的其他类"
· Cast 本身有开销

更好的做法：用接口：
if (IDamageable* D = Cast<IDamageable>(Other)) {
  D->TakeDamage(Amount); // 任何实现了接口的都能处理
}

好处：
· 解耦——不关心具体类型
· 可扩展——新类型实现接口即可
· UE 的 Cast 到接口有优化

Unreal 接口的写法：
UINTERFACE(MinimalAPI)
class UDamageable : public UInterface { GENERATED_BODY() };
class IDamageable { GENERATED_BODY()
public:
  virtual void TakeDamage(int32 Amount) = 0;
};
