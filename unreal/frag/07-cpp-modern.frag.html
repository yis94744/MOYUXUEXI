一、C++11 的六个关键特性

特性解决什么游戏里怎么用
auto类型推导简化迭代器写法
范围 for遍历容器替代下标循环
lambda匿名函数回调、排序比较
移动语义避免拷贝转移大对象
智能指针自动内存管理页 04 已讲
nullptr类型安全的空指针替代 NULL
override/final明确重写意图页 05 已讲
右值引用 &&移动语义基础理解即可
nullptr vs NULL：一个真实的坑 NULL 在 C++ 里就是 0——这会导致重载解析错误：
void F(int x);
void F(char* p);
F(NULL); // ❌ 调用 F(int)！因为 NULL 是 0
F(nullptr); // ✅ 调用 F(char*)

nullptr 是类型安全的——它有独立的类型 std::nullptr_t。

Unreal 里的实践：UE 用 nullptr，不用 NULL。
范围 for 与 lambda 的实战价值 范围 for——少写很多代码：
// 老写法
for (int i = 0; i < arr.Num(); ++i) { arr[i]... }
// 新写法
for (auto& item : arr) { item... }
注意：auto& 是引用（能改原对象），auto 是拷贝。

lambda——游戏里到处都用：
Items.Sort([](const FItem& A, const FItem& B) {
  return A.Price < B.Price;
});
比写一个独立的比较函数方便得多。

捕获方式很重要：
· [=]——按值捕获（拷贝，安全但可能慢）
· [&]——按引用捕获（危险：可能悬垂）
· [this]——捕获 this 指针
· [x, &y]——精确指定（推荐）

二、C++14/17/20 的重要特性

版本特性价值
14泛型 lambda、auto 返回类型写起来更简洁
17std::optional表示"可能没有值"
17std::string_view避免字符串拷贝
17if constexpr编译期分支
17结构化绑定解构 pair/tuple
20concept模板约束（页 06）
20ranges管道式数据处理
20modules替代头文件（UE 尚未采用）
Unreal 的 C++ 版本支持情况 UE5 的 C++ 标准：
· UE5.0-5.2：默认 C++17
· UE5.3+：逐步支持 C++20
· 但很多特性还没法用（因为 UE 自己还没迁移）

实践中能用的：
· C++11/14——完全可用
· C++17——大部分可用（optional/string_view/if constexpr）
· C++20——部分可用，谨慎使用

重要提示：
· UE 有自己的容器（TArray 而不是 std::vector）
· UE 有自己的字符串（FString 而不是 std::string）
· 用 UE 的，不要混用 STL——除非在纯计算模块里

这是 UE 开发的一条重要约定。

三、现代 C++ 的三条实践原则

原则一：能推导就不写类型 用 auto 减少重复：
std::vector<Monster>::iterator it = ...; // 老写法
auto it = ...; // 新写法

但不要滥用：
· 类型不明显时，写出来更清晰
· UE 的容器迭代器类型很长，auto 更合适

判断标准：如果写出来反而更难读，就用 auto。
原则二：优先用标准库和引擎容器 不要自己实现链表、动态数组：
· 标准库的 std::vector 已经高度优化
· UE 的 TArray 针对游戏场景优化过
· 自己写的几乎不可能更好

选择容器：
· 动态数组 → TArray
· 哈希表 → TMap / TSet
· 固定大小 → TStaticArray

标准库的 <algorithm> 也值得用：
std::sort、std::find、std::max_element...
原则三：不要为了"现代"而现代 常见的过度使用：
· 为了用 lambda 而把所有循环改成 lambda
· 为了用 auto 而让类型完全不可读
· 为了炫技写复杂的模板元编程

判断标准：
"这样写让代码更好懂了吗？"
· 是 → 用
· 否 → 用老写法

尤其注意：团队的水平决定可用的特性。
如果一个特性团队里一半人看不懂，它的维护成本就超过了收益。
