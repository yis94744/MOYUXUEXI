09 · 构建系统与工具链

这一页讲让 C++ 项目能编译、能协作、能发布的那些事。Unreal 的构建系统很复杂，但理解了就不神秘。

这一页在路线中的位置 [object Object]

一、Unreal 的构建系统 ★★

组件作用语言
UnrealBuildTool (UBT)决定怎么编译C#（.NET）
.Build.cs声明模块依赖C# 语法
.Target.cs定义构建目标C# 语法
.uproject项目描述文件JSON
UnrealHeaderTool (UHT)处理 UE 宏C++
最反直觉的一点：构建配置用 C# 写 传统 C++ 项目用 CMake / Makefile，Unreal 用 C#。

为什么：
· UBT 本身就是 C# 程序（跑在 .NET 上）
· 用 C# 描述构建逻辑更灵活（有完整的编程能力）
· 能跨平台

这意味着：改构建配置要懂一点 C#——这是很多 Unity 转 UE 的人没想到的。

实际影响：当你需要"条件编译"或"自定义构建步骤"时，要写 C# 代码而不是 CMake 脚本。
最常见的构建错误：模块依赖没声明 症状：
unresolved external symbol
或
cannot open include file

原因：用了某个模块的类，但没在 .Build.cs 里声明。

解法：在 PublicDependencyModuleNames 或 PrivateDependencyModuleNames 里加模块名：
PublicDependencyModuleNames.AddRange(new string[] {
  "Core", "CoreUObject", "Engine", "InputCore",
  "GameplayAbilities", // 用了 GAS 就要加
  "UMG" // 用了 UMG 就要加
});

为什么容易忘：IDE 的补全可能能找到头文件，但链接时会失败——因为编译和链接是两个阶段（页 03）。

二、编译加速的五个手段

手段效果代价
前向声明显著需要改代码结构
减少头文件包含显著同上
把实现放 .cpp中等无法内联
拆分模块中等需要设计
用 IWYU（Include What You Use）中等需要工具支持
增量编译极大（日常）首次全量仍慢
Unreal 的编译为什么这么慢 三个原因：
① 每个头文件改动会触发大量重编译（因为依赖链长）
② UHT 要先处理宏（额外的预处理阶段）
③ 模板实例化开销（页 06）

实际影响：
· 改 .cpp → 通常几十秒
· 改 .h → 可能几分钟到十几分钟

应对策略：
· 尽量把易变的逻辑放蓝图（不触发 C++ 编译）
· 头文件只放必要的声明
· 珍惜每次编译——一次改完再编译
