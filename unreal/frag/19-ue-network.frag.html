一、UE 的网络模型

UE 采用服务器权威（Server Authoritative）模型。理解这个模型是理解一切的前提。

角色含义权限
Server权威决定一切
Client请求与显示没有权威
AutonomousProxy本地控制的角色有输入权
SimulatedProxy其他角色只能插值显示
Listen Server既是服务器又是玩家开发期常用
Dedicated Server专用服务器正式上线用
最重要的一条：客户端不能改权威状态 ★★★ 这是网络游戏的第一原则。

错误做法：客户端直接扣血
// 在客户端执行
Health -= Damage;
作弊者可以随意改这个值。

正确做法：客户端请求 → 服务器验证 → 服务器执行 → 复制回客户端
// 客户端
ServerTakeDamage(Damage); // RPC 请求
// 服务器
void ServerTakeDamage_Implementation(float Damage) {
  Health -= Damage; // 服务器才是权威
}

怎么判断该放哪：问"如果玩家能随意改这个值，会怎样？"
· 会破坏游戏平衡 → 服务器
· 只影响本地显示 → 客户端

这和 Lua 站页 21 讲的"客户端不可信"是同一个原则。
三种 RPC 及其适用场景
RPC方向用途
Server客户端 → 服务器请求操作
Client服务器 → 特定客户端通知特定玩家
NetMulticast服务器 → 所有客户端广播效果

典型用法：
· 开枪 → ServerFire()（请求）
· 播放枪声 → MulticastPlaySound()（所有人听到）
· 提示"你被击中了" → ClientShowHitMarker()（只给本人）

关键规则：
· RPC 只能从"有权限"的一端调用
· 实现函数必须加 _Implementation 后缀
· RPC 不能返回值（异步的）

二、属性复制与预测

机制作用复杂度
Replicated 属性服务器 → 客户端同步低
RepNotify值变化时回调低
RPC单次调用中
客户端预测本地立即响应高
服务器回滚修正预测错误高
插值平滑其他玩家低
为什么需要"客户端预测" 问题：玩家按下移动键，要等服务器确认才动——延迟 100ms 就是明显的手感问题。

预测的做法：
① 客户端立即执行移动
② 同时把输入发给服务器
③ 服务器计算并返回权威位置
④ 如果客户端预测错了，服务器纠正

效果：本地操作零延迟感。

代价：
· 需要"回滚重放"的复杂度
· 可能出现"回拉"（预测错误时位置突然跳）

UE 提供的帮助：
· ACharacter 内置了移动预测
· GAS 内置了技能的预测
这就是为什么要用 UE 的框架而不是自己写。
