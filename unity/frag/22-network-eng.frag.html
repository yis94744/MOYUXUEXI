22 · 网络、工程化与发布

这一页讲三件"项目能不能顺利交付"的事：网络同步方案怎么选、工程化怎么落地、包怎么发出去。它们不是技术难点，但每一件都可能卡住项目。

这一页在路线中的位置 上一页（21）讲性能优化。这一页讲把项目"送到玩家手上"。 关键衔接：页 16 的热更新是发布环节的一部分；页 20 的依赖方向决定了工程化能走多远。 下一页（23）AI 辅助开发与 AI NPC。这是新时代的能力。 提醒：这一页的内容很多人工作几年都用不上（比如不做多人的项目），但面试时会问。

一、网络同步：两种根本方案

所有网络游戏都建立在这两种方案之上。选错了会在项目中期推倒重来。

帧同步（Lockstep）状态同步（State Sync）
同步内容操作指令状态数据
数据量极小（几个字节）较大（位置、属性）
服务器压力低（只转发）高（要跑逻辑）
网络波动敏感（要等齐）容忍（可插值）
反外挂难（客户端有完整逻辑）好（服务器权威）
确定性必须保证（浮点/随机）不需要
适用RTS、MOBA、格斗、卡牌MMO、FPS、大部分手游
帧同步的"确定性"是个大坑 帧同步要求所有客户端在相同输入下产生完全相同的结果。
但浮点运算在不同 CPU / 不同编译器下结果可能不同！

解决方案：
· 全部用定点数代替浮点
· 随机数用自定义的确定性算法（不能用 Random）
· 遍历顺序要固定（不能依赖 Dictionary 的顺序）

这就是为什么帧同步游戏的代码"看起来很怪"——那些约束都是为了让结果可复现。

二、工程化：让项目能长期维护

方面做法解决的问题
版本控制Git + LFS + Unity 设置大文件、场景合并冲突
程序集拆分asmdef改一行代码编译 30 秒
代码规范EditorConfig + 命名约定风格混乱、review 成本高
自动化测试Unity Test Framework重构时不知道有没有改坏
CI/CDJenkins / GitHub Actions每天手动打包
日志系统分级日志 + 上报线上出问题看不到线索
asmdef 是被低估的优化 问题：所有代码在一个程序集里时，改任何一行都要重新编译整个程序集。
项目大了之后，一次编译可能30 秒到 2 分钟。

解决：用 .asmdef 拆成多个程序集：
· 只编译被修改的那个程序集
· 强制依赖方向（跨程序集引用要显式声明）
· 编辑器代码自动排除出包体

这是投入产出比极高的一项改造——半天工作量，省下的是每天几十次编译的时间。
Unity 项目的 Git 配置 必须做的三件事：
① .gitattributes：设置 *.unity 用 force text 序列化（否则无法合并）
② .gitignore：忽略 Library/ Temp/ Obj/ Build/
③ Git LFS：大文件（贴图、模型、音频）走 LFS

场景合并：用 UnityYAMLMerge 配置到 Git，否则两个人改同一个场景必然冲突。

三、发布流程

从"能跑"到"上线"，中间还有一条完整的流水线。

环节内容常见问题
打包设置包名、图标、签名、AOT 配置签名不对导致无法安装
加固代码混淆、防调试、防重打包过不了渠道检测
渠道各应用商店的 SDK 接入每个渠道都要单独测
隐私合规隐私政策、权限申请不合规会被下架
灰度先小范围发布，观察数据没有回滚机制
监控崩溃收集、性能数据上报线上问题靠玩家反馈
三个会导致无法上线的细节 ① 隐私合规：现在国内 Android 与 iOS 都要求首次启动前展示隐私政策，且不能在用户同意前收集数据。不合规直接下架。

② IL2CPP 的 AOT 泛型：反射用到的泛型组合在 IL2CPP 下可能不存在，运行时报错（见页 06）。

③ 签名与密钥丢失：Android 签名密钥丢了就无法更新已上架的包。必须妥善备份。
