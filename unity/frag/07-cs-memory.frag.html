07 · 内存、GC 与零分配 ★

这一页是 C# 语言线的收官，也是全站分量最重的一页之一。前面六页你学会了各种工具——但每个工具都有"账单"：装箱要分配、闭包要分配、LINQ要分配、反射要分配。这一页把这些账单收拢起来，告诉你哪些账必须付、哪些能省、以及怎么省。

这一页在路线中的位置 前一页（06）教你用泛型、反射、特性写"可复用的代码"。但反射慢、泛型不当会装箱——你已经开始感觉到"能力越大，代价越大"。
这一页把这些代价量化：Unity 用的 GC 是什么样的、它什么时候卡、你的代码在哪产生垃圾。
下一页（08）讲协程与异步——它们也有分配问题（new WaitForSeconds），到这里就全部串起来了。
为什么把性能放在语言线里？因为等你写完几十个脚本再学 GC，架构已经烂了，改起来是重写。

一、先搞懂 Unity 的内存模型

Unity 的内存分成几块，不同块的问题要用不同工具解决。搞混它们，你会用错工具、找错方向。

内存区域里面装什么谁管它泄漏表现查它的工具
托管堆C# 对象、装箱的值类型、字符串Boehm GC托管内存持续上涨Memory Profiler
Native 内存纹理、网格、音频、GameObjectUnity 引擎（引用计数）纹理/网格数量不降Memory Profiler
栈局部变量、方法调用帧自动回收几乎不会泄漏—
非托管分配NativeArray、ComputeBuffer你必须手动 Dispose报 Native Collection not disposedLeak Detection
关键认知：GC 只管托管堆 GC 不会帮你回收纹理、网格、RenderTexture。这些是 Native 对象，靠 Unity 的引用计数机制管理。
所以你经常看到的现象是：托管内存很小，但应用照样爆内存——因为涨的是 Native 内存。
反过来，NativeArray、ComputeBuffer 这类非托管分配，即使有 GC 也不会被自动回收，必须手动 Dispose()。

二、Boehm GC：Unity 用的是什么样的 GC

Unity（无论 Mono 还是 IL2CPP）用的都是 Boehm GC。它不是"现代 GC"，理解它的特性才能理解性能问题的根源。

特性说明对你的影响
非分代不像 .NET GC 分 0/1/2 代每次都扫描全部对象，不是只扫新对象
非压缩回收后不整理内存容易产生内存碎片，堆只增不减
全停顿回收时暂停所有线程停顿时间与存活对象数量成正比
标记-清除标记存活对象，清除其余分配越多 → 扫描越久 → 卡顿越久
增量 GCUnity 2019.1+ 可开启把一次大停顿拆成多次小停顿，强烈建议开启
两个必须纠正的误解 误解一：「IL2CPP 没有 GC。」
IL2CPP 只是把 IL 转成 C++ 再编译，GC 依然是 Boehm。"换了 IL2CPP 就不卡了"是错的。
误解二：「用 GC.Collect 手动回收就能解决问题。」
GC.Collect() 会触发一次全停顿回收，本身就是卡顿来源。正确的做法是少产生垃圾，而不是频繁手动回收。

开启增量 GC

// Edit -> Project Settings -> Player -> Other Settings
//   [x] Use Incremental GC            <- 强烈建议勾选
//   Incremental GC Time Slice   3      <- 每次切片的时间上限（毫秒）

using UnityEngine;
using UnityEngine.Scripting;   // GarbageCollector 在这个命名空间下，缺了会报 CS0103

public class GcConfig : MonoBehaviour
{
    private void Start()
    {
        // 默认：GC 自动触发
        // GarbageCollector.GCMode = GarbageCollector.Mode.Enabled;

        // 手动模式：只在调用 Collect 时回收
        // GarbageCollector.GCMode = GarbageCollector.Mode.Manual;

        // 关闭 GC（危险，只适合完全零分配的项目）
        // GarbageCollector.GCMode = GarbageCollector.Mode.Disabled;
    }

    // 手动触发的正确时机：场景切换、加载界面
    public void ForceCollectOnLoadingScreen()
    {
        System.GC.Collect();
        System.GC.WaitForPendingFinalizers();
        System.GC.Collect();
    }
}
增量 GC 能解决什么、不能解决什么 能解决：把一次 20ms 的大停顿拆成 7 次 3ms 的小停顿。体感上从"明显卡一下"变成"几乎感觉不到"。
不能解决：垃圾总量本身。如果每帧产生 100KB 垃圾，GC 依然会高频触发，只是每次停顿短了。
正确的优先级是：① 先减少分配 → ② 再开启增量 GC → ③ 最后才考虑手动控制。

三、每帧 GC 分配的十大来源 ★

下面这份清单必须背下来。面试会问，实战更要靠它。我把它们按出现频率排序——排在前面的，是你在 Profiler 里最常看到的。

using UnityEngine;
using System.Collections.Generic;
using System.Text;
using System.Linq;   // 示例里故意用 LINQ 演示 GC 分配

// ============================================================
//  Update 里最常见的 GC 分配来源（按出现频率排序）
// ============================================================
public class GcSources : MonoBehaviour
{
    private int _score;
    private float _time;
    private List<Enemy> _enemies = new List<Enemy>();
    private Enemy _target;
    private float _scale = 1.5f;

    // ---------- 来源 1：字符串拼接 ----------
    private void Update_Strings()
    {
        // 每帧分配 3~4 个字符串对象
        Debug.Log("Score: " + _score + " / Time: " + _time);
    }
    // 修复：条件编译 + 只在变化时输出
    [System.Diagnostics.Conditional("UNITY_EDITOR")]
    private static void LogScore(int score, float time)
    {
        Debug.Log("Score: " + score + " / Time: " + time);
    }

    // ---------- 来源 2：装箱 ----------
    private void Update_Boxing()
    {
        Debug.LogFormat("Score: {0}", _score);   // params object[] -> 装箱
    }

    // ---------- 来源 3：数组分配 ----------
    private void Update_Arrays()
    {
        // 每次调用都新建一个 RaycastHit[]
        RaycastHit[] hits = Physics.RaycastAll(transform.position, Vector3.down, 10f);
        Debug.Log(hits.Length);
    }

    // ---------- 来源 4：LINQ ----------
    private void Update_Linq()
    {
        // 迭代器对象 + 闭包 + 结果 List，一次三份分配
        var alive = _enemies.Where(e => e.Hp > 0f).ToList();
        Debug.Log(alive.Count);
    }

    // ---------- 来源 5：闭包捕获 ----------
    private void Update_Closure()
    {
        // lambda 读了实例字段 _scale —— 这会捕获 this，每次调用新建一个闭包对象
        // 反例：写成 (a, b) => a.Hp.CompareTo(b.Hp) 反而不分配（编译器缓存静态委托）
        _enemies.Sort((a, b) => (a.Hp * _scale).CompareTo(b.Hp * _scale));
    }

    // ---------- 来源 6：协程等待对象 ----------
    private System.Collections.IEnumerator Routine()
    {
        while (true)
        {
            yield return new WaitForSeconds(1f);   // 每次循环都 new 一个
        }
    }

    // ---------- 来源 7：枚举转字符串 ----------
    private void Update_EnumToString()
    {
        Debug.Log(System.DayOfWeek.Monday.ToString());
    }

    // ---------- 来源 8：GetComponents 系列 ----------
    private void Update_GetComponents()
    {
        Collider[] cols = GetComponentsInChildren<Collider>();   // 分配数组
        Debug.Log(cols.Length);
    }

    // ---------- 来源 9：Camera.main ----------
    private void Update_CameraMain()
    {
        // 内部是 FindGameObjectWithTag，有开销
        Camera.main.transform.position = Vector3.zero;
    }

    // ---------- 来源 10：LayerMask.GetMask ----------
    private void Update_GetMask()
    {
        // 每次都要按名字查层号
        int mask = LayerMask.GetMask("Ground");
        Debug.Log(mask);
    }
}

public class Enemy
{
    public float Hp;
}

1字符串拼接"HP: " + hpStringBuilder / TMP SetText / 条件编译
2装箱Debug.LogFormat("{0}", i)泛型容器 / 避免 object 参数
3数组分配Physics.RaycastAll()RaycastNonAlloc + 预分配数组

8GetComponents 系列GetComponentsInChildren<T>()Awake 收集一次并缓存
9Camera.main每帧访问缓存到字段

零分配版本：逐个击破

using UnityEngine;
using System.Collections.Generic;
using UnityEngine.Profiling;

// 为单文件编译补上被引用的类型（原示例里它定义在 gc-source.cs 末尾）
public class Enemy
{
    public float Hp;
}

// ============================================================
//  上面的每一条，这里给出零分配版本
// ============================================================
public class GcFixed : MonoBehaviour
{
    private int _score;
    private float _time;
    private List<Enemy> _enemies = new List<Enemy>();

    // 预分配缓冲区，全程复用
    private readonly RaycastHit[] _hitBuffer = new RaycastHit[16];
    private readonly Collider[] _colliderBuffer = new Collider[32];
    private readonly List<Enemy> _tempList = new List<Enemy>(64);
    private readonly System.Text.StringBuilder _sb = new System.Text.StringBuilder(64);

    // 缓存
    private Camera _cam;
    private static readonly int GroundMask = LayerMask.GetMask("Ground");
    private static readonly System.Comparison<Enemy> HpComparison =
        (a, b) => a.Hp.CompareTo(b.Hp);
    private readonly WaitForSeconds _wait1s = new WaitForSeconds(1f);

    private void Awake()
    {
        _cam = Camera.main;                 // 只查一次
    }

    private void Update()
    {
        _time += Time.deltaTime;

        // ---------- 只在实际变化时更新 UI ----------
        // 而不是每帧无条件刷新
        UpdateUiIfNeeded();

        // ---------- 零分配物理查询 ----------
        int count = Physics.RaycastNonAlloc(
            transform.position, Vector3.down, _hitBuffer, 10f, GroundMask);

        if (count == _hitBuffer.Length)
        {
            Debug.LogWarning("缓冲区可能已满，结果被截断");
        }

        // ---------- 零分配排序 ----------
        _enemies.Sort(HpComparison);

        // ---------- 手写循环代替 LINQ ----------
        _tempList.Clear();
        for (int i = 0; i < _enemies.Count; i++)
        {
            if (_enemies[i].Hp > 0f) _tempList.Add(_enemies[i]);
        }
    }

    private int _lastShownScore = -1;

    private void UpdateUiIfNeeded()
    {
        if (_score == _lastShownScore) return;   // 没变就不动
        _lastShownScore = _score;

        _sb.Clear();
        _sb.Append("Score: ").Append(_score);
        // label.SetText(_sb);   // TMP 的零分配重载
    }

    // 协程复用等待对象
    private System.Collections.IEnumerator Routine()
    {
        while (true)
        {
            yield return _wait1s;   // 复用同一个对象
        }
    }

    // ---------- 测量工具：把分配量打出来 ----------
    public void MeasureAlloc(string label, System.Action action)
    {
        long before = Profiler.GetMonoUsedSizeLong();
        action();
        long after = Profiler.GetMonoUsedSizeLong();
        Debug.Log(label + " 分配: " + (after - before) + " 字节");
    }
}
十条修复规则的记忆口诀 缓存：能缓存的都缓存（组件、相机、Mask、WaitForSeconds）。
复用：能复用的都复用（数组缓冲区、List、StringBuilder）。
延后：不必要的工作别每帧做（UI 只在变化时更新、日志只在编辑器里输出）。
替换：用 NonAlloc 替换 Alloc、用手写循环替换 LINQ、用静态比较器替换闭包。
这四条覆盖了 90% 的 GC 问题。

四、怎么找到你项目里的分配 ★

上面是"通用清单"，但你的项目具体在哪分配，必须用工具查。这一节讲完整的排查流程。

用 Profiler 定位分配来源（五步）

第 1 步：打开 Profiler 的 CPU 模块
Window -> Analysis -> Profiler，选 CPU Usage。如果是真机调试，用 Attach To Player 连上设备。

第 2 步：打开 GC Alloc 列
Hierarchy 视图左上角的列设置图标，勾选 GC Alloc。这一列显示每个函数在当前帧分配了多少字节。

第 3 步：找分配最多的行，按大小排序
点 GC Alloc 列标题排序。重点关注两个位置：① PlayerLoop 下的 Update.ScriptRunBehaviourUpdate；② 分配量大的具体方法名。

第 4 步：点开看调用栈
选中一行，下方会展开调用栈。很多分配不是你写的代码直接产生的——比如 string.Concat 是你那句字符串拼接引起的。顺着调用栈往上找，才能找到"你自己的那一行"。

第 5 步：验证修复效果
改完代码后重新跑，对比同一位置的 GC Alloc。目标是把 Update 相关行的分配降到 0 B。

关于 Deep Profile Deep Profile 会逐方法采样，开销极大——可能让帧率降 10 倍以上，还会自己产生大量分配。
正确的用法：只在排查具体问题时短时间开启，找到线索就关掉。
更精细的做法：用 ProfilerMarker 手动标记关键代码段，这样即使不开 Deep Profile 也能看到分段耗时。 
using Unity.Profiling;
using UnityEngine;

// ============================================================
//  用 ProfilerMarker 手动标记代码段
// ============================================================
public class ProfilerMarkerDemo : MonoBehaviour
{
    // 静态只读：创建 Marker 本身有开销，不要每次新建
    private static readonly ProfilerMarker s_MovementMarker =
        new ProfilerMarker("MySystem.Movement");
    private static readonly ProfilerMarker s_AiMarker =
        new ProfilerMarker("MySystem.AI");
    private static readonly ProfilerMarker s_PathMarker =
        new ProfilerMarker("MySystem.AI.Pathfinding");

    private void Update()
    {
        using (s_MovementMarker.Auto())     // using 作用域 = 采样区间
        {
            UpdateMovement();
        }

        using (s_AiMarker.Auto())
        {
            UpdateAI();
        }
    }

    private void UpdateAI()
    {
        // 可以嵌套，Profiler 里会显示层级
        using (s_PathMarker.Auto())
        {
            // 寻路计算
        }
    }

    private void UpdateMovement() { }

    // ---------- 用 Profiler API 测量分配量 ----------
    public void MeasureAlloc(string label, System.Action action)
    {
        long before = UnityEngine.Profiling.Profiler.GetMonoUsedSizeLong();
        action();
        long after = UnityEngine.Profiling.Profiler.GetMonoUsedSizeLong();
        Debug.Log(label + " 分配: " + (after - before) + " 字节");
    }
}

五、从"少分配"到"缓存友好"

消除分配是第一步。但真正的高手会走到第二步：让数据的内存布局更利于 CPU 读取。这就是页 03 提到的"struct 数组比 class 数组快 2–5 倍"背后的原理。

using UnityEngine;

// ============================================================
//  从"对象数组"到"结构体数组"的演进
// ============================================================

// ---------- 阶段 1：最直观的写法（class 数组）----------
public class UnitClass
{
    public Vector3 Position;
    public float Hp;
    public float Speed;
}
// 问题：
// 1) 每个 UnitClass 都是堆对象，有 16 字节对象头开销（64 位平台的 Mono/IL2CPP：同步块指针 8 + 方法表指针 8）
// 2) 数组里只存指针，真实数据散落在堆的各处
// 3) 遍历时每次解引用都可能缓存未命中（cache miss）

// ---------- 阶段 2：改成 struct（内存连续）----------
public struct UnitStruct
{
    public Vector3 Position;   // 12 字节
    public float Hp;           // 4 字节
    public float Speed;        // 4 字节
}
// 收益：
// 1) 零 GC 分配（值类型数组）
// 2) 内存完全连续：64 字节缓存行能装 3 个 UnitStruct
// 3) 遍历速度提升 2~5 倍

// ---------- 阶段 3：按"访问模式"拆分（SoA）----------
// 如果你只更新位置，不碰血量和速度，那把数据拆开更省缓存
public struct PositionData { public Vector3 Value; }   // 12 字节
public struct HealthData   { public float Value; }     // 4 字节
public struct SpeedData    { public float Value; }     // 4 字节
// 遍历位置时，只需加载 PositionData 数组
// 64 字节缓存行能装 5 个 PositionData（vs 3 个完整 UnitStruct）
// 这就是 ECS（页 18）的核心思想

public class LayoutDemo : MonoBehaviour
{
    private UnitStruct[] _units = new UnitStruct[10000];

    private void Update()
    {
        float dt = Time.deltaTime;

        // 顺序遍历连续内存，CPU 预取器友好
        for (int i = 0; i < _units.Length; i++)
        {
            // 数组索引是变量，可以直接就地修改
            _units[i].Position += Vector3.forward * (_units[i].Speed * dt);
        }
    }

    // ---------- 对比：List<struct> 的陷阱 ----------
    private System.Collections.Generic.List<UnitStruct> _list =
        new System.Collections.Generic.List<UnitStruct>();

    private void ListTrap()
    {
        // 编译错误 CS1612：List 的索引器返回的是副本，不是变量
        // _list[0].Position += Vector3.one;

        // 正确做法：取出 -> 改 -> 写回（两次结构体拷贝）
        UnitStruct u = _list[0];
        u.Hp -= 10f;
        _list[0] = u;

        // 如果这是热路径，改回数组能省下这两次拷贝
    }
}
什么时候才该做布局优化 答案是：绝大多数时候不需要。先用 Profiler 找到真实瓶颈，再优化。
上面这些技巧只在两种情况值得：① 数据量确实很大（1 万以上），且这是热点循环；② 目标是移动端，需要榨干每一分性能。
写代码的第一优先级永远是正确和可读。过早优化只会让半年后的你调试时想打自己。
