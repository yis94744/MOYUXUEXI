    一、完整排查流程

    性能优化有固定的五步流程。跳过任何一步都会导致白忙。

    步骤做什么工具
    1. 确认现象卡顿？发热？内存涨？具体是什么真机测试
    2. 定位类型CPU / GPU / 内存 / IOProfiler 各模块
    3. 缩小范围哪个系统？哪个函数？Profiler 调用树
    4. 修改验证只改一处，改完立即测Profiler 对比
    5. 回归测试确认没引入新问题全流程跑一遍
    最容易犯的三个错误 ① 凭感觉优化：改了十处，结果改的都是非瓶颈。一次只改一处，才能知道哪处有效。

    ② 在编辑器里测性能：编辑器有额外开销，且很多问题只有真机才暴露。必须连真机 Profile。

    ③ 优化后不复测：改完就提交，结果引入了新 bug 或性能反而下降。每次改动都要测。
    分段计时：最快定位瓶颈的方法 如果 Profiler 调用树太复杂看不清，最有效的办法是手动分段计时：
    var sw = Stopwatch.StartNew();
    // 你的代码
    Debug.Log(sw.ElapsedMilliseconds);

    把系统按模块分段打点，一眼就能看出哪个模块最耗时。这比看 Profiler 的花哨图表更快。

    二、四类瓶颈的定位方法

    类型症状定位工具常见原因
    CPU 逻辑帧率低但 GPU 空闲Profiler CPU每帧查找、LINQ、闭包
    GC 卡顿规律性卡顿（每隔几秒）Profiler GC Alloc页 07 的十大来源
    GPU 渲染CPU 空闲但帧率低Profiler GPU / Frame DebuggerDraw Call、Overdraw
    内存长时间运行后崩溃Memory Profiler资源泄漏、未卸载
    GC 卡顿的识别特征 规律性卡顿是 GC 的典型症状——每隔几秒卡一下，而不是持续低帧。
    原因：每帧产生固定量的垃圾，累积到阈值后 GC 触发一次全停顿。

    验证方法：Profiler 里看 GC.Collect 的调用时间点，是否与卡顿时刻吻合。

    解决：回到页 07 的十大来源清单，逐个消除。目标是把 Update 相关的分配降到 0 B。

    三、移动端的特殊考量

    移动端与 PC 的三个关键差异 ① 发热降频：手机跑几分钟后会降频，帧率从 60 掉到 30。
    → 要测"连续运行 10 分钟后的帧率"，而不是刚启动的。

    ② 内存更紧张：中低端机可用内存可能只有 1~2 GB。
    → 资源加载要更保守，卸载要更积极。

    ③ GPU 带宽受限：移动 GPU 的显存带宽远低于 PC。
    → Overdraw 的代价比 PC 上大得多，半透明要格外克制。
    真机调试的三种方式 ① USB 连接 + Profiler Attach：最常用，能看到完整的 Profiler 数据。
    ② Development Build + Autoconnect：打包时勾选 Development Build。
    ③ 设备日志：用 adb logcat（Android）抓日志，分析崩溃。

    注意：Development Build 本身有性能开销，测出的数字比正式包略差。测绝对性能要用正式包 + 代码内计时。

    四、优化收益的优先级

    同样是花一小时，收益可能差 10 倍。按这个顺序做：

    优先级手段典型收益工作量
    1消除 Update 里的 GC 分配消除规律性卡顿小
    2缓存每帧查找的组件/相机显著降 CPU小
    3拆分 Canvas、关 Raycast Target显著降 UI 开销小
    4合批、降 Draw Call显著降渲染开销中
    5关阴影、降后处理显著降 GPU小
    6对象池减少 GC 峰值中
    7降分辨率 / 画质分级兜底方案小
    8Job System / DOTS数量级提升大
    为什么把 DOTS 放最后 因为它的迁移成本最高——需要重写整个模块，还要团队熟悉数据导向设计。
    而前面七项往往能把性能提升 2~5 倍，且改动量小得多。

    只有当这些都做完还不够时，才考虑 DOTS。
