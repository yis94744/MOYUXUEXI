1.1值类型 vs 引用类型

这是 C# 里唯一一个必须彻底搞懂、且无法靠经验绕过去的概念。搞错它，代码会以"看起来完全正确但行为不对"的方式失败。

一句话定义

  • 值类型：变量里直接装着数据本身。赋值 = 把内容复制一份。
  • 引用类型：变量里装着"东西在哪"的地址。赋值 = 把地址复制一份，两个变量指向同一个对象。
值类型：数据内联存储
Vector3 a = (1, 0, 0)12 字节，数据本身
Vector3 b = (1, 0, 0)独立的一份拷贝
改 b.x → a 完全不受影响
引用类型：数据在堆，变量存地址
list1 → 0x7F2A…只是个地址
list2 → 0x7F2A…同一个地址
改 list2 → list1 跟着变
哪些是值类型，哪些是引用类型
类别具体类型关键说明
值类型struct · enum · 所有数值类型 · bool · char · decimal · DateTime赋值即拷贝

using UnityEngine; using System.Collections.Generic; public class ValueVsReference : MonoBehaviour { private void Start() { // ============ 值类型：赋值即拷贝 ============ Vector3 a = new Vector3(1f, 0f, 0f); Vector3 b = a; // 拷贝了三个 float，a 和 b 从此无关 b.x = 999f; Debug.Log("a.x = " + a.x); // 1 ← a 完全不受影响 Debug.Log("b.x = " + b.x); // 999 // ============ 引用类型：赋值即共享 ============ var list1 = new List<int> { 1, 2, 3 }; var list2 = list1; // 两者指向同一个 List 对象 list2.Add(4); // 通过 list2 改对象 Debug.Log("list1.Count = " + list1.Count); // 4 ← list1 也变了！ // 想真正复制一份 List，必须显式新建并逐元素拷贝 var list3 = new List<int>(list1); // 拷贝构造函数 list3.Add(5); Debug.Log("list1.Count = " + list1.Count); // 4 ← 这次没变 Debug.Log("list3.Count = " + list3.Count); // 5 // ============ Unity 特有：Transform 是引用类型 ============ Transform t1 = transform; Transform t2 = transform; // ReferenceEquals 判断两个引用是否指向同一个对象 Debug.Log("同一实例？ " + ReferenceEquals(t1, t2)); // True // 由于是同一个对象，通过 t2 改位置，t1 也会变 t2.position = new Vector3(5f, 0f, 0f); Debug.Log("t1.position = " + t1.position); // (5.0, 0.0, 0.0) } }
"值类型在栈上、引用类型在堆上" 是不准确的说法

准确表述是：值类型内联存储在它所属的位置——

  • 是方法局部变量 → 在栈上
  • 是类的字段 → 就在堆上，跟对象连在一起
  • 是数组元素 → 就在数组里，连续排列

所以"值类型一定快"也是错的：一个 96 字节的 struct 每次传参都要复制 96 字节，比传一个 8 字节的引用慢得多。

CS1612：返回 struct 的属性不能被直接改成员

这是 Unity 新手遇到的第一个编译错误，几乎人手一次。它的报错原文是：

CS1612

Cannot modify the return value of 'Transform.position' because it is not a variable

中文：无法修改 "Transform.position" 的返回值，因为它不是变量。

using UnityEngine; public class PositionTrap : MonoBehaviour { private void Start() { // ❌ 编译错误 CS1612 // transform.position.x = 5f; // 为什么？因为 position 是「属性」，它的 get 访问器 // 返回的是一个 Vector3 临时副本。你改副本，原对象纹丝不动。 // 编译器干脆直接禁止这种写法，避免你写出无效代码。 // ============ ✅ 写法一：取出 → 改 → 写回 ============ Vector3 p = transform.position; // p 是一个独立的 Vector3 p.x = 5f; // 改的是 p transform.position = p; // 整体写回，触发 set 访问器 // ============ ✅ 写法二：用内置 API（推荐）============ // 只需一次 native 调用，比上面"读-改-写"三次调用更省 transform.Translate(5f, 0f, 0f, Space.World); // ============ ✅ 写法三：SetPositionAndRotation（Unity 2022.1+）============ // 一次设置位置和旋转，只需一次内部同步 transform.SetPositionAndRotation(new Vector3(5f, 0f, 0f), Quaternion.identity); } }

in 参数：给 struct 传参的零拷贝写法

C# 7.2 引入的 in 关键字，让 struct 以只读引用的方式传递：既不复制内容，也不允许修改。

using UnityEngine; public static class Geometry { // ❌ 普通值传递：每次调用复制 12 字节（Vector3 = 3 个 float） // 10 万次/帧 → 1.2 MB 的纯拷贝开销 public static float SqrMagnitudeOld(Vector3 v) { return v.x * v.x + v.y * v.y + v.z * v.z; } // ✅ in 参数：零拷贝，且方法内不能修改 v public static float SqrMagnitudeNew(in Vector3 v) { // v.x = 1f; // ❌ 编译错误：in 参数是只读的 return v.x * v.x + v.y * v.y + v.z * v.z; } // 需要一个可修改的副本时，先拷贝出来 public static Vector3 Flattened(in Vector3 v) { Vector3 copy = v; // 这时才产生一次拷贝 copy.y = 0f; return copy; } // ref 参数可读可写，但调用方必须显式写 ref public static void ClampInPlace(ref Vector3 v, float max) { float sq = v.x * v.x + v.y * v.y + v.z * v.z; if (sq > max * max) v = v.normalized * max; } } public class InDemo : MonoBehaviour { private void Start() { Vector3 pos = new Vector3(3f, 4f, 0f); // 调用时可以省略 in（编译器自动处理） float sq = Geometry.SqrMagnitudeNew(pos); Debug.Log("sqrMagnitude = " + sq); // 25 // 也可以显式写出 in，语义更清晰 float sq2 = Geometry.SqrMagnitudeNew(in pos); Debug.Log("sqrMagnitude = " + sq2); // 25 // ref 参数必须显式写 ref Geometry.ClampInPlace(ref pos, 2f); Debug.Log("clamped = " + pos); // (1.2, 1.6, 0.0) } }
什么时候值得用 in
  • 值得：方法被高频调用（每帧数千次以上），且参数是较大的 struct（Matrix4x4 64 字节、Bounds 24 字节、RaycastHit 40+ 字节）。
  • 不值得：参数是引用类型（引用本身只有 4/8 字节，加 in 反而多一层间接寻址）。
  • 不值得：小 struct 如 Vector2Int（8 字节），拷贝成本和一次指针传递差不多。

版本要求：in 参数需要 Unity 2018.3+（C# 7.3）。

装箱（Boxing）与拆箱（Unboxing）

把值类型塞进 object，运行时会在堆上新建一个"箱子"把值装进去。这是 Unity 里 GC 压力的头号来源之一，而且大多数时候是隐式发生的——你看不见它。

using UnityEngine; using System.Collections; using System.Collections.Generic; public class BoxingDemo : MonoBehaviour { private void Start() { int hp = 100; // ============ 显式装箱 ============ object boxed = hp; // ① 堆上分配一个箱子，把 100 装进去 int back = (int)boxed; // ② 拆箱：类型检查 + 取值 Debug.Log(back); // 100 // ============ 隐式装箱（更危险，因为你看不见）============ // ① 字符串拼接：编译器生成 string.Concat(object, object) Debug.Log("HP = " + hp); // int → object → 装箱 // ② 非泛型容器 var arrayList = new ArrayList(); arrayList.Add(hp); // 装箱 arrayList.Add(Vector3.zero); // Vector3 也装箱（12 字节） // ③ params object[] 参数 string s = string.Format("{0}", hp); // 装箱 Debug.LogFormat("HP = {0}", hp); // 装箱（params object[]，官方已确认无法避免） // ④ 枚举转字符串 System.DayOfWeek day = System.DayOfWeek.Monday; string dayName = day.ToString(); // 反射查找名字，可能装箱 Debug.Log(s + dayName); } } // ============================================================ // 正确做法：全程用泛型 + 避免隐式转换 // ============================================================ public class NoBoxingDemo : MonoBehaviour { private readonly List<int> _numbers = new List<int>(); // ✅ 零装箱 private readonly List<Vector3> _points = new List<Vector3>(); // ✅ 零装箱 private void Start() { for (int i = 0; i < 100; i++) { _numbers.Add(i); // 泛型容器：值类型按原样存进内部数组 _points.Add(new Vector3(i, 0f, 0f)); } // ✅ 显式 ToString()，避免经过 object 中转 Debug.Log("数量 = " + _numbers.Count.ToString()); // ✅ 高频日志用条件编译彻底去掉，发布版一行不留 LogVerbose("这一行只在编辑器和开发构建里存在"); } [System.Diagnostics.Conditional("UNITY_EDITOR")] [System.Diagnostics.Conditional("DEVELOPMENT_BUILD")] private static void LogVerbose(string msg) { Debug.Log("[Verbose] " + msg); } }

using UnityEngine; // ============================================================ // 真实项目里最常见的「每帧装箱」写法（都在这段里） // ============================================================ public class BoxingInUpdate : MonoBehaviour { private int _score = 0; private float _timer = 0f; // ❌ 反例：每帧都在装箱 + 拼字符串 private void BadUpdate() { _timer += Time.deltaTime; // 每帧 3 次字符串分配 + 1 次装箱 if (_timer > 1f) { _timer = 0f; _score++; // string.Concat(object, object, object) → int 装箱 Debug.Log("Score: " + _score + " / Time: " + Time.time); } } // ✅ 正例一：只在需要时格式化，且用 ToString 避免装箱 private void GoodUpdate1() { _timer += Time.deltaTime; if (_timer > 1f) { _timer = 0f; _score++; // 仍然有字符串分配，但少了装箱 Debug.Log("Score: " + _score.ToString() + " / Time: " + Time.time.ToString("F1")); } } // ✅ 正例二：发布版彻底不执行（条件编译） private void GoodUpdate2() { _timer += Time.deltaTime; if (_timer > 1f) { _timer = 0f; _score++; LogScore(_score, Time.time); } } // 整个调用点 + 方法体在非编辑器/非开发构建下会被编译器完全移除 [System.Diagnostics.Conditional("UNITY_EDITOR")] [System.Diagnostics.Conditional("DEVELOPMENT_BUILD")] private static void LogScore(int score, float time) { Debug.Log("Score: " + score + " / Time: " + time); } // ✅ 正例三：需要显示到 UI 时，用 TextMeshPro 的零分配重载 // TMP_Text.SetText("{0}", value) 内部用 StringBuilder，不产生装箱 // // [SerializeField] private TMPro.TMP_Text _scoreLabel; // private void Update() { _scoreLabel.SetText("Score: {0}", _score); } }
哪些情况其实不装箱（避免过度焦虑）
  • List<int>、Dictionary<string, Vector3> 等泛型容器不装箱——泛型参数在运行时会为值类型生成专用代码。
  • Dictionary<枚举, T> 在 Unity 2018.3+ 的 .NET 4.x 下不装箱（编译器生成了专用的 EqualityComparer）。
  • string.Concat 在 C# 编译器优化下会绕过装箱："a" + 1 实际会调用 string.Concat(string, string)，而 int → string 是通过 ToString() 完成的。
  • 但 string.Format("{0}", hp) 确实会装箱（因为签名是 params object[]）。

结论：不要凭记忆猜，直接用 Profiler 看 GC Alloc。这是唯一可靠的方法。

struct 与 class 的选型

✅ 用 struct 的场景
  • 体积小：≤ 16 字节（约等于 4 个 int）
  • 逻辑上是"值"而不是"东西"：坐标、颜色、范围、伤害数值
  • 声明为 readonly struct（不可变）
  • 生命周期短、创建频繁
  • 需要数组连续存储来获得缓存友好性
❌ 该用 class 的场景
  • 需要继承（struct 不能继承）
  • 需要引用语义（多处共享同一份数据）
  • 体积大（> 24 字节）
  • 需要 null 表示"不存在"
  • 会被装箱（塞进 object 或非泛型集合）
  • 需要被 Unity 序列化为多态字段
完整实例：战斗伤害系统的 struct 设计
using UnityEngine; // ============================================================ // 实战：伤害信息用 readonly struct —— 12 字节的精致体积 // ============================================================ public readonly struct DamageInfo { public readonly float Amount; // 4 字节 public readonly int AttackerId; // 4 字节 —— 用 int 而不是 GameObject 引用 // 避免意外持有对象导致无法回收 public readonly byte DamageType; // 1 字节 public readonly byte Flags; // 1 字节（bit0 = 暴击，bit1 = 格挡…） public DamageInfo(float amount, int attackerId, byte damageType, byte flags) { Amount = amount; AttackerId = attackerId; DamageType = damageType; Flags = flags; } public bool IsCritical { get { return (Flags & 1) != 0; } } public bool IsBlocked { get { return (Flags & 2) != 0; } } // readonly struct 的 ToString 不会装箱（编译器有优化） public override string ToString() { return "伤害 " + Amount + " 来自 #" + AttackerId; } } // ============================================================ // 对比：同样逻辑用 class 实现 // ============================================================ public class DamageInfoClass { public float Amount; public GameObject Attacker; // 引用 → 会阻止对象被回收 public string DamageTypeName; // 字符串引用 → 额外的堆对象 public bool IsCritical; // 对象头 16 字节 + 字段 + 对齐 ≈ 48 字节以上，且每次都要走 GC } // ============================================================ // 接收方 // ============================================================ public class DamageReceiver : MonoBehaviour { [SerializeField] private float _maxHp = 100f; private float _hp; private void Awake() { _hp = _maxHp; } // ✅ struct 按值或 in 传入：调用方拿到的是快照，方法内改不了原数据 public void TakeDamage(in DamageInfo info) { float final = info.IsCritical ? info.Amount * 1.5f : info.Amount; if (info.IsBlocked) final *= 0.5f; _hp -= final; _hp = Mathf.Max(0f, _hp); Debug.Log(name + " 受到 " + final.ToString("F1") + " 点伤害，剩余 " + _hp.ToString("F1")); if (_hp <= 0f) Die(); } private void Die() { Debug.Log(name + " 已阵亡"); } public float CurrentHp { get { return _hp; } } } // ============================================================ // 发布方 // ============================================================ public class Weapon : MonoBehaviour { [SerializeField] private float _baseDamage = 25f; [SerializeField] private float _critRate = 0.3f; public void Fire(Vector3 origin, Vector3 direction) { if (!Physics.Raycast(origin, direction, out RaycastHit hit, 100f)) return; if (!hit.collider.TryGetComponent(out DamageReceiver receiver)) return; bool isCrit = Random.value < _critRate; byte flags = isCrit ? 性能对比：struct 数组 vs class 数组
using UnityEngine; // ⚠️ 注意：System.Diagnostics 与 UnityEngine 都有 Debug 类， // 同时 using 会产生 CS0104 歧义，所以这里用全限定名 System.Diagnostics.Stopwatch。 // using System.Diagnostics; // ============================================================ // struct 数组 vs class 数组：实测缓存友好性差异 // ============================================================ public class BenchmarkStructVsClass : MonoBehaviour { private const int Count = 200000; private const int Loops = 50; private struct UnitStruct { public float X, Y, Z; public float Hp; // 16 字节 } private class UnitClass { public float X, Y, Z; public float Hp; } private void Start() { // ---------- 准备数据 ---------- var structs = new UnitStruct[Count]; var classes = new UnitClass[Count]; for (int i = 0; i < Count; i++) { structs[i] = new UnitStruct { X = i, Y = i, Z = i, Hp = 100f }; classes[i] = new UnitClass { X = i, Y = i, Z = i, Hp = 100f }; } // ---------- 测 struct ---------- var sw = System.Diagnostics.Stopwatch.StartNew(); for (int l = 0; l < Loops; l++) { for (int i = 0; i < Count; i++) { structs[i].Hp -= 0.01f; // 数组索引是变量，可直接就地修改 } } sw.Stop(); long msStruct = sw.ElapsedMilliseconds; // ---------- 测 class ---------- sw.Restart(); for (int l = 0; l < Loops; l++) { for (int i = 0; i < Count; i++) { classes[i].Hp -= 0.01f; // 每个元素都要解引用一次堆对象 } } sw.Stop(); long msClass = sw.ElapsedMilliseconds; Debug.Log("struct 数组: " + msStruct + " ms"); Debug.Log("class 数组: " + msClass + " ms"); Debug.Log("class 慢 " + ((float)msClass / Mathf.Max(1, msStruct)).ToString("F2") + " 倍"); // 典型结果：class 数组慢 2~5 倍 // 原因：引用类型数据散落在堆上，每次访问都可能缓存未命中（cache miss） } }
为什么 struct 数组快 2~5 倍

这不是玄学，而是 CPU 缓存行（cache line）的物理限制。一次内存访问会加载 64 字节：

  • struct 数组：64 字节能拿到 4 个 UnitStruct（每个 16 字节），后续 3 次访问全部命中缓存。
  • class 数组：64 字节只装了 16 个指针。真实数据散落在堆的各个角落，每次解引用都可能是新的内存访问。

这就是 Unity 的 DOTS / ECS 架构的核心思想。同屏上万单位时，把数据从 class 改成 struct 数组，往往是最有效的一步优化。

绝对不要用可变 struct 做字典键

如果 struct 有可写字段，把它放进 Dictionary 后再改它的字段， 它的哈希值就变了，但字典还按原来的桶存放它——从此再也查不到、也删不掉，成为永久泄漏。

规则：所有用作键的 struct 必须声明为 readonly struct。

using UnityEngine; // ============================================================ // readonly struct：编译期保证不可变 // 额外收益：所有成员访问都免除「防御性拷贝」 // ============================================================ public readonly struct DamageResult { public readonly float Raw; // 原始伤害 public readonly float Final; // 减免后伤害 public readonly bool Killed; // 是否击杀 public DamageResult(float raw, float final, bool killed) { Raw = raw; Final = final; Killed = killed; } // ⚡ 关键收益：readonly struct 上访问成员不会产生防御性拷贝。 // 普通 struct 的方法/属性调用，编译器会先复制一份 this // 以防方法内部修改它 —— 高频调用时这会累积成可观开销。 public float ReductionRatio { get { return Raw <= 0f ? 0f : 1f - (Final / Raw); } } } public class ReadonlyDemo : MonoBehaviour { private void Start() { var result = new DamageResult(100f, 75f, false); // 这个属性访问在 readonly struct 上是零拷贝的 Debug.Log("减伤比例: " + (result.ReductionRatio * 100f).ToString("F1") + "%"); // 25.0% } }

Mathf.Approximately 的真实实现（别被"万能"骗了）

Unity 的源码是：

Mathf.Abs(b - a) < Mathf.Max(1E-06f * Mathf.Max(Mathf.Abs(a), Mathf.Abs(b)), Mathf.Epsilon * 8f)

  • 它用的是相对误差：数值越大，允许的绝对误差也越大。
  • 在 1e10 这个量级上，它认为两个相差 1 万 的数是"相等"的。
  • 在 0 附近，它退化成绝对误差 float.Epsilon * 8（极度严格，几乎只对完全相同的位模式返回 true）。

结论：游戏逻辑里比较位置、速度时，用自定义的 sqrMagnitude < epsilon 更可控。

1.3类型转换

类型转换分成三类：隐式（编译器自动做，安全）、显式（你手动写，可能丢数据）、运行时转换（引用类型之间，可能失败）。搞混这三类，就会出现"数值莫名其妙变了"或"运行时突然空引用"。

铁律：重写 Equals 必须重写 GetHashCode

如果你只重写了 Equals 而没重写 GetHashCode，会发生什么？

  • a.Equals(b) 返回 true（你认为它们相等）
  • 但 a.GetHashCode() != b.GetHashCode()（默认按对象地址算）
  • Dictionary / HashSet 先用哈希找桶，再去桶里比较
  • 两个"相等"的对象落在不同的桶里 → 查找失败 → 行为完全不可预测

C# 编译器会给警告 CS0659，但不会报错。Unity 项目里这是很难排查的 bug 之一。

这是 Unity 最著名的"坑"之一。UnityEngine.Object 重载了 == 运算符， 让"已被销毁的对象"在比较时表现为 null：

为什么 Unity 要这么做

Unity 的对象分成两半：C# 侧的托管包装（GameObject 对象本身）和 C++ 侧的 native 对象（真正的场景节点）。 Destroy() 只销毁 native 对象，C# 包装会等到 GC 才回收。

如果 == 不重载，obj == null 就会返回 false， 于是你调用 obj.transform 时直接抛 MissingReferenceException。 重载 == 后，Unity 能同时检查两半，给你一个"直观"的 null 判断。

代价是：这个重载让 UnityEngine.Object 不能直接用作 Dictionary 的键 （哈希和相等语义会冲突），也需要你注意"假 null"带来的列表膨胀问题。

const 的跨程序集陷阱（Unity 项目必踩）

假设你用了 Assembly Definition（asmdef）把项目拆成多个程序集：

  • Game.Core.dll 里定义 public const int MaxLevel = 99;
  • Game.UI.dll 里使用 Config.MaxLevel

现在你把 Core 里的值改成 999，只重新编译 Core.dll—— UI.dll 里仍然是 99！因为 const 的值在编译 UI 时就被内联写死进了 UI.dll 的 IL。

在 Unity 里的表现是：改了常量，部分代码行为没变，重启 Unity / 全量重编译后才生效。 团队协作时这会导致"我这儿是好的，你那儿是坏的"这种诡异问题。

规则：跨程序集共享的数值，一律用 static readonly。 const 只用于真正永远不会变的东西（如数学常量、枚举值）。

ScriptableObject 是 Unity 里做配置的最优解

对比三种配置方式：

  • const：编译期写死，改一个数要重编译整个项目，且跨程序集有内联陷阱。只适合数学常量。

  • static readonly：运行期只读，但仍要改代码重新编译。适合真正的代码级常量。

字符串优化的优先级
  1. 先看 Profiler：确认字符串分配真的是瓶颈（看 GC Alloc 列的来源）。
  2. 消除每帧调用：UI 只在数值变化时更新，而不是每帧无条件刷新。这一步往往能解决 80% 的问题。
  3. 用 TMP 的 SetText 重载：这是性价比最高的一步，改一行代码。
  4. 预格式化 + 缓存：适合数值范围有限的场景（等级、星期、月份）。
  5. StringBuilder 复用：适合复杂拼接，但要注意 ToString() 本身仍会分配。

最后的手段是 ZString、Cysharp 的 UniTask 作者写的零分配字符串库， 或者 Unity 的 FixedString（Burst 环境用）。对普通项目来说，前三步就够了。

NonAlloc 缓冲区太小会静默失败

Physics.RaycastNonAlloc 返回的是实际写入的元素数量。 如果缓冲区装不下所有命中，它不报错，而是静默截断——你只会得到前 N 个结果， 而且逻辑上完全看不出问题（比如"子弹明明该打中最近的敌人，却打到了后面的"）。

实战做法：

  • 开发期把数组开大一些（32 或 64），并检查返回值是否接近数组长度，接近时打警告。

List 中 struct 元素的修改陷阱（CS1612 的另一种形态）

List<T> 的索引器本质是方法 get_Item，返回的是副本。 所以对 struct 元素的字段修改会直接编译失败：

_list[0].position.x = 5f;   // ❌ CS1612

正确写法是取出 → 改 → 写回：

var v = _list[0]; v.position.x = 5f; _list[0] = v;

如果这个 List 在热路径上（每帧遍历上万次），"取出-写回"意味着两次结构体拷贝。 这种情况改用数组——数组索引是变量，可以直接就地修改。

Dictionary 的遍历顺序是不确定的

你可能会发现"添加顺序和遍历顺序正好一样"——这是巧合，不是保证。

NativeContainer 的五条铁律
  1. 必须 Dispose。用 try/finally 或 using 保证释放，异常路径也不能漏。
  2. Job 里不能用托管对象：不能 new 类、不能碰 GameObject、不能 Debug.Log、不能 try/catch。
  3. Schedule 后要有依赖或 Complete，否则会产生竞态（Job 还在读，主线程已经在写）。
  4. Burst 只支持有限的 API，尽量用 Unity.Mathematics（float3、math.sin）。
  5. 不要跨 Job 持有引用，数据传递只能通过 NativeContainer。

本章真正的三个核心结论
  1. 结构体是值，类是引用——这决定了赋值、传参、修改的全部行为。Unity 的 Vector3、Quaternion、Color 都是结构体。
  2. 每个隐蔽的错误都有对应的工具能看到——CS1612 是编译器帮你拦住了；装箱和字符串分配要用 Profiler 的 GC Alloc 列看；假 null 要在容器的清理逻辑里防。
  3. 性能优化永远排在正确性之后——in 参数、readonly struct、数组替代 List、short 压缩坐标，这些手段只有在你确认了瓶颈之后才值得用。
