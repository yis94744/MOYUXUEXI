    一、AI 辅助开发的真实效果

    先说结论：AI 在"有明确输入的样板代码"上非常强，在"需要判断的设计决策"上很弱。

    任务类型AI 效果原因
    样板代码（属性、DTO、配置类）很好模式固定
    API 用法查询中等可能给出过时 API
    算法实现好经典问题有标准答案
    性能优化差需要实际测量
    架构设计差需要理解业务上下文
    调试难查的 bug中等能给方向，但要自己验证
    AI 的最大风险：看似正确的错误 AI 最危险的不是"不知道怎么答"，而是"自信地给出错误答案"。
    常见的有：
    · 用了已经过时的 Unity API（比如 Unity 6 里 velocity 改名 linearVelocity）
    · 给出在当前 Unity 版本不支持的 C# 语法（比如 C# 10 的 record struct）
    · 参数顺序或类型错误（尤其是不常用的 API）

    防御方法：把 AI 给的代码直接扔进编译器。编译器是唯一不会骗你的裁判——这也是本站所有代码都用编译器验证的原因。
    怎么用 AI 才能真正提效 ① 让它写"有明确模式"的代码：DTO、配置解析、重复的样板逻辑。
    ② 用它做"知识查询"但必须验证：问 API 用法后，去官方文档或程序集里核对。
    ③ 用它做 code review 的第二双眼睛：让它找空引用、资源泄漏、边界条件。
    ④ 不要让它做性能决策：性能只能靠测量。
    ⑤ 不要让它设计架构：它不了解你的业务、团队、时间约束。

    二、AI NPC 的架构

    把 LLM 接进游戏做 NPC，是技术上可行、工程上要小心的事。核心是四步循环：

    步骤做什么关键约束
    1. 感知收集上下文（玩家位置、对话历史）数据量要控制
    2. 决策调 LLM 生成行为或对话延迟 1~3 秒
    3. 过滤安全审核、格式校验必须做，否则会输出不当内容
    4. 执行映射到游戏行为只能执行白名单内的行为
    AI NPC 的四个工程问题 ① 延迟：LLM 响应通常 1~3 秒。玩家等不了这么久。
    解决：预生成部分回复、用本地小模型做初步响应、异步生成 + 打字机效果。

    ② 成本：每次调用都要钱。一个活跃 NPC 频道可能每天几万次调用。
    解决：缓存常见问答、限制调用频率、只在关键节点调用。

    ③ 安全：LLM 可能输出不当内容或"越狱"行为。
    解决：输出必须过审核 + 执行必须走白名单。绝不能让 LLM 直接产生游戏行为指令。

    ④ 一致性：NPC 会"忘记"之前说过的话。
    解决：维护对话摘要 + 关键信息表，作为每次请求的上下文。
    适用与不适用场景 适合：
    · 模拟经营 / 沙盒游戏的 NPC 对话
    · 侦探游戏的动态线索
    · 玩家自定义的剧情
    · 非实时性要求高的场景

    不适合：
    · 竞技游戏的对抗 AI（延迟和确定性都不满足）
    · 需要精确数值平衡的战斗
    · 大规模 NPC（成本爆炸）

    结论：LLM 适合"表达"，不适合"对抗"。
