7status 状态码全解

svn status 是 SVN 里使用频率最高的命令，也是信息密度最高的。 它的输出前七列每列一个字符宽，每列表示一种不同维度的状态。 很多人以为只有两列——这是最常见的误读，会导致完全相反的结论。

先记住这个结论：status 有七列，不是两列

官方文档（svn help status）原文：The first seven columns in the output are each one character wide。 下面这七列各管一件事：内容、属性、工作副本锁、复制历史、切换/外部、仓库锁、树冲突。 用 -u 时还有第 9 列表示服务器是否有更新。

◈图 7-1　status 输出的七列结构解剖（依据 svn help status 实测）Output Anatomy
最容易踩的坑：M 出现在第 1 列还是第 2 列，含义完全不同—— 第 1 列是文件内容变了，第 2 列（前面有个空格）是属性变了。 同理 X 在第 1 列是「externals 创建的外部目录」， 在第 5 列是「externals 定义的版本控制文件」——两者都不是同一个意思。

所有状态码实测

bash构造所有状态码并观察

touch newfile.txt && svn add newfile.txt

# M —— 修改已跟踪文件（第 1 列）

# M —— 修改属性（第 2 列！注意前导空格）

# D —— 标记删除

# ? —— 未版本控制

# ! —— 缺失（绕过 svn delete 直接删）

# I —— 被 svn:ignore 忽略（默认不显示）

# 一次性看全部
svn status
svn status --no-ignore      # 连被忽略的也列出来

! 缺失：最需要立刻处理的异常状态

! 产生的原因只有一个：你绕过了 SVN 直接删文件—— 用 rm / del / 在资源管理器里按 Delete。 SVN 的元数据里还记着这个文件，但磁盘上找不到了。

✗ 错误做法：直接删文件
rm src/old.cpp

$ svn status
!       src/old.cpp
# 状态异常，提交时会报错

$ svn commit -m "删除旧文件"
svn: E200009: Commit failed
'src/old.cpp' is scheduled for addition,
but is missing from the working copy
✓ 正确做法：用 svn delete
svn delete src/old.cpp

$ svn status
D       src/old.cpp
# 状态正常，文件也从磁盘移除了

$ svn commit -m "删除旧文件"
Deleting       src/old.cpp
Committed revision 12.
# 顺利提交，历史里留下了完整记录
实测：! 状态的两种补救方式
PowerShell
# 场景：误删了 src\main.cs
$ Remove-Item src\main.cs -Force
$ svn status
!       src\main.cs

# 补救方式一：我其实不想删 → update 找回来
$ svn update
Updating '.':
Restored 'src\main.cs'          ← 从 pristine / 服务器恢复
At revision 17.

# 补救方式二：确实要删 → 补一个登记动作
$ svn delete --force old-file.txt
D         old-file.txt               ← 即使文件已经不在，也能标记删除

# 补救方式三：批量处理一堆 ! （比如清空了一个目录）
$ svn status | Select-String "^!" | % { svn delete --force $_.ToString().Substring(8).Trim() }
铁律：删除文件永远用 svn delete，不要用 rm

同理，重命名永远用 svn move，不要用 mv / 右键重命名。 原因见第 22 节：svn move 会记录「这是同一次移动」，历史才不会断； 而 mv 在 SVN 看来是「删了一个文件 + 加了一个新文件」，追溯历史时会断掉。

单人开发、多人协作、紧急修复——所有场景最后都收敛成同一个循环： update → 改 → status → diff → update → commit。 这一节把循环里的 update、log、diff 三个命令挖到底。

◈图 8-1　多人协作的日常循环与冲突预防Daily Loop

update：不只是「拉代码」

bashupdate 的高级用法
svn update                          # 把整个工作副本更新到 HEAD
svn update src/                     # 只更新某个目录
svn update README.md config.json    # 只更新指定文件
svn update -r 100                   # 更新到指定版本 r100（不是最新）
svn update --revision PREV          # 回退到上一个版本（常用！）
svn update --revision BASE          # 回到工作副本的基准版本（丢弃所有更新）

# 冲突处理策略（重要，脚本里必用）
svn update --accept postpone        # 冲突了就放着，产生冲突标记（默认行为）
svn update --accept mine-full       # 冲突时全用我的
svn update --accept theirs-full     # 冲突时全用服务器的
svn update --accept mine-conflict   # 只在本文件的冲突块用我的
svn update --accept theirs-conflict # 只在冲突块用服务器的
svn update --accept base            # 丢弃双方改动，回到原始版本

# 其他常用
svn update --force                  # 强制覆盖，即使有未版本控制的同名文件
svn update --ignore-ancestry        # 忽略祖先关系，直接覆盖（慎用）
svn update --set-depth infinity .   # 把稀疏工作副本变回完整（第 22 节）
svn update --non-interactive        # 脚本必备，遇冲突不卡住等输入
脚本里必须加 --non-interactive 和 --accept

SVN 默认遇到冲突会弹出交互式选择菜单，等待你输入字母。 在 CI / 定时任务 / 批处理脚本里，这会让进程永久挂起。

本教程在实测阶段就踩过这个坑——一个看似简单的 update 命令阻塞了 120 秒后被强制中断。 正确写法：

svn commit -m "auto build" --non-interactive

log：查历史，但有个大坑

实测踩坑：svn log -l 1 显示的不是最新提交！

这是 SVN 新手最困惑的行为之一。svn log 默认从工作副本的 BASE 版本开始往回走， 而不是从服务器的最新版本。如果你很久没 update 过，log 给你看的就是「你本地那个古老时间点」的历史。

实测：这个坑长什么样

↑ 显示的是 r9 而不是 r10！
  因为 log 从工作副本 BASE（r9）开始往回数

# 正确写法一：显式指定从 HEAD 开始
$ svn log -r HEAD -l 1
------------------------------------------------------------------------
r10 | kelang | 2026-10-08 11:02:58 | 1 line
↑ 这才是服务器上真正的最后一次提交

# 正确写法二：先 update 再 log
$ svn update; svn log -l 1

At revision 10.

r10 | kelang | 2026-10-08 11:02:58 | 1 line

# 正确写法三：用 URL 而不是工作副本路径
$ svn log -l 1 file:///E:/repo/trunk
URL 形式默认从 HEAD 开始，没有这个坑

diff：三种比较维度

bashdiff 的三种比较对象
# 【维度一】工作副本 vs BASE —— 看我自己改了什么（最常用）
svn diff
# 等价于 svn diff -r BASE，BASE 就是最近一次 update 拿到的那份

# 【维度二】任意两个版本之间 —— 看别人/历史改了什么
svn diff -r 5:8
svn diff -r 5:HEAD
svn diff -c 8                  # 只看 r8 这一次提交引入的改动（= -r 7:8 的简写）
svn diff -r "{2026-10-01}:HEAD"

# 【维度三】URL 之间 —— 比较分支/标签
svn diff file:///repo/trunk file:///repo/branches/feature
svn diff ^/trunk ^/branches/feature        # 用 ^ 简写仓库根（工作副本内可用）

# 输出控制（很实用）
svn diff --summarize           # 只列文件名，不要内容（大改动时先扫一遍）
svn diff --git                  # 1.9+ 支持的 git 风格 diff，方便贴到别处
svn diff --diff-cmd meld        # 调用外部图形化对比工具
svn diff --internal-diff        # 强制用内置引擎（当外部工具配置出错时救急）
svn diff --no-diff-added        # 新增文件不显示全部内容（新增大文件时避免刷屏）

# 保存为补丁文件
svn diff > my.patch
svn diff --file my.patch        # 等价写法，Windows PowerShell 下推荐这个

# 应用补丁
svn patch my.patch
svn patch my.patch --dry-run    # 试运行，不实际改动（先验证再应用）
svn patch --reverse-diff my.patch  # 反向应用（撤销补丁）

# 用第三方 diff 工具（配置在 ~/.subversion/config 的 diff-cmd）
svn diff --diff-cmd diff -x "-u"
Windows PowerShell 下重定向会毁掉补丁文件

实测踩过的坑：在 PowerShell 里执行 svn diff > my.patch， PowerShell 默认用 UTF-16 LE 编码写文件，结果补丁开头多了 FF FE BOM 字节， 用 svn patch 应用时会报 Malformed dumpfile header 之类的解析错误。

解决方案（三选一）：

  • 用内置参数：svn diff --file my.patch（推荐，跨平台一致）
  • 用 cmd 重定向：cmd /c "svn diff > my.patch"
  • 改用 Git Bash / WSL 执行命令

9撤销与回退：五种「后悔」场景

「我改错了」「我想回到上个版本」「这个提交整个不要了」—— 这是 SVN 里最容易混淆的一组操作，因为撤销本地改动和撤销已提交的改动完全是两回事。

◈图 9-1　回退的五种场景与对应命令Rollback Matrix
决策口诀：没提交 → revert； 已提交想抵消 → merge -c -N + commit； 只想看看过去 → update -r / cat -r； 要从历史抹掉 → svnadmin dump/load（极危险）。 SVN 里「撤销已提交」永远是「再提交一次反向改动」，而不是删除历史——这是集中式系统的安全基石。
实测：revert 撤销本地修改
PowerShell
# 改了文件，status 显示 M
$ svn status
M       README.md

# 后悔了，撤销
$ svn revert README.md
Reverted 'README.md'

# 验证：干净了
$ svn status
<空输出 = 已恢复>

# 递归撤销整个工作副本的所有本地改动（慎用！）
$ svn revert -R .
Reverted '.'                    ← 会逐层列出被撤销的路径

# 撤销「添加」动作：A 变回 ?
$ svn revert newfile.txt
Reverted 'newfile.txt'
$ svn status
?       newfile.txt            ← 回到未跟踪状态，文件还在
revert 是不可逆的

svn revert 会把文件内容恢复成 pristine 副本（最近一次 update 拿到的那份）， 你所有未提交的修改会永久丢失，无法通过 SVN 找回。

养成习惯：revert 之前先 svn diff --file backup.patch 存一份， 至少给自己留条后路。IDE 的本地历史（如 VS Code 的 Timeline、JetBrains 的 Local History）也能救急。

撤销已提交的改动：反向合并

对于已经提交上去的错误改动，标准做法是「再提交一次反向补丁」。 svn merge -c -10 里那个负号就是关键——它表示「反向应用」。

bash撤销已提交改动的标准流程
# 前提：你的工作副本是干净的，且在正确的分支/目录上
cd wc
svn update --non-interactive

# 第 1 步：先看看 r10 到底改了什么（确认没找错对象）
svn log -v -c 10
svn diff -c 10

# 第 2 步：反向合并 r10（注意那个负号！）
svn merge -c -10 .
# 执行后工作副本里，r10 的改动被「倒回去」了，但还没提交

# 第 3 步：确认结果符合预期
svn status
svn diff

# 第 4 步：提交这次回退
svn commit -m "回退 r10：该版本引入了错误的登录逻辑"
# 得到一个新版本号（比如 r13），历史完整保留

# ---- 撤销多个版本 ----
svn merge -c -10,-11,-12 .              # 撤销三个不连续的版本
svn merge -r 12:9 .                     # 撤销 r10~r12（反向区间）

# ---- 只想撤销某次提交里的一部分文件 ----
svn merge -c -10 src/login.cs           # 只回退这个文件的改动

# ---- 撤销还没提交的 merge 结果（反悔了）----
svn revert -R .
svn cleanup                              # 清掉 mergeinfo 的中间状态

只想看历史版本，不想改动

bash查看历史版本的四种方式
# 方式一：看单个文件的历史内容（不落盘，最轻量）
svn cat -r 8 README.md
svn cat -r 8 file:///repo/trunk/README.md

# 方式二：导出某个版本的干净副本（无 .svn 目录）
svn export -r 8 file:///repo/trunk ./release-8/
svn export file:///repo/tags/v1.0 ./v1.0/

# 方式三：把整个工作副本拨回某个版本（可随时回来）
svn update -r 8
# 此时 svn info 会显示 Revision: 8，但这是「混合版本」状态
svn update                    # 回到最新

# 方式四：取回一个已删除的文件
svn cat -r 5 file:///repo/trunk/deleted-file.txt > recovered.txt
# 或先记下路径再复制回来
svn copy -r 5 file:///repo/trunk/deleted-file.txt ./recovered.txt
svn commit -m "恢复被删除的 deleted-file.txt"

# 方式五：把某个文件回退到历史版本（但其他文件不动）
svn merge -c -8 README.md     # 只回退这个文件在 r8 的改动
# 或直接取出旧内容覆盖
svn cat -r 8 README.md > README.md
svn commit -m "README 回退到 r8 内容"
快捷键：-c 与 -r 的区别
  • -c N　= -r N-1:N　——只看第 N 次提交引入的变化
  • -c -N　= 反向应用第 N 次提交（撤销）
  • -r A:B　—— 从 A 到 B 之间的全部变化（多个提交的累积）

所以「撤销单次提交」要用 -c -N，用 -r 容易一下子撤多了。

10冲突：产生、解剖与解决

冲突不是错误，是 SVN 拒绝替你做决定的诚实表现。 它在说：「这两份改动都改到了同一行，我判断不了该留谁，你来定。」

冲突是怎么产生的：三方合并

◈图 10-1　三方合并：SVN 如何判断能否自动合并3-Way Merge
关键洞察：冲突只在双方改到同一区域时才发生。 这就是为什么「频繁 update」能有效降低冲突——把 BASE 不断往前推， 你和同事的改动窗口就越小，重叠概率越低。

亲手制造一次冲突（实测）

要理解冲突，最好的办法是亲手造一个。下面这段操作在两个工作副本之间模拟「你和同事同时改一个文件」。

bash复现冲突的最小步骤
# 准备：两个工作副本，模拟你和同事
svn checkout file:///repo/trunk wc      # 你的
svn checkout file:///repo/trunk wc2     # 同事的

# 同事先改并提交
cd wc2
echo "版本A：来自同事的修改" > README.md
svn commit -m "同事修改 README"            # → r3

# 你在旧版本上改了同一个文件（但还没更新）
cd ../wc
echo "版本B：我本地的修改" > README.md

# 现在 update，冲突就出现了
svn update
# C    README.md
# Merge conflict discovered in file 'README.md'.

--accept 的六个取值

取值含义什么时候用
working 接受当前工作副本里的内容（默认） 最常用。你手工编辑完冲突标记后选它
mine-full 丢弃服务器改动，整个文件用我的 确定自己的版本是对的，同事改的完全不需要
theirs-full 丢弃我的改动，整个文件用服务器的 自己改错了，想完全跟随服务器版本
mine-conflict 只在冲突块用我的，非冲突区保留合并结果 大部分改动挺好，只有冲突那几行以我为准
theirs-conflict 只在冲突块用服务器的 只有冲突那几行以服务器为准，其余保留我的
base 回到原始版本，双方改动全部丢弃 两边都改乱了，想从头再来
批量解决：-R 递归
bash一次解决多个冲突
# 递归解决当前目录下所有冲突
svn resolve --accept working -R .

# 先看看有哪些冲突文件（解决前必做）
svn status | grep '^C'
svn status | findstr "^C"          # Windows

# 批量把冲突都当「用我的」处理（危险，确认清楚再用）
svn resolve --accept mine-full -R .

# 如果搞砸了想重来：先 cleanup 再 update 还会重新产生冲突
svn revert -R .
svn cleanup
svn update
解决冲突时最常见的三个错误
  1. 忘了删掉冲突标记 —— 提交后发现文件里还留着 <<<<<<<，代码直接编译不过。 提交前务必搜索一遍：grep -rn "^<<<<<<<" .
  2. 解决了文件但忘了 svn resolve —— status 永远显示 C，提交会被拒绝： svn: E155015: Aborting commit: 'README.md' remains in conflict
  3. 用 svn resolve 但没实际编辑文件 —— --accept working 只是「声明已解决」，它不会自动帮你删标记。 必须先真的编辑好，再声明。
