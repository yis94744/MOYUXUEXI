4仓库、版本号与工作副本

SVN 有三个概念必须先立住：仓库（存哪）、版本号（怎么标定时间点）、 工作副本（你手里那份）。这三个概念一旦串起来，后面所有命令都只是它们的排列组合。

版本号是全局的——这是 SVN 最独特的设计

在 Git 里，每个提交有自己的哈希，两个文件可能是八竿子打不着的两个哈希。 但在 SVN 里，版本号是一个贯穿整个仓库的递增整数，从 1 开始，每次提交加一。

◈图 4-1　全局版本号：任何一次提交都会推进整个仓库的版本号Revision Model
记住这张图右上角的紫色框——它解释了几乎所有「为什么我的版本号和同事看到的不一样」的疑问。 版本号是仓库级的，不是文件级的。

工作副本的三种状态：理解 status 的前提

工作副本里的每个文件，相对于服务器上的「BASE 版本」，只可能是三种状态之一。 svn status 的字母输出，就是在这三种状态上再细分出来的。

◈图 4-2　文件状态机：从新建到提交的完整流转State Machine
读图技巧：绿色路径是正常业务流程（add → commit → 修改 → commit）； 红色路径是出错路径（手删文件、直接 rm、update 撞车）；紫色是救回路径（revert / resolve）。 第 7 节会给出每个状态码的实测输出。

亲手创建一个仓库

理论说够了，动手。创建仓库的命令是 svnadmin create：

bash创建仓库并观察目录结构
# 建一个仓库目录（服务端动作，和客户端 checkout 无关）
svnadmin create /var/svn/repo

# 看看它生成了什么
ls -la /var/svn/repo
# conf/  db/  format  hooks/  locks/  README.txt

# 关键子目录说明
ls /var/svn/repo/conf          # svnserve.conf  passwd  authz（认证权限配置）
ls /var/svn/repo/hooks         # 9 个 .tmpl 钩子模板，改掉后缀 .tmpl 才会生效
cat /var/svn/repo/format       # 仓库格式版本，1.14 下是 5
实测输出（Windows / SVN 1.14.5）
PowerShell
$ svnadmin create E:\svn-demo\repo
<无输出即成功>

$ Get-ChildItem E:\svn-demo\repo | Select-Object Mode,Name
Mode   Name
----   ----
d----- conf
d----- db
d----- hooks
d----- locks
-ar--- format
-a---- README.txt

$ Get-ChildItem E:\svn-demo\repo\conf | Select Name,Length
Name           Length
----           ------
authz            1112   ← 权限配置文件（整套模板）
hooks-env.tmpl   904   ← 钩子环境变量配置
passwd           317   ← 账号密码文件
svnserve.conf   4456   ← svnserve 服务端主配置

$ cat E:\svn-demo\repo\format
5   ← 仓库格式版本 5（对应 SVN 1.8+ 特性）
别把仓库目录手动改坏

db/ 是版本数据的全部家当。 永远不要直接编辑 db/ 下的文件、不要手动删除 db/revs 里的内容、 不要用普通文件复制工具去「备份」正在使用的仓库（要用 svnadmin hotcopy，见第 21 节）。

5标准目录结构 trunk / branches / tags

SVN 强制不了一个仓库长什么样——你完全可以把所有文件堆在根目录。 但社区有一套沿用二十年的约定，几乎所有团队都这么干，你最好也这么干。

◈图 5-1　标准目录结构与其用途Layout
一句话记忆：trunk 是主干（当前开发线），branches 是岔路（并行开发）， tags 是路标（发布快照）。三者都是普通目录，SVN 不赋予它们任何特殊含义， 特殊含义完全来自团队约定与合并工具。这一点和 Git 的 tag 是「特殊对象」有本质区别。

一次性建好结构

bash建立标准三段式结构
# 注意：-m 是必填的提交日志，即使只是建目录也要写
svn mkdir file:///var/svn/repo/trunk   \
          file:///var/svn/repo/branches \
          file:///var/svn/repo/tags     \
          -m "建立标准目录结构"

# 如果用的是 svn:// 协议，URL 换成对应形式
# svn mkdir svn://192.168.1.10/repo/trunk -m "..."

# 验证一下（不需要检出就能看）
svn list file:///var/svn/repo
# branches/
# tags/
# trunk/
实测输出：一次建三个目录只消耗一个版本号
PowerShell
$ svn mkdir https://.../trunk .../branches .../tags -m "建立标准目录结构"
Committing transaction...
Committed revision 1.   ← 三条路径合并成一次提交，只占一个版本号

$ svn list --verbose file:///C:/Work/svn-demo/repo
      1 kelang              10 08 10:55 ./
      1 kelang              10 08 10:55 branches/
      1 kelang              10 08 10:55 tags/
      1 kelang              10 08 10:55 trunk/
   ↑ 版号   ↑ 提交者        ↑ 时间       ↑ 路径

$ svn list --verbose file:///C:/Work/svn-demo/repo/trunk
      1 kelang              10 08 10:55 ./
   ↑ 空目录只显示一个点（代表目录自身），这是正常的
svn mkdir 有两种用法，别混了
  • svn mkdir URL -m "..." → 直接在服务端建，立刻产生一个新版本号。适合批量初始化。
  • svn mkdir 目录名（本地路径）→ 在本地建目录并标记为待添加，之后还需要 svn commit 才生效。

同理，svn delete / svn copy / svn move 也都支持「URL 形式」和「本地路径形式」两种，行为差异一致。

6第一次完整上手：从零到提交

这一节把「拿到一个仓库地址」到「成功提交第一份代码」的完整链路走一遍， 每一步都配真实输出。照着敲一遍，你就掌握了 SVN 80% 的日常。

◈图 6-1　首次上手六步流程Workflow

步骤 1：checkout 拉取工作副本

bashcheckout 的三种写法
# 写法一：最常用，把 trunk 检出到当前目录下的 wc 文件夹
svn checkout https://svn.example.com/repo/trunk wc

# 写法二：检出到当前目录（省略目标目录名，会直接铺在当前目录）
mkdir myproject && cd myproject
svn checkout https://svn.example.com/repo/trunk .

# 写法三：简写 co（SVN 几乎所有命令都有简写）
svn co https://svn.example.com/repo/trunk wc

# 常用选项
svn checkout --username alice --password 'secret' URL wc   # 指定账号
svn checkout --non-interactive URL wc                     # 不交互，脚本里必备
svn checkout --depth immediates URL wc                    # 稀疏检出，只拉一层（第 22 节）
svn checkout -r 100 URL wc                                # 检出历史版本 r100
实测输出
PowerShell
$ svn checkout file:///C:/Work/svn-demo/repo/trunk wc
A    wc\README.md
A    wc\src
A    wc\src\main.cs
Checked out revision 2.
    ↑ 每个 A 表示这个文件被「添加」到本地工作副本
PowerShell
$ svn info
Path: .
Working Copy Root Path: C:\Work\svn-demo\wc
URL: file:///C:/Work/svn-demo/repo/trunk
Relative URL: ^/trunk              ← 相对仓库根的位置（^ 代表仓库根）
Repository Root: file:///C:/Work/svn-demo/repo
Repository UUID: 021a334f-9907-c84d-81c4-e10db7ecd948
Revision: 1                        ← 整个工作副本的版本
Node Kind: directory
Schedule: normal
Last Changed Author: kelang
Last Changed Rev: 1
Last Changed Date: 2026-10-08 10:55:51 +0800
看懂 svn info 输出里的三个版本号
  • Revision: 1 —— 整个工作副本的基准版本（刚 checkout 时等于检出的版本）
  • Last Changed Rev: 1 —— 当前这个目录/文件最后一次被改动的版本
  • Last Changed Author / Date —— 那次改动是谁、什么时候做的

刚 checkout 完这两个值往往不同，那很正常。Revision 是「你手上这份数据处于哪个时间点」，Last Changed Rev 是「这个路径上次被改是在哪个时间点」。

步骤 2：add 纳入版本控制

新建的文件 SVN 默认完全无视。你必须显式告诉它「这个文件我要管」—— 这就是 svn add。

bashadd 的各种姿势
svn add README.md            # 添加单个文件
svn add src/                 # 递归添加整个目录（含其中所有未忽略的文件）
svn add *.py                 # 通配符（bash 会先展开，Windows 下 SVN 自己展开）
svn add --force .            # 添加当前目录下所有未版本控制的东西

# 只想标记、不实际加入（很少用）
svn add --depth empty src/

# 危险选项：--no-ignore 会把 svn:ignore 忽略的文件也加进来，慎用
svn add --no-ignore .
实测输出：add 前后 status 的变化
PowerShell
# 先创建两个文件和一个目录
$ Set-Content README.md "# 我的项目"; Set-Content src\main.cs "class Main {}"

# add 之前：全是 ? 号
$ svn status
?       README.md
?       src
        ↑ ? = 未版本控制，提交时会被完全忽略

# 执行 add
$ svn add README.md src
A         README.md
A         src
A         src\main.cs
        ↑ A = 已添加到版本控制，但尚未提交到服务器

# add 之后再看 status：? 变成了 A
$ svn status
A       README.md
A       src
A       src\main.cs

# 注意：svn add 目录时会递归列出其中每个文件
# 所以 src 和 src\main.cs 都各占一行
常见误区：svn add 不等于提交

新手最容易犯的错：以为 svn add 之后文件就在服务器上了。 不是的。add 只是在本地登记，必须在同一个工作副本里执行 svn commit 才会真正上传。

判断方法：svn status 看到 A 就是还没提交；提交干净后这一行会消失。

步骤 3-4：status 与 diff 自查

bash提交前的自查清单
# 1. 我到底改了哪些东西？（本地操作，秒出）
svn status

# 2. 排除那些我不关心的（比如编辑器临时文件）
svn status --no-ignore           # 连被忽略的也显示（排查「为什么文件传不上去」时有用）
svn status -q                    # 只显示有改动的，不显示 ? 未跟踪文件
svn status -u                    # 联网对比服务器，显示哪些文件服务器上有更新
svn status -v                    # 显示每个文件的版本号和最后修改者
svn status --depth immediates     # 只看当前层，不递归子目录

# 3. 逐行看我改了什么
svn diff
svn diff README.md               # 只看某个文件
svn diff -r 5:8                  # 比较仓库里 r5 和 r8 的差异
svn diff -r 5:HEAD               # 从 r5 到现在
svn diff --summarize             # 只列出改了哪些文件，不显示内容（大改动时好用）
实测输出：status 与 diff
PowerShell
# 修改 README.md 后
$ svn status
M       README.md
        ↑ M = Modified，与 pristine 副本（最近一次 update 时的快照）不同

$ svn diff
Index: README.md
===================================================================
--- README.md   (revision 2)       ← 左：服务器 BASE 版本
+++ README.md   (working copy)     ← 右：你磁盘上的当前内容
@@ -1 +1,5 @@
 ﻿# 我的项目
+
+## 安装
+
+1. 克隆仓库
   ↑ + 号是新增行；对应地，- 号是删除行，无前缀是上下文

$ svn diff --summarize
M       README.md
        ↑ 只给文件名，不显示逐行内容，适合大改动时快速扫一遍
          注意：--summarize 是 svn diff 的选项，svn status 没有这个选项

步骤 5-6：update 再 commit

bash提交的完整动作
# 第 5 步：先拉取别人的改动
svn update

# 第 6 步：提交
svn commit -m "初始化项目结构与说明文档"

# 只提交指定文件（危险：容易漏掉相关文件，但有场景需要）
svn commit README.md src/main.cs -m "修改文档与主程序"

# 从文件读提交日志（日志很长、或要嵌入特殊字符时用）
svn commit --file commit-msg.txt

# 只提交某个变更列表（第 22 节 changelist）
svn commit --changelist doc-fix -m "文档修正"

# 常用选项
svn commit --depth immediates -m "只提交当前层"
svn commit --username alice --password secret -m "..."
svn commit --non-interactive -m "..."      # 脚本里必备
实测输出：commit 的完整回显
PowerShell
$ svn commit -m "初始化项目结构与说明文档"
Adding         README.md
Adding         src
Adding         src\main.cs
Transmitting file data ..done
Committing transaction...
Committed revision 2.
   ↑ 拿到了新版本号 r2 —— 记下来，这就是你这次提交的「身份证」

# 提交后 status 应该完全干净（无输出）
$ svn status
<空输出 = 工作副本干净>

# 用 svn status -v 确认版本号已经更新
$ svn status -v
                 1        1 kelang       .
                 2        2 kelang       README.md
                 2        2 kelang       src
                 2        2 kelang       src\main.cs
                 ↑ 工作版本  ↑ 最后改动版本  ↑ 作者  ↑ 路径

# 确认工作副本版本已跟上
$ svn update
Updating '.':
At revision 2.
