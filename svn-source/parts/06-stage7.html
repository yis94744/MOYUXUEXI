17服务端部署：方案选型

服务端怎么搭，取决于三件事：要什么协议、要不要精细权限、运维能力如何。 这一节先把三条路线摊开对比，再手把手走一遍最常用的 svnserve 路线。

◈图 17-1　三种部署方案的架构对比Deployment
决策建议：内网小团队、追求省事 → svnserve； 需要加密或对接域账号、公司有安全审计 → Apache； Windows 环境、没人愿意碰配置文件 → VisualSVN Server。 三者可以共存（比如内网用 svnserve，外网出口用 Apache），仓库目录是同一份。

sudo chown -R svn:svn /var/svn

第二步：配置 svnserve.conf

最常见的坑：配置项前面有空格 → 整个仓库无法访问（实测确认）

svnserve.conf 的 ini 格式对前导空格极其敏感。 模板文件里所有配置项都是 # 注释 开头、前面带一个空格。 如果你只删掉 # 却留下了那个空格，配置解析会直接失败。

实测结果比「被忽略」更严重：svnserve 进程能正常启动、端口也处于监听状态， 但客户端一连接就报解析错误，整个仓库彻底无法访问：

实测报错
$ svn list svn://127.0.0.1/repo/trunk
svn: E170013: Unable to connect to a repository at URL 'svn://127.0.0.1/repo/trunk'
svn: E200002: Error while parsing config file: /var/svn/repo/conf/svnserve.conf:
svn: E200002: line 1: Option expected
↑ "Option expected" 就是「这一行不是合法的配置项」
  排查时看到这个错误，第一件事就是检查行首有没有多余空格
✗ 错误：行首有空格
 anon-access = none
 ↑ 前面有一个空格

svn: E200002: line 1: Option expected
→ 整个仓库无法访问
✓ 正确：顶格写
anon-access = none
 ↑ 从第 1 列开始，不留空格

配置生效，服务正常

快速自检命令： grep -n "^[[:space:]]\+[a-z-]\+ *=" conf/svnserve.conf —— 能匹配到任何行，就说明有配置项前面带了空格。

[general]

### 生产环境一律用 none，强制登录

### 已认证用户的权限：read / write

19认证与权限：authz 精细控制

authz 是 SVN 相对 Git 的杀手级优势： 它能精确到「某个目录，某个组，只能读不能写」。这一节把语法和坑一次讲透。

◈图 19-1　authz 权限模型：从路径到权限的映射Authorization
核心心法：authz 是白名单模型——没有明确授权的就是拒绝。 所以第一行永远写 [/] + * =（全部拒绝）， 再逐条放开需要的路径和组。这样最安全，也最容易排查。
iniconf/authz　完整企业级配置示例
#############################################################
# authz —— SVN 权限控制文件
# 格式：[路径] 后面跟 "用户/组 = 权限"
# 路径以 / 开头，相对于仓库根（注意：不是相对于仓库目录）
#############################################################

# ============ 用户组定义 ============
[groups]
admins    = alice, bob          # 管理员：能改标签、能改权限
devs      = alice, bob, carol   # 开发：能读写主干和分支
qa        = dave, erin          # 测试：只读代码，能写测试报告
outsource = frank               # 外包：只能看一个目录

# ============ 仓库根：默认拒绝一切 ============
[/]
* =                        # 所有用户，无权限
@admins = rw               # 管理员全权

# ============ 主干：开发可读写，全员可读 ============
[/trunk]
@devs = rw
@qa   = r
@admins = rw
* = r                      # 其他登录用户只读（比上面 [/] 更具体，覆盖它）

# 主干下的机密子目录：只有 admins 能看
[/trunk/secret]
@admins = rw
* =                        # 其他人依然被 [/] 的 * = 挡住

# 外包只读这一个目录
[/trunk/art/external]
@outsource = r
@devs = rw
* = r

# ============ 分支：开发可读写 ============
[/branches]
@devs = rw
@qa   = r
@admins = rw

# ============ 标签：只读！只有 admins 能打标签 ============
[/tags]
* = r                      # 所有人只读 —— 这就是「标签不可变」的实现
@admins = rw               # 只有管理员能创建/删除标签

# ============ 特殊场景：允许所有人提交日志修正 ============
# （revprop 修改的权限控制，需要配合 pre-revprop-change 钩子）
[revprop]
# 这里不写具体路径规则，revprop 权限在钩子里控制
实测：权限矩阵验证

Committed revision 13.

↑ 这就是「标签只读」的实际效果

Committing transaction...
Committed revision 15.

# ---- bob 访问仓库根：被拒绝（[/] 里 * = 无权限）----
$ svn list --username bob --password bob123 svn://127.0.0.1/repo
svn: E170001: Authorization failed

# ---- 未认证访问：被拒绝（anon-access = none）----
$ svn list --non-interactive svn://127.0.0.1/repo/trunk
svn: E170001: Can't get password
authz 的五个高频坑
  1. 路径写错基准 —— authz 里的路径是相对仓库根的， 写 [/repo/trunk] 是错的，应该是 [/trunk]。
  2. 忘记 authz-db 配置 —— svnserve.conf 里不写 authz-db = authz， 整个权限文件根本不会被读取，所有登录用户都是全权。
  3. 以为没写 = 没权限，但有父级规则兜着 —— [/trunk/secret] 里不写规则，不代表无人可访问； 它会继承 [/] 或 [/trunk] 的规则。要真正锁死必须显式写 * =。
  4. 组名前的 @ 忘了写 —— devs = rw 会被理解为「用户 devs」而不是「组 devs」， 正确写法是 @devs = rw。
  5. 权限改完不生效 —— svnserve 每次请求都会重读 authz，通常立即生效。 如果没生效，检查是不是改错了仓库的 conf 目录（多仓库时容易改串）。
调试权限问题的利器：svnauthz-validate
bash校验 authz 语法
# 检查语法错误（拼错、格式不对会明确报错）
svnauthz-validate /var/svn/repo/conf/authz

# 1.9+ 还能直接查询某个用户对某路径的权限
svnauthz access --username bob --path /tags /var/svn/repo/conf/authz
# 输出：r   （只读）

svnauthz access --username alice --path /tags /var/svn/repo/conf/authz
# 输出：rw  （读写）

svnauthz access --username carol --path /trunk /var/svn/repo/conf/authz
# 输出：（空） = 无权限

改完权限先跑一遍这个，能省掉大量「为什么还是拒绝」的排查时间。

20钩子脚本：让 SVN 按你的规矩办事

钩子（Hook）是服务端在特定操作前后自动执行的脚本。 提交日志格式检查、自动发通知、触发 CI、防止误删——都靠它。 这是把 SVN 从「能用」变成「好用」的关键一步。

◈图 20-1　九个钩子的触发时机Hooks Timeline
钩子部署的关键规则： ① 钩子文件必须放在 {仓库}/hooks/ 目录下； ② 必须去掉 .tmpl 后缀才会生效（pre-commit.tmpl → pre-commit）； ③ Linux 上必须有可执行权限（chmod +x）； ④ Windows 上要写成 .bat / .cmd / .exe。

pre-commit 实战：强制日志规范

需求

团队里总有人写「fix」「update」「111」这种毫无信息量的提交日志， 或者干脆留空。事后查历史时完全看不懂。

目标：强制提交日志至少 10 个字符，并且必须包含关联的任务号。

方案

用 pre-commit 钩子，在提交写入前检查日志： 不符合规则就 exit 1，把错误信息回显给提交者。

关键工具：svnlook log -t TXN 仓库 读取本次提交的日志。

bashhooks/pre-commit　Linux / macOS 版本
#!/bin/sh
#############################################################################
# pre-commit 钩子：强制提交日志规范
#
# 参数：
#   $1 = 仓库路径
#   $2 = 事务名（transaction，本次提交的临时 ID）
#
# 退出码：
#   0 = 允许提交
#   非 0 = 拒绝提交，stderr 的内容会回显给客户端
#############################################################################

REPOS="$1"
TXN="$2"

# ---- 读取本次提交的日志 ----
LOGMSG=$(svnlook log -t "$TXN" "$REPOS")

# ---- 去掉首尾空白字符 ----
TRIMMED=$(echo "$LOGMSG" | sed 's/^[[:space:]]*//;s/[[:space:]]*$//')

# ---- 规则 1：日志不能为空 ----
if [ -z "$TRIMMED" ]; then
  echo "" >&2
  echo "══════════════════════════════════════════════" >&2
  echo " 提交被拒绝：必须填写提交日志" >&2
  echo "══════════════════════════════════════════════" >&2
  echo " 原因：空的提交日志会让历史完全无法追溯。" >&2
  echo " 正确示例：" >&2
  echo "   svn commit -m \"[PROJ-123] 修复登录接口空指针异常\"" >&2
  echo "" >&2
  exit 1
fi

# ---- 规则 2：日志长度至少 10 个字符 ----
LEN=${#TRIMMED}
if [ "$LEN" -lt 10 ]; then
  echo "" >&2
  echo "══════════════════════════════════════════════" >&2
  echo " 提交被拒绝：提交日志太短（当前 $LEN 字符，最少 10 字符）" >&2
  echo "══════════════════════════════════════════════" >&2
  echo " 你的日志：$TRIMMED" >&2
  echo " 请说明「做了什么 + 为什么改」。" >&2
  echo "" >&2
  exit 1
fi

# ---- 规则 3：必须包含任务编号（[PROJ-数字] 格式，可按需调整）----
# 如需强制，取消下面的注释
# if ! echo "$TRIMMED" | grep -qE '\[[A-Z]+-[0-9]+\]'; then
#   echo "" >&2
#   echo "提交被拒绝：日志必须包含任务编号，格式 [PROJ-123]" >&2
#   echo "你的日志：$TRIMMED" >&2
#   exit 1
# fi

# ---- 规则 4：禁止无意义日志（黑名单）----
case "$(echo "$TRIMMED" | tr '[:upper:]' '[:lower:]')" in
  fix|update|commit|test|111|aaa|test1|临时提交|修改|更新)
    echo "" >&2
    echo "提交被拒绝：'$TRIMMED' 是无意义日志，请描述具体改动内容" >&2
    exit 1
    ;;
esac

# ---- 规则 5：检查文件后缀黑名单（防止误传编译产物）----
CHANGED=$(svnlook changed -t "$TXN" "$REPOS")
if echo "$CHANGED" | grep -qE '\.(exe|dll|so|a|class|pyc|o|obj|log|tmp)$'; then
  echo "" >&2
  echo "提交被拒绝：检测到编译产物/临时文件，请勿提交这些内容" >&2
  echo "$(echo "$CHANGED" | grep -E '\.(exe|dll|so|a|class|pyc|o|obj|log|tmp)$')" >&2
  echo "建议：在 svn:ignore 中加入这些模式" >&2
  exit 1
fi

# ---- 规则 6：禁止提交超大文件（比如大于 50MB）----
for f in $(svnlook changed -t "$TXN" "$REPOS" | awk '{print $2}'); do
  SIZE=$(svnlook filesize -t "$TXN" "$REPOS" "$f" 2>/dev/null || echo 0)
  if [ "$SIZE" -gt 52428800 ]; then
    echo "提交被拒绝：文件 $f 大小 $(($SIZE/1024/1024))MB，超过 50MB 限制" >&2
    echo "大文件请使用独立的二进制仓库或制品库" >&2
    exit 1
  fi
done

# ---- 全部通过 ----
exit 0

Windows 上写钩子的三个坑（全部实测踩过）
  1. 必须用 ASCII 无 BOM 编码写文件 —— 如果用 UTF-8 with BOM 保存，CMD 会把 BOM 字节当成命令的一部分， 出现 '∩╗┐@echo' is not recognized as an internal or external command 这种莫名其妙的错误。 用 PowerShell 的话：[System.IO.File]::WriteAllText($path, $content, [System.Text.Encoding]::ASCII)
  2. 批处理里的变量替换语法 —— %LOG:~9% 这种子串语法在普通批处理里可用， 但在 if 块内部会出问题，需要 setlocal enabledelayedexpansion + !LOG:~9!。 更稳妥的写法是避免在 if 块里做字符串操作。
  3. 必须写到 stderr —— echo 消息 1>&2。 如果只写 stdout，有的 SVN 版本不会把内容回显给客户端，提交者只会看到「Commit blocked」而不知道原因。
bathooks/pre-commit.bat　Windows 版本
@echo off
rem =====================================================================
rem pre-commit 钩子（Windows）：强制提交日志规范
rem 参数：%1 = 仓库路径    %2 = 事务名
rem 注意：本文件必须保存为 ASCII 无 BOM 编码！
rem =====================================================================

set REPOS=%1
set TXN=%2
set LOGFILE=%TEMP%\svn_precommit_%RANDOM%.txt

rem ---- 读取本次提交的日志 ----
svnlook log "%REPOS%" -t "%TXN%" > "%LOGFILE%"

rem ---- 读入变量（只取第一行做长度判断）----
set LOG=
for /f "usebackq delims=" %%a in ("%LOGFILE%") do set LOG=%%a

del "%LOGFILE%" >nul 2>&1

rem ---- 规则 1：日志不能为空 ----
if "%LOG%"=="" (
  echo. 1>&2
  echo ============================================== 1>&2
  echo  REJECTED: commit message is required. 1>&2
  echo ============================================== 1>&2
  echo  Example: svn commit -m "[PROJ-123] fix login NPE" 1>&2
  echo. 1>&2
  exit /b 1
)

rem ---- 规则 2：日志至少 10 个字符 ----
rem 通过「取第 10 个字符之后的子串是否为空」来判断长度
set TAIL=%LOG:~9%
if "%TAIL%"=="" (
  echo. 1>&2
  echo ============================================== 1>&2
  echo  REJECTED: log must be at least 10 chars. 1>&2
  echo  Got: [%LOG%] 1>&2
  echo ============================================== 1>&2
  echo  Please describe WHAT you changed and WHY. 1>&2
  echo. 1>&2
  exit /b 1
)

rem ---- 规则 3：禁止无意义日志 ----
echo %LOG% | findstr /i /x "fix update commit test 111 aaa" >nul
if not errorlevel 1 (
  echo REJECTED: '%LOG%' is a meaningless message. 1>&2
  exit /b 1
)

rem ---- 规则 4：拒绝编译产物 ----
svnlook changed "%REPOS%" -t "%TXN%" | findstr /i /r "\.exe$ \.dll$ \.pyc$ \.class$ \.obj$ \.log$ \.tmp$" >nul
if not errorlevel 1 (
  echo. 1>&2
  echo REJECTED: build artifacts / temp files detected. 1>&2
  echo Add them to svn:ignore instead of committing. 1>&2
  exit /b 1
)

rem ---- 全部通过 ----
exit /b 0

其余八个钩子的实用脚本

post-commit　提交后自动通知

最常用的用途：提交后自动发邮件、触发 CI 构建、写审计日志。

bashhooks/post-commit
#!/bin/sh
REPOS="$1"
REV="$2"

# 收集本次提交的信息
AUTHOR=$(svnlook author -r "$REV" "$REPOS")
DATE=$(svnlook date -r "$REV" "$REPOS")
LOG=$(svnlook log -r "$REV" "$REPOS")
CHANGED=$(svnlook changed -r "$REV" "$REPOS")

# ---- 1. 写审计日志 ----
{
  echo "==================================================="
  echo "Revision : $REV"
  echo "Author   : $AUTHOR"
  echo "Date     : $DATE"
  echo "Message  : $LOG"
  echo "Changed  :"
  echo "$CHANGED"
} >> /var/log/svn-commits.log

# ---- 2. 发邮件通知（需装 mailutils）----
{
  echo "提交版本：r$REV"
  echo "提交者：$AUTHOR"
  echo "时间：$DATE"
  echo ""
  echo "日志：$LOG"
  echo ""
  echo "变更文件："
  echo "$CHANGED"
} | mail -s "[SVN] r$REV by $AUTHOR" dev-team@example.com

# ---- 3. 触发 CI 构建（调用 Jenkins/GitLab CI 的 webhook）----
curl -s -X POST "https://jenkins.example.com/job/myproject/build?token=BUILD_TOKEN" >/dev/null 2>&1

# post-commit 的返回值不影响提交（已经提交成功了）
exit 0
pre-revprop-change　防止日志被改

SVN 默认禁止修改版本库属性（包括提交日志），因为该钩子不存在。 想允许修改必须显式创建它并 exit 0；想禁止篡改就 exit 1。

bash方案 A：完全禁止修改（推荐）
#!/bin/sh
# 拒绝一切 revprop 修改，保证历史不可篡改
echo "revision properties are immutable" >&2
exit 1
bash方案 B：只允许管理员改日志，且记录审计
#!/bin/sh
REPOS="$1"; REV="$2"; USER="$3"
PROPNAME="$4"; ACTION="$5"

# 只允许修改 svn:log，不允许改 svn:author / svn:date
if [ "$PROPNAME" != "svn:log" ]; then
  echo "only svn:log can be changed (attempted: $PROPNAME)" >&2
  exit 1
fi

# 只允许 admin 用户
if [ "$USER" != "admin" ]; then
  echo "only 'admin' can modify revision properties" >&2
  exit 1
fi

# 记审计日志
OLD=$(svnlook propget -r "$REV" --revprop svn:log "$REPOS" 2>/dev/null)
echo "[$(date -Iseconds)] $USER modified svn:log of r$REV" >> /var/log/svn-revprop-audit.log
echo "  old: $OLD" >> /var/log/svn-revprop-audit.log

exit 0
钩子触发时机参数典型用途
start-commit 提交开始前（还不知道改了哪些文件） 仓库 用户 拉黑用户、限制提交时段、检查用户是否有提交权限
pre-commit 提交写入前（最后一道关卡） 仓库 事务名 日志规范检查、禁止提交编译产物、大文件拦截、代码风格检查
post-commit 提交成功后 仓库 版本号 邮件通知、触发 CI、写审计日志、更新文档站
pre-lock 加锁前 仓库 路径 用户 [注释] [force] 限制谁可以加锁、禁止抢占他人锁
post-lock 加锁成功后 仓库 用户 (stdin 传路径列表) 通知相关人「某文件已被锁定」
pre-unlock 解锁前 仓库 路径 用户 [token] [break-lock] 禁止强制解除他人锁
post-unlock 解锁成功后 仓库 用户 通知「文件已释放，可以编辑了」
pre-revprop-change 修改版本库属性前 仓库 版本号 用户 属性名 动作 防止日志被篡改；或仅允许管理员修改并审计
post-revprop-change 修改版本库属性后 仓库 版本号 用户 属性名 动作 记录属性修改的审计日志、发通知
实测：revprop 保护的两个方向
PowerShell
# ===== 方向一：钩子返回 1 → 拒绝修改历史日志 =====
$ svn propset --revprop -r 19 svn:log "篡改历史日志"
svn: E165001: Revprop change blocked by pre-revprop-change hook (exit code 1) with output:
[pre-revprop-change] REJECTED: revision properties are immutable.
↑ 历史不可篡改，符合审计要求

# ===== 方向二：钩子返回 0 → 允许修改 =====
# 把钩子内容改成：@echo off / exit /b 0
$ svn propset --revprop -r 19 svn:log "Corrected commit message for r19"
property 'svn:log' set on repository revision 19

# 验证修改生效
$ svn log -r 19
------------------------------------------------------------------------
r19 | kelang | 2026-10-08 11:14:04 | 1 line

Corrected commit message for r19
------------------------------------------------------------------------

# ===== 未创建钩子时（默认状态）=====
$ svn propset --revprop -r 20 svn:log "test"
svn: E165006: Repository has not been enabled to accept revision propchanges;
              ask the administrator to create a pre-revprop-change hook
↑ 这是 SVN 的安全默认值：没有钩子 = 不允许改
钩子调试的三个建议
  1. 钩子里的输出一定要写到 stderr（>&2）。 写到 stdout 的内容在多数情况下不会回显给提交者。
  2. 先在命令行手工测一遍再部署。比如测 pre-commit：
    bash手工测试钩子
    # 先制造一个事务（不提交）
svnmucc -U svn://localhost/repo mkdir /trunk/tmp # 或在客户端执行提交但取消

# 更实用的方式：直接手工调用钩子脚本
/var/svn/repo/hooks/pre-commit /var/svn/repo "1-abc"
echo $?   # 看退出码

# 查看某个事务的信息
svnlook changed -t "1-abc" /var/svn/repo
svnlook log -t "1-abc" /var/svn/repo

# 清理卡住的事务（钩子崩溃可能留下垃圾事务）
svnadmin lstxns /var/svn/repo
svnadmin rmtxns /var/svn/repo "1-abc"
  3. 注意执行环境——钩子运行时的工作目录、PATH、环境变量与你登录时完全不同。 命令一定要写绝对路径（比如 /usr/bin/svnlook 而不是 svnlook）， 否则会出现「我在终端能跑，钩子一跑就失败」。 更稳妥的做法是用 hooks/hooks-env.tmpl 配置环境变量。
