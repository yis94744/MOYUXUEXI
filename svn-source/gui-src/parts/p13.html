13切换分支：在主干和分支间跳

分支建好之后，最自然的疑问是：我本地这份文件夹怎么跑到分支上去？ 答案不是「再检出一次」，而是 Switch（切换）—— 同一份工作副本，手指一拨，就在主干和各个分支之间来回跳。

Switch 到底改了什么？

你的工作副本里，除了那些看得见的文件，还藏着一个 .svn 隐藏目录 （没有它，你的文件夹就只是一堆普通文件，SVN 也不认识它）。

这个目录里记着一件事：「这份工作副本对应的是仓库里的哪条路径」。 平时它指向主干。

Switch 做的事情就一件：把这条记录改成新分支的路径，然后让文件内容追上那条分支的样子。 从这一刻起，你的提交都进新分支，更新也是从新分支拉—— 但在你眼里，还是同一个文件夹、同一个路径，什么都没挪窝。

这就是为什么它比重新检出舒服：不用换目录、不用重配环境、IDE 里打开的项目也还在原地。

面对面看这个对话框

◈Switch 对话框：告诉 SVN 从现在起跟着谁走SWITCH
这个对话框比 Branch/Tag 简单得多，一共就几个元素：

① To URL · 目标地址——你要切到哪条路径去。 这里填的是完整的仓库地址（比如 https://服务器/svn/项目/branches/order-export）， 不是像建分支那样填相对路径。
这一栏是整个对话框的核心，填对了就成功了一大半。

② ... · 浏览按钮——在输入框旁边的这个小按钮，点开就是仓库浏览器。 可以在里面一层层展开目录，直接点选你要切过去的分支，地址会自动填进输入框。
推荐用它，而不是手打地址：手打容易多一个斜杠、少一段路径， 而一旦切到错误的路径，你的下一堆提交可能就提交到不该去的地方了。

③ 输入框右侧的下拉箭头——历史记录。 点开可以看到你以前切换过的路径列表。 如果你经常在固定的两个分支之间来回切，直接从这儿选最快，不用每次去浏览。

④ HEAD revision 选项——决定切过去之后文件内容停在哪个版本。 通常保持默认（对应最新版本）就行，切过去就是分支上最新的样子。
下面如果还有指定版本号的选项，那是给「我要把工作副本停在分支的某个历史版本上」这种特殊情况用的，日常用不到。

⑤ Show log · 查看日志——点开目标路径的提交历史。 它是用来「确认自己要切到哪儿」的： 对着日志看一眼这条分支最近的提交，就知道是不是你要找的那条—— 特别是分支名字起得比较像的时候，这一眼能避免切错。

⑥ 底部 OK / Cancel——确认或放弃。 点 OK 之后会有一个进度过程，SVN 会把工作副本里的文件内容换成目标分支的样子。 分支和主干差异大的时候，这个替换过程会杀掉几百上千个文件，属正常现象。

实际操作步骤

SWITCH把工作副本拨到另一条线上
先处理掉手上的本地改动（最重要的一步） 在工作副本的根文件夹上右键（就是你想整份切过去的那一层）， 先看看有没有红色叹号的文件。
有未提交的改动，先提交；不想要的，先撤销。 理由见下面橙色警告框。
右键打开切换 TortoiseSVN → Switch...
注意是在文件夹上右键，不是在某个文件上——切换的作用范围是整个工作副本。
用「...」浏览并选中目标分支 点输入框旁边的 ... 按钮，在仓库浏览器里展开目录， 点中你要切过去的那条分支，地址会自动填进 To URL。
不确定是不是这条？顺手点一下 Show log，看看它的提交记录对不对得上。
确认地址，点 OK 最后再核对一遍 To URL 里的路径—— 尤其是路径最后一段（分支名）。确认无误后点 OK。
等待完成，注意看进度里的删除与新增 进度对话框里会滚动大量文件名。 「删除」不代表真的删了你的东西，只是把当前分支独有的文件撤走， 再把目标分支独有的文件放进来。别看到一堆删除就慌了。
做完确认「我现在确实在目标分支上」 这一步别省。确认方法见下一小节。
切换完之后，一切照旧——你只是从此在另一条线上干活了。
切换前必须提交或撤销本地改动

这是切换分支最容易踩的坑，而且后果不算小。

问题出在哪：工作副本里那些你改了但还没提交的文件， 在你执行 Switch 的时候不会消失——SVN 会尽量把它们保留在原地， 然后把它们「套到」新分支的对应文件上去。

如果你的改动和新分支上的内容不冲突，表面上好像没事。但只要有一点交集，就会出现两种情况之一：

  • 直接冲突——你现在得先解决冲突才能继续干活， 而这个冲突的起因完全是你自己「没提交就乱切」造成的，纯属自找麻烦。
  • 更糟的：悄悄跟着你跑了——你在主干改了一半的东西，现在是新分支上的未提交改动。 过一会儿你顺手提交，就把主干那边的半成品提进了分支。 这种问题往往过很久才被发现。

正确做法只有两个，没有第三种：

  • 这些改动要留 → 先提交，提交完再切。
  • 这些改动不要了 → 先右键 TortoiseSVN → Revert... 撤销掉，再切。

如果实在拿不准改动要不要留，切换到新分支之前先把文件夹整体复制一份到别处备份，是最省心的办法。

怎么知道「我现在在哪个分支」

切换完成之后，文件夹看起来一模一样，没有任何横幅提醒你在哪条线上。 这是切换功能让人心里没底的地方。有几个办法可以确认：

方法看哪里说明
看文件夹属性 右键 → TortoiseSVN → Properties 属性标签页里会显示这份工作副本关联的 URL， 那里面就写着 /trunk 还是 /branches/xxx。 路径最后一段就是答案。这是最直接的确认方式。
看日志路径 TortoiseSVN → Show log 日志窗口里会标明你正在查看的路径。 如果显示的路径是分支的地址，说明你就在分支上。 同时也能看到这条分支自己的提交记录（不含主干的）。
看提交对话框 右键 → SVN Commit... 提交时提交对话框里也会显示涉及的路径。 提交前顺手瞥一眼，确认提交目标是主干还是分支。
看仓库浏览器 TortoiseSVN → Repo-browser 打开后对比一下本地文件夹结构和仓库里的哪条路径一致。 笨但可靠，适合心里完全没底的时候。
养成一个小习惯：提交前看一眼路径

切换分支最常见的翻车方式是：切完忘了自己在分支上，然后提交了一批本该进主干的改动。 提交对话框弹出时，里面会显示这次提交涉及的路径—— 只要养成「点 OK 之前扫一眼路径」的习惯，这类错误基本可以杜绝。

补救也不是不行：发现提交错地方了，去错误的路径上把那次提交撤销（反向合并），再切回去重新提交。 但远不如一开始就看清省事。

两种干活方式：切换，还是多检出几份？

想同时在主干和分支上工作，有两种办法。它们没有绝对的好坏，看你的工作节奏。

◈ 一份工作副本 + 随时 Switch

优点：磁盘上只有一份文件，省空间； IDE 里只开一个项目，不用切来切去； 编译缓存、环境配置都只有一份，不会出现「两个目录里的依赖版本不一致」这种怪问题。

缺点：同一时刻只能待在一个分支上。 想同时对照主干和分支的代码，就只能来回切； 每次切换都要替换文件内容，分支差异大的时候要等一阵； 切换期间本地编译产物、临时文件容易和另一条线的状态打架。

适合：手上同时只有一个任务，做完一个再切下一个； 磁盘空间紧张（大项目一份工作副本就好几个 G）的场景。

最大的风险：忘切、切错——所以每次动手前确认路径特别重要。

◈ 检出多份工作副本，各管一条线

优点：主干和分支各有一个文件夹，彼此完全独立， 想看哪边就看哪边，不用切换、不用等待； 一边在跑测试、一边在改代码互不干扰； 完全不会「忘记自己在哪条线上」，因为文件夹名字就写着呢。

缺点：占磁盘——两份工作副本就是两份完整的代码； IDE 要开两个项目，编译输出的产物也变成两份； 磁盘上容易出现两个相似的文件夹，时间久了可能搞混， 在一个里改了半天的东西跑到另一个里找。

适合：长期并行维护（比如主干做新功能、同时维护一个已发布版本）； 需要频繁在两条线之间比对代码的场景。

实用建议：把工作副本目录命名成 项目名-trunk、 项目名-hotfix-1.2.1，一眼就能分辨。

怎么选：按「你一天里切几次」来定
  • 一天切一两次（上午收尾主干的事，下午做分支）——用 Switch 就够了，省空间也省事。
  • 一天切十几次（两边都要频繁改、频繁跑）——检出两份更划算，切换等待的时间比磁盘空间贵得多。
  • 两条线都要长期维护（如主干 + 已发布版本）——必须两份， 否则你会天天在等待文件替换和忘记切换之间反复折腾。

两种方式可以混用：长期维护的用两份工作副本，临时试一下的分支用 Switch 切过去看一眼再切回来。

Update 和 Switch 到底差在哪？一个改版本，一个改地址

这两个操作在界面上挨得很近，但管的事完全不同：

操作改变的是什么什么时候用
Update
同一地址，换版本		 版本号：路径不变，还是同一条线 把别人在这条线上提交的新改动拉到本地。 日常最常用，一天要做很多次。更新永远只在当前这条线内部走，不会把你带到别的分支去。
Update to revision...
同一地址，停在旧版本		 版本号，但可以指定一个历史版本 「我想看看这个文件上个月是什么样」。 之后工作副本会停在那个旧版本上，提交前通常要再更新回最新。一般用来看旧代码、定位问题是哪次改动引入的。
Switch...
换地址，跨分支		 URL 指向：工作副本改跟另一条线 从主干切到分支、从一个分支切到另一个分支、功能做完切回主干。 这是本节讲的操作，用得不频繁，但每次都要慎重。

一句好记的话：Update 是「同一条线往前走走」； Update to revision 是「同一条线往回看看」； Switch 是「换一条线走」。

为什么容易搞混：三个操作都会弹出进度框、都会替换本地文件，看起来差不多。 但搞错后果差别很大——Update 用错顶多内容不对，重更一次就好； Switch 用错可能把提交送到错误的线上。

切换之后，别忘了这几件事
  • 先更新一次。切换只是把你的工作副本换成目标分支的大致状态， 切完顺手 SVN Update 一下，确保拿到的是最新内容。
  • 重新编译一次。切换过来的代码可能和之前差别很大， 旧的编译产物是过期的，不重新编译就跑，看到的可能是假象。
  • IDE 可能需要刷新。项目文件都还在老位置，但内容变了； 有些 IDE 需要手动让它重新加载一下才能反映变化。
  • 清理掉未受控的临时文件。那些「不在版本库里、SVN 管不着」的文件（编译输出、日志、临时目录） 不会被切换过程处理，它们还是上一份工作的残留。感觉不对劲时，先清一遍再编译。
