12建分支：开一条独立开发线

分支（branch）说穿了就一句话：把主干复制一份出来，在副本上随便折腾，不影响主干。 折腾成功了就合回去，折腾失败了就把副本一删，主干干干净净。

为什么需要分支：给自己一块可以随便踩的地

没有分支的时候，所有改动都直接落在主干上。主干是大家共用的那条线， 你在上面改一半的东西，别人一更新就全看见了——包括那些还没写完、根本跑不起来的半成品。

分支解决的就是这个问题。典型有三种场景：

  • 做新功能——一个功能可能要写两周。 这两周里主干还会不断有新提交，你不想天天去处理冲突， 也不想把自己写了一半的代码塞给别人。开条分支，安安静静写完再合回去。
  • 修紧急 bug——线上出问题了，必须马上出一个修复版本。 但主干上正在做的新功能还没完成，不能跟着一起发。 这时候从已发布的那个版本拉一条修复分支出来，只改 bug，改完发版。
  • 试不确定的方案——这个思路不一定成，先试试。 在分支上试，成了就合回来，不成就丢掉。主干完全没被污染。

一句话：分支让你在「不动别人」的前提下，想怎么改就怎么改。

好消息：SVN 的分支不是「复制一份文件」

很多人一听「复制一份出来」就担心：仓库是不是要占两份空间？复制是不是要等很久？

都不会。SVN 的分支非常轻量：它本质上是服务器端的一次路径复制—— 服务器把某个目录的内容用链接的方式指向原来那份数据，而不是真的把每个文件再存一遍。

创建分支时发生的事
  • 瞬间完成——不管项目有多大，创建分支都是几秒钟的事，不会再传一遍几百兆的代码。
  • 几乎不占空间——新分支只是多了一行「指向旧数据」的记录。只有你之后在新分支上真正改了文件，那些改动才会额外占用空间。
  • 服务器端操作——整个过程在服务器上完成，你的本地工作副本不会有任何变化。
但有两件事要想清楚
  • 它是一条新路径，意味着以后你要对着这条路径做检出、切换、合并，需要记住自己在哪条线上。
  • 分支不是「保险箱」——开了分支不等于自动安全， 长期不合回主干的分支最后会越来越难合，这一点在后面的合并章节会专门讲。

面对面看这个对话框

创建分支只有一个对话框，但它上面的选项比前面几节的都多，值得逐项认一遍。

◈Branch/Tag 对话框：从源到目标，一步复制BRANCH / TAG
这个窗口从上到下分成四块，认清了就不会填错：

① From WC/URL · 源头——你要从哪儿复制。 这里显示的是你当前右键的那个路径（可以是本地工作副本路径，也可以是仓库地址）。 大多数时候它就是你的主干目录，这一栏一般不用改。
「WC」是 working copy（工作副本）的缩写，意思是「从我本地这份复制」， 这是最常见也最省事的来源。

② To path · 目标路径——新分支叫什么名字、放在哪儿。 注意这里填的是仓库内的相对路径，不是磁盘上的文件夹。 通常写成 /branches/功能名 这种形式。 这是整个对话框里唯一必须你动脑子的地方，下一节表格专门讲怎么填。

③ Destination URL · 目标完整地址——你不用填，它会自己算出来。 系统把你上面写的 To path 拼接到仓库根地址后面， 在这里显示成一个完整的 URL，让你确认一眼「最终会建到哪儿」。
养成习惯：动手点 OK 之前，瞟一眼这一栏，看路径是不是你预期的那条。

④ Log message · 说明区——给这次建分支留一句说明。 别嫌麻烦，这一句会被记进历史里，以后在日志里翻到这一版时， 全靠它告诉别人「这条分支是干嘛用的」。 写法比如 从主干拉出分支，开始做订单导出功能。

⑤ Create copy in the repository from: · 从哪个版本复制——这一组是单选项，决定「复制哪一时刻的内容」：
  • HEAD revision in the repository——用服务器上最新那一版。 最常用，默认就是它，绝大多数情况选这个就够了。
  • Specific revision in the repository——用指定的某一版。 比如「我要从上次发版的那个版本拉一条修复分支」，就在这儿填版本号。 旁边通常有 Show log 之类的入口帮你挑版本，不用自己记编号。
  • Working copy——用你本地工作副本当前的样子。 这个要特别小心：它会把你还没提交的本地改动一起复制进新分支。 好处是「我本地试得差不多了，直接开成分支」，坏处是那段内容在主干历史里找不到对应的版本记录。
拿不准的时候，永远选第一个。

⑥ Create intermediate folders · 自动建中间目录——勾上之后， 如果你写的路径中间有还不存在的目录（比如 branches 这个目录压根还没建过）， SVN 会顺手帮你一层层建好，而不会报错说「路径不存在」。
通常保持勾选，省事。

⑦ Switch working copy to new branch/tag · 建完就切过去——勾上这个， 创建完成后你当前的工作副本会直接转到新分支上，不用再单独执行一次切换。 详细说明见下面蓝色提示框。

⑧ 底部的 OK / Cancel——确认或放弃。 点 OK 只是创建分支，不会修改你的文件，也不会自动提交任何代码改动。

实际操作步骤

BRANCH从右键到分支建好
在一个已受版本控制的文件夹上右键 在你要作为「源头」的那个文件夹上点右键——一般是主干目录。 选错目录会导致分支的内容不对，动手前先在地址栏确认一眼路径。
打开分支菜单 TortoiseSVN → Branch/tag...
菜单名里那个 ... 表示「点了会打开一个对话框」，不是直接执行。
确认来源，填写目标路径 看一眼 From WC/URL 是不是你要的源头； 然后在 To path 里写新分支的路径， 比如 /branches/order-export。
路径写完后看一眼 Destination URL，确认最终地址是对的。
填一句提交说明 在 Log message 里写清这条分支的用途。 例如 从主干创建分支，开始开发订单导出功能，预计两周后合并。
把「大概什么时候合回来」也写上，对以后接手的人非常友好。
选择从哪个版本复制 保持默认的 HEAD revision in the repository 通常就对。 如果是从某个已发布版本拉修复分支，才选 Specific revision 并指定版本号。
慎用 Working copy 那一项，理由前面已经说过。
决定要不要顺手切过去 如果你想「建完立刻就在新分支上干活」， 勾上 Switch working copy to new branch/tag。
如果你的打算是「主干这边继续改，抽空再去检出分支」，就别勾。
点 OK，等待完成提示 服务器端复制非常快，通常一闪而过。 完成后的提示框里会显示这次操作产生的版本号—— 记一下它，以后查这条分支从哪儿来的就靠这个号。
回到文件夹，确认结果 如果你没勾「切换」，那么本地工作副本看起来毫无变化，这是正常的—— 分支建在服务器上。 想看看新分支确实存在，可以右键 → TortoiseSVN → Repo-browser 在仓库浏览器里展开 branches 目录确认。

To path 到底该怎么填

这是唯一容易填错的地方。记住一个原则：分支是仓库里的一条路径，不是磁盘上的文件夹。 大家约定俗成会在仓库根下放三个目录：

目录放什么写路径的例子
trunk 主干：日常开发的那条主线 主干自己不用再建。To path 里通常不会出现它，它只是别人复制时的来源。
branches 分支：临时开发线，用完可以删 /branches/order-export
功能相关的分支都放这儿，一看目录就知道有哪些在并行开发。
tags 标签：留作纪念的快照，比如每个发布版本 /tags/v1.2.0
标签本质上就是分支，操作方式完全一样，区别只在「约定上不许改」。
标签是怎么来的？其实就是分支对话框，换个路径而已

你可能注意到菜单叫 Branch/tag...。这不是偷懒，是事实如此： 在 SVN 里标签和分支是同一个操作——都是「复制一份到新路径」。 唯一的区别是人为约定：

  • 放在 branches/ 下面的，大家默认会继续改它。
  • 放在 tags/ 下面的，大家默认只读不改，当作一个历史快照。

所以要打一个「v1.2.0 发布快照」，操作和建分支一模一样， 只是 To path 写成 /tags/v1.2.0。发版打标签是个好习惯： 以后线上出问题，能立刻定位到「当时发的到底是哪一版代码」。

勾上「Switch working copy to new branch/tag」能省一步

正常情况下，建完分支你的工作副本还停在主干上。 想去新分支干活，还得再单独做一次切换操作。

勾上这个勾选框，SVN 会在创建完成后自动把你当前这份工作副本切到新分支上—— 你的文件夹、文件一个都没动，但从此以后所有提交都落到新分支去了，少点一次右键，少一次选择。

什么时候该勾：

  • 你就是为了做这个新功能才拉的分支，拉完马上就要开工——勾上。
  • 主干那边还有事要收尾，想两边都保留——别勾，或者干脆再检出第二份工作副本。

提醒：切换之后左下角或文件夹属性里显示的路径会变， 这时候你的提交都会进新分支。 如果刚刚切换完就随手提交了一个改动，很容易「以为提交到主干，其实进了分支」—— 养成提交前看一眼当前分支的习惯。

分支路径别乱起名，团队要先统一约定

To path 一旦点下去，这个名字就会长期留在服务器上， 而且以后合并、查日志都靠它。随手起名过几个月自己都认不出来。

  • 别用中文和空格。有些工具和环境对中文路径支持不好， 空格有时也会带来麻烦。用英文小写加连字符最稳，比如 fix-login-timeout。
  • 名字里带上「是干什么的」。 test1、new、temp 这种名字一个月后就是垃圾。写 order-export 这种能看懂的。
  • 修复分支带上版本号。比如 /branches/hotfix-1.2.1， 一眼就知道它是给哪个版本打的补丁。
  • 功能完成、合并回主干后就把分支删掉。 分支列表里堆几十条僵尸分支，谁也说不清哪条还有人用。删分支不影响历史记录，真要找回也很容易。
  • 开工前问一句团队。很多团队会规定「分支必须放在 branches 下、 命名必须是 xxx-yyy 格式」——照着团队的约定来，比自己发明一套强。
建分支这一节的要点回顾
  • 分支 = 服务器端的一次复制，瞬间完成、几乎不占空间，不是真的存两份代码。
  • 操作路径只有一条：右键 → TortoiseSVN → Branch/tag... → 填 To path → 写说明 → OK。
  • 版本来源保持默认，只有拉修复分支才需要指定具体版本。
  • 想建完就在分支上干活，就勾上「切换工作副本」那一项。
  • 命名和存放位置要跟着团队约定走，别自己发明格式。
