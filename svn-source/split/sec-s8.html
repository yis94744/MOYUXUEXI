8日常开发循环与 diff / log 进阶

单人开发、多人协作、紧急修复——所有场景最后都收敛成同一个循环： update → 改 → status → diff → update → commit。 这一节把循环里的 update、log、diff 三个命令挖到底。

◈图 8-1　多人协作的日常循环与冲突预防Daily Loop

update：不只是「拉代码」

bashupdate 的高级用法
svn update                          # 把整个工作副本更新到 HEAD
svn update src/                     # 只更新某个目录
svn update README.md config.json    # 只更新指定文件
svn update -r 100                   # 更新到指定版本 r100（不是最新）
svn update --revision PREV          # 回退到上一个版本（常用！）
svn update --revision BASE          # 回到工作副本的基准版本（丢弃所有更新）

# 冲突处理策略（重要，脚本里必用）
svn update --accept postpone        # 冲突了就放着，产生冲突标记（默认行为）
svn update --accept mine-full       # 冲突时全用我的
svn update --accept theirs-full     # 冲突时全用服务器的
svn update --accept mine-conflict   # 只在本文件的冲突块用我的
svn update --accept theirs-conflict # 只在冲突块用服务器的
svn update --accept base            # 丢弃双方改动，回到原始版本

# 其他常用
svn update --force                  # 强制覆盖，即使有未版本控制的同名文件
svn update --ignore-ancestry        # 忽略祖先关系，直接覆盖（慎用）
svn update --set-depth infinity .   # 把稀疏工作副本变回完整（第 22 节）
svn update --non-interactive        # 脚本必备，遇冲突不卡住等输入
脚本里必须加 --non-interactive 和 --accept

SVN 默认遇到冲突会弹出交互式选择菜单，等待你输入字母。 在 CI / 定时任务 / 批处理脚本里，这会让进程永久挂起。

本教程在实测阶段就踩过这个坑——一个看似简单的 update 命令阻塞了 120 秒后被强制中断。 正确写法：

bashCI 里的安全写法
svn update --non-interactive --accept postpone
svn commit -m "auto build" --non-interactive
实测：update 输出的字母含义
PowerShell
$ svn update
Updating '.':
A    bob-test                        ← 服务器新增的，添加到本地
U    src\main.cs                     ← 文件被更新（Updated）
D    old-file.txt                    ← 服务器删除了，本地也删掉
G    config.json                     ← 自动合并成功（merGed），无冲突！
C    README.md                       ← 冲突（Conflicted），需要人工介入
Updated to revision 12.

# 输出字母速查
A Added     服务器上新增的条目
U Updated   内容是服务器的版本（本地没改过）
D Deleted   服务器上删除了
G merGed    本地和服务器都改了，SVN 自动合并成功
C Conflicted 自动合并失败，产生冲突，必须人工解决
E Existed   已存在（通常是添加时同名文件在）

log：查历史，但有个大坑

实测踩坑：svn log -l 1 显示的不是最新提交！

这是 SVN 新手最困惑的行为之一。svn log 默认从工作副本的 BASE 版本开始往回走， 而不是从服务器的最新版本。如果你很久没 update 过，log 给你看的就是「你本地那个古老时间点」的历史。

实测：这个坑长什么样
PowerShell
# 工作副本停在 r9，但服务器上已经有 r10 了
$ svn log -l 1
------------------------------------------------------------------------
r9 | kelang | 2026-10-08 11:02:52 | 1 line
↑ 显示的是 r9 而不是 r10！
  因为 log 从工作副本 BASE（r9）开始往回数

# 正确写法一：显式指定从 HEAD 开始
$ svn log -r HEAD -l 1
------------------------------------------------------------------------
r10 | kelang | 2026-10-08 11:02:58 | 1 line
↑ 这才是服务器上真正的最后一次提交

# 正确写法二：先 update 再 log
$ svn update; svn log -l 1
Updating '.':
At revision 10.
------------------------------------------------------------------------
r10 | kelang | 2026-10-08 11:02:58 | 1 line

# 正确写法三：用 URL 而不是工作副本路径
$ svn log -l 1 file:///E:/repo/trunk
URL 形式默认从 HEAD 开始，没有这个坑
bashlog 的完整用法
svn log                              # 全部历史（从 BASE 往回），大仓库会刷屏
svn log -l 10                        # 只看最近 10 条
svn log -r HEAD -l 1                 # 看服务器最新那一条（避开 BASE 坑）
svn log -r 5:10                      # 指定区间
svn log -r "{2026-10-01}:{2026-10-08}"  # 按日期区间（1.8+）
svn log -r "{2026-10-01}:HEAD"

# 输出控制
svn log -q                           # 只要版本号/作者/时间，不要日志正文
svn log -v                           # 显示每次提交具体改了哪些路径（重要！）
svn log --xml                        # XML 格式，给脚本解析用
svn log -g                           # 显示合并追踪信息（Merged via: rXX）
svn log --search "修复登录"          # 按关键字搜日志（1.8+）
svn log --diff                       # 直接带上 diff 内容，非常直观

# 看某个文件的完整历史（含重命名追踪）
svn log -v src/main.cs
svn log --stop-on-copy               # 追到创建该分支的那次提交就停（分析分支起点）
实测：svn log -v 显示变更的路径
PowerShell
$ svn log -v -l 1
------------------------------------------------------------------------

Changed paths:
   A /trunk/README.md             ← A=Added U=Updated D=Deleted R=Replaced
   A /trunk/src
   A /trunk/src/main.cs

------------------------------------------------------------------------

# 路径首字母含义（和 status 的字母不同！）
A 新增   M 修改   D 删除
R 替换（删除+新增同名）  C 复制  G 属性改动

# 用 -g 看合并关系，这一步是理解分支的关键
$ svn log -g -l 4

合并 feature-login 分支（冲突已解决）
------------------------------------------------------------------------

Merged via: r8

------------------------------------------------------------------------
-g 是分支调试的杀手锏

svn log -g 会显示 Merged via: rXX 标记， 告诉你「这个分支上的提交是被哪个主干版本合并进去的」。 分支合并出问题时，这条命令能瞬间定位是哪一步合漏了。

diff：三种比较维度

bashdiff 的三种比较对象
# 【维度一】工作副本 vs BASE —— 看我自己改了什么（最常用）
svn diff
# 等价于 svn diff -r BASE，BASE 就是最近一次 update 拿到的那份

# 【维度二】任意两个版本之间 —— 看别人/历史改了什么
svn diff -r 5:8
svn diff -r 5:HEAD
svn diff -c 8                  # 只看 r8 这一次提交引入的改动（= -r 7:8 的简写）
svn diff -r "{2026-10-01}:HEAD"

# 【维度三】URL 之间 —— 比较分支/标签
svn diff file:///repo/trunk file:///repo/branches/feature
svn diff ^/trunk ^/branches/feature        # 用 ^ 简写仓库根（工作副本内可用）

# 输出控制（很实用）
svn diff --summarize           # 只列文件名，不要内容（大改动时先扫一遍）
svn diff --git                  # 1.9+ 支持的 git 风格 diff，方便贴到别处
svn diff --diff-cmd meld        # 调用外部图形化对比工具
svn diff --internal-diff        # 强制用内置引擎（当外部工具配置出错时救急）
svn diff --no-diff-added        # 新增文件不显示全部内容（新增大文件时避免刷屏）

# 保存为补丁文件
svn diff > my.patch
svn diff --file my.patch        # 等价写法，Windows PowerShell 下推荐这个

# 应用补丁
svn patch my.patch
svn patch my.patch --dry-run    # 试运行，不实际改动（先验证再应用）
svn patch --reverse-diff my.patch  # 反向应用（撤销补丁）

# 用第三方 diff 工具（配置在 ~/.subversion/config 的 diff-cmd）
svn diff --diff-cmd diff -x "-u"
Windows PowerShell 下重定向会毁掉补丁文件

实测踩过的坑：在 PowerShell 里执行 svn diff > my.patch， PowerShell 默认用 UTF-16 LE 编码写文件，结果补丁开头多了 FF FE BOM 字节， 用 svn patch 应用时会报 Malformed dumpfile header 之类的解析错误。

解决方案（三选一）：

  • 用内置参数：svn diff --file my.patch（推荐，跨平台一致）
  • 用 cmd 重定向：cmd /c "svn diff > my.patch"
  • 改用 Git Bash / WSL 执行命令
实测：diff 生成补丁并应用
PowerShell
# 1. 产生一个改动
$ Set-Content src\main.cs "class Main { /* patched */ }"

# 2. 生成补丁（用 --file 避开编码坑）
$ svn diff --file E:\my.patch

# 3. 补丁内容
$ Get-Content E:\my.patch
Index: src/main.cs
===================================================================
--- src/main.cs     (revision 17)
+++ src/main.cs     (working copy)
@@ -1 +1 @@
-﻿class Main {}
+class Main { /* patched */ }

# 4. 撤销改动，再从补丁恢复
$ svn revert src\main.cs
Reverted 'src\main.cs'

$ svn patch E:\my.patch
U         src\main.cs
          ↑ U = Updated，补丁成功应用

# 5. 验证内容确实恢复了
$ Get-Content src\main.cs
class Main { /* patched */ }        ← 补丁内容已生效

svn patch 的返回值很直观： U 表示更新成功，A 表示新增了文件，D 表示删除了文件， C 表示补丁上下文对不上、需要人工处理， G 表示自动合并成功。
