1SVN 是什么

SVN（Subversion）是一个集中式版本控制系统。一句话概括它的作用： 把文件的每一次修改都记成一条不可篡改的历史，让多人协作时不互相覆盖、随时能回到过去。

它要解决的核心问题只有三个，但每个都很要命：

① 覆盖问题

两个人同时改同一个文件，后保存的把先保存的整个覆盖掉。SVN 通过「先更新再提交」的机制拦住这种情况。

② 回退问题

改了三天发现方向全错，想退回上周五的状态。没有版本控制就只能靠手抄备份。

③ 追责问题

这行代码是谁写的、为什么这么写、当时跟着什么需求一起改的——svn blame 一行行告诉你。

集中式的本质：一个中央仓库

「集中式」这三个字是整个 SVN 设计的地基，理解了它就理解了 SVN 一半的行为。 它意味着：所有历史只存在一个地方——服务器上的那个仓库（Repository）。 每个开发者的电脑上只有一份「工作副本」（Working Copy），是某次快照的解压结果，不含完整历史。

◈图 1-1　集中式 vs 分布式：历史存在哪里Architecture
看图要点：左边 SVN 的所有箭头都指向同一个中心——没有网络就没有版本历史可言。 右边每个节点自己就是一份完整仓库，节点之间是对等关系。 这张图解释了 SVN 的绝大部分「行为特性」：为什么提交要联网、为什么 .svn 目录不大、为什么分支那么轻量（服务端只记一条路径映射）。
一个必须扭转的直觉

很多人以为 SVN 的分支是「复制一份代码」——恰恰相反。 在 SVN 里创建分支是服务端一瞬间的元数据操作，0 字节数据被复制。 第 11 节会用一张图彻底讲清楚这个「廉价复制」机制，这也是 SVN 分支比 Git 更「轻」的地方。

SVN 与 Git 对照：该选谁

这是绕不开的一问。结论先给：SVN 没有死，它在特定场景下依然是最优解。

对比项SVN（集中式）Git（分布式）
历史存放 只在服务器 每人一份完整副本
提交是否需联网 需要 每次 commit 都走网络 不需要 本地 commit，push 才联网
版本号 全局递增整数（r1, r2, r3…）——好沟通 每对象一个 SHA-1 哈希——精确但难口述
分支成本 服务端几乎零成本；但切换要联网 本地瞬时切换
权限粒度 极细 可精确到目录级读/写 通常只能到仓库级
大文件 / 二进制 友好 支持 svn lock 独占锁 弱，需 LFS 外挂
部分检出 原生支持 --depth 稀疏检出 需 sparse-checkout，较繁琐
学习曲线 平缓 约 15 个命令覆盖 95% 场景 陡峭，需理解暂存区、引用、rebase
目录结构 约定俗成 trunk/branches/tags，靠人遵守 内置分支模型
典型用户 企业内网、游戏美术、嵌入式、
需要精细权限的团队		 开源社区、互联网研发
选 SVN 的场景
  • 项目里大量二进制资源（美术图、模型、音效）——Git 仓库会被撑爆
  • 需要目录级权限隔离，比如外包只能看 /trunk/art
  • 团队成员非技术人员多，需要简单直白的模型
  • 公司内网隔离，不希望完整代码库散落在每台电脑上
  • 需要「版本号」这种人类可读的沟通语言（"你回退到 r1523 试试"）
选 Git 的场景
  • 以文本代码为主，需要高频分支、频繁试验
  • 需要离线开发，或网络不稳定
  • 依赖 PR / Code Review 工作流
  • 参与开源协作，需要 fork + pull request
  • 大量历史清理需求（rebase、squash、Cherry-pick）
现实中两者常共存

很多游戏团队的做法是：美术资源用 SVN，程序代码用 Git，两边通过一个脚本同步。 这不是妥协，而是让每个工具做它最擅长的事。
