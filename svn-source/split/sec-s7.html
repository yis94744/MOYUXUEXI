7status 状态码全解

svn status 是 SVN 里使用频率最高的命令，也是信息密度最高的。 它的输出前七列每列一个字符宽，每列表示一种不同维度的状态。 很多人以为只有两列——这是最常见的误读，会导致完全相反的结论。

先记住这个结论：status 有七列，不是两列

官方文档（svn help status）原文：The first seven columns in the output are each one character wide。 下面这七列各管一件事：内容、属性、工作副本锁、复制历史、切换/外部、仓库锁、树冲突。 用 -u 时还有第 9 列表示服务器是否有更新。

◈图 7-1　status 输出的七列结构解剖（依据 svn help status 实测）Output Anatomy
最容易踩的坑：M 出现在第 1 列还是第 2 列，含义完全不同—— 第 1 列是文件内容变了，第 2 列（前面有个空格）是属性变了。 同理 X 在第 1 列是「externals 创建的外部目录」， 在第 5 列是「externals 定义的版本控制文件」——两者都不是同一个意思。

所有状态码实测

bash构造所有状态码并观察
# 在一个干净的工作副本里依次制造各种状态

# A —— 新增待提交（目录会递归展开成多行）
touch newfile.txt && svn add newfile.txt
mkdir src && echo "code" > src/main.cs && svn add src

# M —— 修改已跟踪文件（第 1 列）
echo "append" >> docs.md

# M —— 修改属性（第 2 列！注意前导空格）
svn propset svn:ignore "*.log" .

# D —— 标记删除
svn delete test-hook.txt

# ? —— 未版本控制
touch untracked.txt

# ! —— 缺失（绕过 svn delete 直接删）
rm src/main.cs

# I —— 被 svn:ignore 忽略（默认不显示）
touch debug.log

# 一次性看全部
svn status
svn status --no-ignore      # 连被忽略的也列出来
实测输出：一次看全各种状态码
PowerShell
$ svn status
 M      .                  ← 第2列 M：当前目录的【属性】被改了（设了 svn:ignore）
M       docs.md            ← 第1列 M：文件【内容】已修改
A       newfile.txt        ← 新增，等待提交
A       src                ← 新增目录
A       src\main.cs        ← 目录里的文件也被递归添加
D       test-hook.txt      ← 已用 svn delete 标记删除
?       untracked.txt      ← 未版本控制，提交时会被忽略

# 注意：debug.log 没有出现在上面 —— 它被 svn:ignore 规则挡住了
# 用 --no-ignore 让被忽略的也现形
$ svn status --no-ignore
I       debug.log          ← I = Ignored，被 svn:ignore 规则匹配

# 再看第2列的 M 具体改了什么属性
$ svn propget svn:ignore .
*.log

这张输出值得多看两眼：第一行  M      . 的 M 出现在第 2 列—— 它表示「当前目录的属性被改了」，而不是「有文件内容被改了」。 如果你误读成第 1 列，就会以为某个文件被修改，从而找错方向。
另外注意 A  src 和 A  src\main.cs 是两行—— 添加目录时 SVN 会把里面的每个条目逐条列出，这是它的默认行为（可以用 -q 精简）。

怎么快速记住列号

不必死记。实战中只需要盯住前两列——它们覆盖了 95% 的日常判断。 第 3~7 列属于「出现时再去查」的类型。把 svn help status 的输出留着， 遇到不认识的字母搜一下就有答案。

! 缺失：最需要立刻处理的异常状态

! 产生的原因只有一个：你绕过了 SVN 直接删文件—— 用 rm / del / 在资源管理器里按 Delete。 SVN 的元数据里还记着这个文件，但磁盘上找不到了。

✗ 错误做法：直接删文件
rm src/old.cpp

$ svn status
!       src/old.cpp
# 状态异常，提交时会报错

$ svn commit -m "删除旧文件"
svn: E200009: Commit failed
'src/old.cpp' is scheduled for addition,
but is missing from the working copy
✓ 正确做法：用 svn delete
svn delete src/old.cpp

$ svn status
D       src/old.cpp
# 状态正常，文件也从磁盘移除了

$ svn commit -m "删除旧文件"
Deleting       src/old.cpp
Committed revision 12.
# 顺利提交，历史里留下了完整记录
实测：! 状态的两种补救方式
PowerShell
# 场景：误删了 src\main.cs
$ Remove-Item src\main.cs -Force
$ svn status
!       src\main.cs

# 补救方式一：我其实不想删 → update 找回来
$ svn update
Updating '.':
Restored 'src\main.cs'          ← 从 pristine / 服务器恢复
At revision 17.

# 补救方式二：确实要删 → 补一个登记动作
$ svn delete --force old-file.txt
D         old-file.txt               ← 即使文件已经不在，也能标记删除

# 补救方式三：批量处理一堆 ! （比如清空了一个目录）
$ svn status | Select-String "^!" | % { svn delete --force $_.ToString().Substring(8).Trim() }
铁律：删除文件永远用 svn delete，不要用 rm

同理，重命名永远用 svn move，不要用 mv / 右键重命名。 原因见第 22 节：svn move 会记录「这是同一次移动」，历史才不会断； 而 mv 在 SVN 看来是「删了一个文件 + 加了一个新文件」，追溯历史时会断掉。
