10冲突：产生、解剖与解决

冲突不是错误，是 SVN 拒绝替你做决定的诚实表现。 它在说：「这两份改动都改到了同一行，我判断不了该留谁，你来定。」

冲突是怎么产生的：三方合并

◈图 10-1　三方合并：SVN 如何判断能否自动合并3-Way Merge
关键洞察：冲突只在双方改到同一区域时才发生。 这就是为什么「频繁 update」能有效降低冲突——把 BASE 不断往前推， 你和同事的改动窗口就越小，重叠概率越低。

亲手制造一次冲突（实测）

要理解冲突，最好的办法是亲手造一个。下面这段操作在两个工作副本之间模拟「你和同事同时改一个文件」。

bash复现冲突的最小步骤
# 准备：两个工作副本，模拟你和同事
svn checkout file:///repo/trunk wc      # 你的
svn checkout file:///repo/trunk wc2     # 同事的

# 同事先改并提交
cd wc2
echo "版本A：来自同事的修改" > README.md
svn commit -m "同事修改 README"            # → r3

# 你在旧版本上改了同一个文件（但还没更新）
cd ../wc
echo "版本B：我本地的修改" > README.md

# 现在 update，冲突就出现了
svn update
# C    README.md
# Merge conflict discovered in file 'README.md'.
实测输出：冲突爆发的那一刻
PowerShell
$ svn update
Updating '.':
C    README.md
Updated to revision 3.

svn: Merge conflict discovered in file 'README.md'.
↑ 注意：update 的退出码是 0，但确实产生了冲突
  在交互式终端下，这里会弹出菜单让你选 postpon/mine/theirs 等

$ svn status
C       README.md                 ← C = Conflicted
?       README.md.mine            ← 冲突辅助文件开始出现
?       README.md.r2
?       README.md.r3
Summary of conflicts:
  Text conflicts: 1
  ↑ 冲突汇总，一眼知道有几个文件要处理

实测：手工解决冲突的完整流程
PowerShell
# 第 1 步：看清冲突长什么样
$ Get-Content README.md
<<<<<<< .mine
﻿版本B：我本地的修改
||||||| .r2
﻿# 我的项目
=======
﻿版本A：来自同事的修改
>>>>>>> .r3

# 第 2 步：编辑文件，删掉所有标记，留下最终内容
$ Set-Content README.md "版本B+C：合并后的最终内容"

# 第 3 步：告诉 SVN「我解决了」
$ svn resolve --accept working README.md
Merge conflicts in 'README.md' marked as resolved.

# 第 4 步：验证状态从 C 变成了 M
$ svn status
M       README.md
        ↑ 冲突标记消失，现在它是普通修改了

# 第 5 步：提交
$ svn commit -m "解决 README 冲突并合并双方修改"
Sending        README.md
Transmitting file data .done
Committing transaction...
Committed revision 4.

# 第 6 步：确认辅助文件也被清理了
$ Get-ChildItem README.md*
README.md                        ← .mine / .r2 / .r3 已自动删除

--accept 的六个取值

取值含义什么时候用
working 接受当前工作副本里的内容（默认） 最常用。你手工编辑完冲突标记后选它
mine-full 丢弃服务器改动，整个文件用我的 确定自己的版本是对的，同事改的完全不需要
theirs-full 丢弃我的改动，整个文件用服务器的 自己改错了，想完全跟随服务器版本
mine-conflict 只在冲突块用我的，非冲突区保留合并结果 大部分改动挺好，只有冲突那几行以我为准
theirs-conflict 只在冲突块用服务器的 只有冲突那几行以服务器为准，其余保留我的
base 回到原始版本，双方改动全部丢弃 两边都改乱了，想从头再来
批量解决：-R 递归
bash一次解决多个冲突
# 递归解决当前目录下所有冲突
svn resolve --accept working -R .

# 先看看有哪些冲突文件（解决前必做）
svn status | grep '^C'
svn status | findstr "^C"          # Windows

# 批量把冲突都当「用我的」处理（危险，确认清楚再用）
svn resolve --accept mine-full -R .

# 如果搞砸了想重来：先 cleanup 再 update 还会重新产生冲突
svn revert -R .
svn cleanup
svn update
解决冲突时最常见的三个错误
  1. 忘了删掉冲突标记 —— 提交后发现文件里还留着 <<<<<<<，代码直接编译不过。 提交前务必搜索一遍：grep -rn "^<<<<<<<" .
  2. 解决了文件但忘了 svn resolve —— status 永远显示 C，提交会被拒绝： svn: E155015: Aborting commit: 'README.md' remains in conflict
  3. 用 svn resolve 但没实际编辑文件 —— --accept working 只是「声明已解决」，它不会自动帮你删标记。 必须先真的编辑好，再声明。
冲突处理的黄金流程（背下来）
CONFLICT五步走
看清分歧svn status 找出所有 C 文件；svn diff 看冲突块内容
逐个编辑打开文件，删掉 <<<<<<< / ||||||| / ======= / >>>>>>> 全部标记，留下正确内容
声明解决svn resolve --accept working 文件名（或 -R . 批量）
复查一遍svn status 应该只剩 M；再 grep -rn "^<<<<<<<" . 确认没漏标记
提交svn commit -m "解决 XXX 冲突（与 某人 的改动合并）" —— 日志里写清跟谁冲突、怎么解决的
