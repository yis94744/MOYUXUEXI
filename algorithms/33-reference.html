    三个最容易"想当然"的选择 ① "找最短路径就用 Dijkstra"
    如果图是无权的，BFS 更快也更简单。
    如果是"已知目标"，A* 比 Dijkstra 快得多。
    Dijkstra 只在"需要到所有点的距离"时才合适。

    ② "排序就用快排"
    · 需要稳定 → 归并
    · 只要前 K 个 → 堆
    · 只要第 K 个 → 快速选择
    · 小数组 → 插入排序

    ③ "碰撞检测就两两比较"
    单位超过 100 个就必须用空间划分。
    而且要注意格子大小的陷阱（页 12）。

    脏标记频繁重算视场景21
    三个"可能反而更慢"的模式 本站在实测中发现的三个反例：

    ① 对象池——实测 0.93x（更慢）
    小对象的分配成本很低，而池的管理有开销。
    真正的收益是减少 GC 导致的帧抖动——微基准测不出来。

    ② 三角函数查表——实测 0.89x（更慢）
    现代 CPU 的 sin 是一条指令。
    查表的收益在没有硬件浮点的老设备上才明显。

    ③ Lua 里缓存全局函数——实测 1.00x（无收益）
    Lua 5.4 用数组存全局变量，访问本身就是 O(1)。
    这和 LuaJIT 时代、以及很多博客的说法相反。

    结论：这三个反例都指向同一条原则——先测量，再优化。

    四、快速判断清单

    遇到性能问题，按这个顺序问 ① 这个操作多少时间执行一次？
    · 每帧 → 必须优化
    · 每秒 / 每次操作 → 要小心
    · 加载时一次 → 基本不用管

    ② 数据规模多大？
    · < 100 → 任何算法都够快
    · 100~1000 → 注意 O(n²)
    · > 1000 → 必须用合适的结构

    ③ 有没有"隐藏的循环"？
    · table.remove(t, 1) → O(n)
    · 循环内字符串拼接 → O(n²)
    · 循环内 Find/GetComponent → O(n) 或更慢

    ④ 有没有跨语言调用？
    · 循环里调 C# API → 重点优化对象

    ⑤ 测量过了吗？
    · 没测量就先测量
    四个"别急着优化"的信号 ① 数据量很小——100 个元素，O(n²) 也只要几微秒
    ② 只执行一次——加载、初始化阶段的代码
    ③ 不是瓶颈——Profiler 显示它只占 1%
    ④ 优化会降低可读性——除非收益很大，否则不值得

    判断标准：如果能明确说出"优化后省了多少"，就做；说不出来，就先别做。
