    一、三种序列化格式的取舍

    格式体积速度可读性适用
    JSON大慢好配置文件、存档（简单场景）
    二进制小快差存档、网络
    Lua 表中中好Lua 项目专用
    存档的第一原则：向后兼容 ★★★ 场景：v1.0 的玩家存档，在 v1.1 里要怎么读？

    错误做法：
    -- v1.1 直接读 v1.0 的存档
    local level = data.newField -- 老存档里没有这个字段
    -- level 是 nil -> 崩溃

    正确做法：
    ① 存档带版本号：{ version = 2, ... }
    ② 读取时迁移：
    if data.version == 1 then
      data.newField = DEFAULT_VALUE
      data.version = 2
    end
    ③ 所有字段都要有默认值：data.newField or DEFAULT

    必须遵守的规则：
    · 永远不要删除字段——只标记废弃
    · 永远不要改变字段类型（number 不能变成 string）
    · 每次改存档结构都要写迁移逻辑
    · 测试老存档能否在新版本读取

    上线后才发现"老玩家存档读不了"，是最严重的事故之一。

    二、存档系统的五个安全措施 ★★★

    措施一：原子写入（防止存档损坏） 问题：写入过程中崩溃/断电 → 存档文件被写坏一半。

    解决：先写临时文件，成功后再替换。
    写 save.tmp
    校验 save.tmp 可读
    删除 save.dat
    重命名 save.tmp → save.dat

    关键点：文件系统层面保证"要么是完整的旧数据，要么是完整的新数据"。
    这和页 17 的热更原子切换是同一个思路。
    措施二：备份（防止数据丢失） 问题：存档写坏了，玩家数据全丢。

    解决：保留上一份存档。
    · save.dat——当前存档
    · save.bak——上一份存档
    · 写入前：把 save.dat 复制成 save.bak
    · 读取失败时：尝试从 save.bak 恢复

    进一步：服务器备份（重要数据上传服务器）。
    这是防"玩家换设备"和"本地数据丢失"的唯一手段。
    措施三：校验（发现损坏） 做法：存档里存一个校验值（CRC / MD5 / 简单哈希）。
    读取时重新计算，不一致就说明损坏了。

    校验值放哪：
    · 存档文件末尾（读完后校验）
    · 单独一个 .checksum 文件

    作用：
    · 发现"文件被截断"
    · 发现"部分字节被改"
    · 但不能发现"有意的完整篡改"（那需要加密签名）
    措施四：加密（防篡改）与措施五：压缩 加密：
    · 防止玩家直接修改存档文件作弊
    · 但客户端加密总是能被破解（见页 21）
    · 关键数据应该在服务器
    · 加密的实际价值：提高修改门槛

    压缩：
    · 存档大时用（比如 > 100KB）
    · 常用算法：LZ4（快）、zlib（压缩率高）
    · 注意：压缩后仍然要校验（压缩本身不保证数据正确）

    顺序：序列化 → 压缩 → 加密 → 写入
    读取：读取 → 解密 → 解压 → 反序列化
