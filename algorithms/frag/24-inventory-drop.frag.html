24 · 背包、掉落与权重随机

这一页讲两个每个游戏都有的系统：背包和掉落。它们看起来简单，但有几个容易写错的地方——尤其是权重随机。

这一页在路线中的位置 上一页（23）讲"效果怎么作用"。这一页讲"东西怎么产出、怎么存放"——背包与掉落。
关键衔接：背包的"遍历中删除"陷阱连回页 04 的队列问题；权重随机的前缀和 + 二分复用页 14 的二分查找。
下一页（25）定时器。掉落、刷新、活动开启都靠它驱动。
验证方式：权重的概率分布可以跑 10 万次统计验证；可复现随机可以用同种子对照。

一、背包的三种实现

实现结构适用
数组（格子）固定格子数，每格放一个道具大多数游戏
哈希（无限）itemId → 数量材料类游戏
混合装备用格子，材料用哈希最优
背包最常见的两个 bug ① 道具数量为 0 但格子还在
删除道具时只把数量减到 0，没清空格子。
后果：格子显示为"空的"，但仍然占用位置——玩家看到背包满了但看不到东西。
解决：数量归零时立即清空格子（设为 nil）。

② 遍历背包时删除道具
for i = 1, #bag do
  if bag[i].count == 0 then table.remove(bag, i) end
end
删除元素后，后面的元素前移，但 i 继续递增——会跳过元素。
解决：倒序遍历，或先收集再统一删除。

这两个 bug 我在 C# 站和 页 04 都提过——它们是"遍历中修改集合"这个通病的具体表现。

二、权重随机：三种实现的实测 ★★★

错误做法：随机数除以总权重 看起来对的写法：
local total = 0
for _, item in ipairs(drops) do total = total + item.weight end
local r = math.random() * total
for _, item in ipairs(drops) do
  r = r - item.weight
  if r <= 0 then return item end
end
这个写法是对的——但每次掉落都要遍历计算总权重。

真正的错误做法：
if math.random() < 0.1 then -- 10% 概率
-- 但"10%"是按什么算的？
如果所有道具的概率加起来不等于 1，就会出现"永远掉不出某道具"或"某道具概率被悄悄放大"。
正确思路：权重是相对值，不是绝对概率。
权重 10 / 100 / 200 → 实际概率 = 10/310、100/310、200/310。
总权重会变（比如某个道具不可掉落时），概率自动重分配。
优化：前缀和 + 二分查找 问题：上面的写法每次掉落都是 O(n)——遍历计算总权重。
如果每次击杀要掉落 5 次，1000 个怪就是 5000 次 O(n) 遍历。

优化做法：
① 预计算前缀和：cum[1]=10, cum[2]=110, cum[3]=310
② 随机 r = math.random(1, total)
③ 二分查找 r 落在哪个区间
复杂度从 O(n) 降到 O(log n)

更好的做法：如果权重不变，前缀和算一次就好。
每次掉落只需 O(log n) 的二分。

适用场景：掉落表很大（几百项）且频繁调用时。
小掉落表（十几项）直接用遍历就够——不要过度优化。
随机的可复现性问题 问题：如果需要"同样的种子产生同样的掉落"（录像回放、战斗重算、帧同步）——
math.random 是全局状态，无法保证复现。

解决：用独立的随机数生成器：
local rng = { seed = 12345 }
function rng:next()
  self.seed = (self.seed * 1103515245 + 12345) % 2147483648
  return self.seed
end
每个系统用自己的 rng 实例，互不干扰。

帧同步游戏必须这样做——否则不同客户端的随机结果不一致，直接导致战斗结果分歧。
详见 Lua 站页 12（帧同步的确定性）。
