一、哈希的核心与冲突解决

哈希的理想是一次计算定位数据。现实中不同的 key 会算出同一个下标，这叫哈希冲突。

--    · 需要控制内存布局（连续数组 vs 哈希）

print("=== 2. 链地址法实现 ===")

local HashTable = {}
HashTable.__index = HashTable

function HashTable.new(capacity)
  capacity = capacity or 16
  return setmetatable({
    slots = {},          -- 每个槽是一个链表（这里用表模拟）
    capacity = capacity,
    count = 0,
    collisions = 0,      -- 统计冲突次数
  }, HashTable)
end

-- 哈希函数：把字符串映射成数字
-- 【关键】好的哈希函数要让 key 均匀分布
function HashTable:hash(key)
  local h = 0
  local s = tostring(key)

  -- 经典的 DJB2 算法
  for i = 1, #s do
    h = h * 33 + s:byte(i)
    h = h % 2147483647          -- 防止溢出（Lua 整数是 64 位，但保持一致性）
  end

  return (h % self.capacity) + 1  -- Lua 索引从 1 开始
end

function HashTable:set(key, value)
  local idx = self:hash(key)

  if not self.slots[idx] then
    self.slots[idx] = {}
  end

  local bucket = self.slots[idx]

  -- 查找是否已存在
  for i = 1, #bucket do
    if bucket[i].key == key then
      bucket[i].value = value     -- 更新
      return
    end
  end

  -- 不存在则添加
  if #bucket > 0 then
    self.collisions = self.collisions + 1
  end

  bucket[#bucket + 1] = { key = key, value = value }
  self.count = self.count + 1
end

function HashTable:get(key)
  local idx = self:hash(key)
  local bucket = self.slots[idx]
  if not bucket then return nil end

  for i = 1, #bucket do
    if bucket[i].key == key then
      return bucket[i].value
    end
  end
  return nil
end

function HashTable:remove(key)
  local idx = self:hash(key)
  local bucket = self.slots[idx]
  if not bucket then return false end

  for i = 1, #bucket do
    if bucket[i].key == key then
      table.remove(bucket, i)
      self.count = self.count - 1
      return true
    end
  end
  return false
end

-- 演示：不扩容 vs 扩容的性能差异
local function testWithCapacity(cap, n)
  local t = HashTable.new(cap)
  for i = 1, n do
    t:set("key" .. i, i)
  end
  return t.collisions, t.capacity
end

print(string.format("  %-12s %-14s %s", "容量", "冲突次数", "负载因子"))
print("  " .. string.rep("-", 44))

for _, cap in ipairs({ 8, 64, 256, 1024, 4096 }) do
  local col, c = testWithCapacity(cap, 1000)
  print(string.format("  %-12d %-14d %.2f", cap, col, 1000 / cap))
end

local function posKey(x, y)
  -- 【错误做法】用浮点数直接拼字符串
  -- 0.1 + 0.2 = 0.30000000000000004 != 0.3
  -- 会导致「明明在同一个位置却查不到」

  -- 【正确做法】量化成整数
  local SCALE = 100          -- 精度：0.01
  return math.floor(x * SCALE) * 100000 + math.floor(y * SCALE)
end

-- 演示：预分配的效果
local function bench(fn, times)
  local t = os.clock()
  for i = 1, times do fn() end
  return os.clock() - t
end

local N = 100000

-- 不预分配
local t1 = bench(function()
  local t = {}
  for i = 1, N do t[i] = i end
end, 3)

-- 预分配（先用整数填满，触发扩容，再清空）
local t2 = bench(function()
  local t = {}
  for i = 1, N do t[i] = false end   -- 先填满，触发一次性扩容
  for i = 1, N do t[i] = nil end     -- 清空
  for i = 1, N do t[i] = i end       -- 真正填充
end, 3)

print(string.format("    不预分配: %.4f 秒", t1))
print(string.format("    预分配:   %.4f 秒", t2))
print("    【实测结论】预分配反而更慢（因为多做了一轮填充和清空）")
print()
print("    原因：Lua 的 table 扩容是【摊销 O(1)】——")
print("          每次扩容容量翻倍，总的复制成本是 O(n)，摊到每次插入就是 O(1)。")
print("          而「先填满再清空」多做了 n 次赋值和 n 次 nil 写入。")
print()
print("    这和 C++ vector 的 reserve 完全不同：")
print("      C++ vector.reserve(n) 会一次性分配，避免中间所有扩容")
print("      Lua table 没有 reserve API，所谓的「预分配技巧」反而增加开销")
print()
print("    【实战结论】不要用「先填满再清空」这种技巧。")
print("                如果真的在意，用 table.new(n)（LuaJIT 扩展）或直接接受摊销成本。")
方法原理优缺点
链地址法每个槽挂一个链表实现简单，删除方便；但链表有指针开销
开放寻址法冲突了就找下一个空位缓存友好；但删除麻烦（要标记墓碑）
再哈希法冲突时换一个哈希函数实现复杂，少用

二、负载因子：哈希表的生死线 ★★

负载因子超标 = 哈希表退化成链表 本页实测了"容量 vs 1000 个元素的冲突次数"：
容量冲突次数负载因子后果
8992125.00退化成链表
6493715.62严重退化
2567853.91较慢
10246300.98正常
40961080.24很快（浪费内存）
结论：容量太小会让冲突爆炸，查找从 O(1) 退化成 O(n)。
经验值：容量约为元素数量的 1.3~2 倍。
标准实现会在负载因子超过 0.75 时自动扩容。

三、游戏里的三个真实应用

应用一：用坐标做 key 的浮点陷阱 这是游戏开发中最经典的坑。

实测输出：
0.1 + 0.2 = 0.30000000000000004
0.3 = 0.29999999999999999
0.1 + 0.2 == 0.3 → false

后果：如果你用 "x,y" 拼字符串做 key，明明在同一个位置却查不到。
这类 bug 极难复现——因为取决于浮点运算的具体顺序。

正确做法：量化成整数
local SCALE = 100
return math.floor(x * SCALE) * 100000 + math.floor(y * SCALE)
实测验证：量化后 posKey(0.3, 0) 与 posKey(0.1+0.2, 0) 相等。
应用二：ID → 数据的索引 场景：你有 10000 个道具配置，经常需要"按名字查 ID"。
做法：加载配置时额外构建一个反向索引表。
nameIndex[config.name] = config.id

这是"用内存换时间"的典型案例（见页 26 性能模式库）。
收益：从"遍历查找 O(n)"变成"哈希查找 O(1)"。
应用三：状态机的事件映射 不用哈希表：一堆 if-else 判断"当前状态 + 事件"的组合。
用哈希表：transitions["walking:attack"] = "attacking"

好处：
· 新增状态转换只需加一行配置，不用改逻辑
· 可以序列化成 JSON，让策划配置

这是数据驱动设计的典型应用（对比算法站页 16 状态机）。

四、Lua table 的四个性能要点

要点说明
数字 key 最快数组部分用整数索引，是纯数组访问
字符串 key 有 intern 优化短字符串会被内部化，哈希是 O(1)
避免稀疏数组t[1] 和 t[1000000] 之间的空洞会占内存
扩容是摊销 O(1)每次翻倍，总复制成本 O(n)，摊到每次就是 O(1)
反例：Lua 里的"预分配技巧"反而更慢 常见说法：「先用整数填满 table 触发扩容，清空后再用，能避免中间扩容」。
实测结果：不预分配 0.0070 秒，预分配 0.0110 秒——预分配慢了 57%。

为什么：
· Lua 的扩容是摊销 O(1)，总成本已经很低
· 而"先填满再清空"多做了 n 次赋值 + n 次 nil 写入

这和 C++ 完全不同：
· C++ vector.reserve(n) 一次性分配，避免中间所有扩容——确实有效
· Lua table 没有 reserve API，所谓的"技巧"只是绕路

结论：不要用这种技巧。LuaJIT 用户可以用 table.new(n)，标准 Lua 直接接受摊销成本。
