一、寻路算法的演进

从 BFS 到 A* 到 JPS，每一步优化的本质都是"减少盲目搜索"。

缺少代码样本11/pathfinding
算法核心思想扩展节点适用
BFS按层扩展最多无权图
Dijkstra按累计代价扩展多有权图，要算到所有点
A*按 f = g + h 扩展少已知目标的寻路（主流）
JPS跳过直线上的点最少均匀代价网格
流场从目标反向计算方向一次计算大量单位去同一目标

二、启发函数：A* 的灵魂 ★★★

实测数据：启发函数让扩展节点减少 82% 本页在同一张地图上测试了四种启发函数：
启发函数扩展节点数路径代价说明
h = 018430.0退化成 Dijkstra
曼哈顿距离7330.0准确（4 方向）
欧几里得距离14830.0偏小（低估）
欧几里得 x23230.0偏大，本例仍最优
结论：准确的启发函数把扩展节点从 184 降到 73——减少 60%。 而 h=0 就是"完全盲目"的 Dijkstra，慢得多。 但要小心：上表中"偏大的启发"依然得到最优解，这是地图特殊导致的巧合——不是保证。

三、启发函数的正确性规则 ★★★

什么情况下 A* 会找到非最优解 规则：h 必须【不高估】真实剩余代价（称为"可采纳性"）。
h 的情况结果
h = 0退化成 Dijkstra，保证最优但慢
h <= 真实代价保证最优，越快越好
h == 真实代价几乎只扩展一条路径（最快）
h > 真实代价可能非最优（但更快）
各启发函数的正确性（4 方向网格）： · 曼哈顿距离：可采纳（在只能上下左右走时，它就是真实距离） · 欧几里得距离：可采纳（直线距离永远 <= 实际走的距离） · 对角线距离（octile）：可采纳（8 方向移动的最优启发） 但要注意：如果地图有"传送门"或"快速通道"，直线距离可能【高估】真实代价，就会失去最优性。

四、A* 的工程要点

要点一：必须设最大搜索上限 实测中 100x60 的地图返回了"无路径"——因为障碍率 25% 时起点与终点可能被完全阻断。 问题：A* 在"无路径"时要遍历整个可达区域才能确定。 · 20x12 地图：只扩展 104 个节点 · 100x60 地图：可能要扩展 6000 个节点 解决办法：设最大扩展节点数上限，超过就返回失败。 这比任何算法优化都有效——它保证了最坏情况的耗时。 实战做法： · 设一个预算（比如 2000 个节点） · 超预算就返回"找不到路径"或走直线 · 用分帧计算把这个预算摊到多帧（见页 26）
要点二：重复入堆 vs 更新堆内元素 问题：发现更优路径时，需要更新堆中已有节点的 f 值。 但标准堆不支持"更新任意元素"（你不知道它在数组的哪个位置）。 两种解决方案： ① 允许重复入堆（本页的做法） · 同一个节点可能入堆多次 · 取出时检查"是否已处理"，已处理就跳过 · 简单，但堆会变大 ② 索引堆（Indexed Heap） · 维护"节点 → 堆内位置"的映射 · 支持 O(log n) 更新 · 实现复杂，但堆更小 实战建议：用方案 ①，除非节点数极大（>10 万）。
要点三：斜向移动要检查"穿墙角" 问题：允许斜走时，如果两个相邻的直角位置都是障碍，斜着穿过去会穿过墙角。 本页代码的处理： if map[current.y][nx] == 1 or map[ny][current.x] == 1 then blocked = true end 但还有另一种策略：允许穿墙角（某些游戏故意这样设计，让移动更流畅）。 这是一个"设计决策"而不是"技术问题"——要和策划确认。

五、什么时候该换方案

场景推荐方案理由
单个角色寻路A* + 堆通用，实现简单
大量单位去同目标流场寻路一次计算，共享使用
大量单位去不同目标A* + 路径缓存缓存重复请求
超大地图分层寻路先粗后细
均匀代价网格JPS减少 90% 扩展
动态障碍多流场 / 局部避障全场重算代价高
流场寻路：RTS 的标配 场景：RTS 游戏，200 个单位要去同一个目标点。 用 A* 的问题：每个单位跑一次 = 200 次寻路 = 卡死。 流场的做法： ① 从目标点反向 BFS，计算每个格子到目标的距离 ② 每个格子记录"朝哪个方向走能更快到达" ③ 所有单位只需查自己格子的方向——O(1) 收益：CPU 开销降低上百倍。 本页代码实现了完整的流场并做了可视化（用箭头显示流向）——这是理解流场最直观的方式。
