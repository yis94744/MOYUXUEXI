23 · Buff 与技能系统

Buff 和技能是战斗系统的核心。它们的难点不在算法，而在架构设计——怎么让策划配置几百个技能而不写代码。

这一页在路线中的位置 上一页（22）是任务进度的追踪。这一页是战斗数值的追踪——Buff 的叠加、优先级、到期，比任务复杂得多。
关键衔接：Buff 到期用堆（07）管理，与定时器（25）是同一套机制；原子效果拆分则与技能配置的数据驱动直接相关。
下一页（24）背包与掉落。数值系统的另一半：产出。
验证方式：本页的四种叠加规则都能用最小用例验证——尤其是"控制类必须设上限"这一条。

一、技能系统的数据驱动设计 ★★★

反例：每个技能写一段代码 错误做法：
function castFireball(caster, target)
  -- 火球逻辑
end
function castHeal(caster, target)
  -- 治疗逻辑
end
… 200 个技能 = 200 个函数

问题：
· 策划改数值要找程序
· 加新技能要写代码 + 发版
· 相似的技能重复实现
· 无法热更配置

正确做法：把技能拆成原子效果的组合。
{ id = 1001, name = "火球",
  effects = {
    { type = "damage", element = "fire", ratio = 1.5 },
    { type = "buff", buffId = 2001, chance = 0.3 },
  }}

策划只需要"组合效果"，不需要写代码。

二、原子效果的六种类型

类型作用参数
damage造成伤害数值、元素、是否暴击
heal治疗数值、是否过量
buff添加 BuffbuffId、层数、概率
dispel驱散驱散类型、数量
summon召唤单位 ID、数量、位置
move位移距离、方向、是否穿墙
为什么原子效果要好 100 个技能 = 6 种原子效果的组合
· 火球 = damage + buff
· 治疗术 = heal
· 冲锋 = move + damage
· 召唤骷髅 = summon
· AOE 火球 = damage（范围）+ buff

加新技能：组合已有的效果，不需要写代码。
加新效果类型：才需要写代码——但这是低频操作。

判断标准：如果加一个新技能要写代码，说明效果拆分得不够细。

三、Buff 系统的五个要点

要点说明常见错误
叠加规则同名 Buff 怎么叠重复生效导致数值爆炸
优先级同类型谁生效高级被低级覆盖
到期处理用定时器还是每帧检查每帧遍历所有 Buff
来源追踪谁施加的（用于伤害归属）击杀不计入施加者
驱散规则哪些可驱散、驱散顺序驱散了不该驱散的
叠加规则的四种设计 ① 不可叠加——重复施加刷新持续时间
适用：控制类（眩晕、沉默）
无限叠加的眩晕会让玩家永远动不了

② 可叠加层数——最多 N 层，每层独立计算
适用：增益类（攻击提升 10%，最多 5 层）
必须有上限——否则数值爆炸

③ 刷新持续时间——只保留一个，但刷新时间
适用：DoT（持续伤害）

④ 取最强——同名只生效最强的那个
适用：装备光环

经典事故：上线后发现眩晕可以无限叠加，玩家被永久控制。
防护：所有控制类 Buff 都必须设叠加上限。
到期处理：别每帧遍历 错误做法：
for _, buff in ipairs(buffs) do
  if buff.endTime <= now then remove(buff) end
end
每帧遍历所有 Buff——Buff 多了就是瓶颈

正确做法：用最小堆按到期时间排序（页 07、25）。
· 每帧只需检查堆顶是否到期
· O(1) 检查，O(log n) 插入

注意：Buff 的持续时间可能被刷新（再施加一次）。
方案：标记删除 + 重新入堆（同页 07 的堆更新问题）。
