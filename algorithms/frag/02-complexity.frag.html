02 · 复杂度与性能直觉

这一页讲游戏程序员最需要的那个能力：看到一段代码，能立刻判断它会不会成为瓶颈。这比记住任何算法都重要。

这一页在路线中的位置 上一页（01）说了要学什么。这一页给出判断标准——看到一个操作，能立刻说出它值不值得优化。
关键衔接：这里定下的"每帧 16.7ms、单系统 1~2ms"是后面所有性能结论的基准；页 12、26、30 的取舍都建立在这个预算上。
下一页（03）开始讲具体结构。先有预算感，再看结构，才不会把注意力放错地方。
验证方式：本页的"队列 vs 环形缓冲""拼接 vs concat"都有实测数字，后面的页面会逐个复现。

一、游戏程序的"复杂度预算"

游戏和普通程序最大的不同：每帧只有 16.7 毫秒（60 帧时）。超了就是卡顿。

数据量O(n)O(n log n)O(n²)
10瞬时瞬时瞬时
100瞬时瞬时微秒级
1,000瞬时微秒毫秒级（危险）
10,000微秒毫秒秒级（不可接受）
100,000毫秒几十毫秒分钟级
记住这三个数字 在 60 帧的游戏里，每帧预算是 16.7 毫秒。
但不要把这 16.7 毫秒全用在一个系统上——要分给逻辑、物理、动画、UI、渲染。

实际的预算参考：
· 单个系统：1~2 毫秒
· 单帧所有逻辑：5 毫秒以内
· 剩下留给渲染和引擎

换算成操作次数（很粗略）：
· 1 毫秒 ≈ 100 万次简单运算（Lua 里约 10 万次）
· 所以：每帧几十万次循环是危险的

有了这个直觉，你就能快速判断一段代码能不能放在 Update 里。

二、常见操作的复杂度速查

操作复杂度游戏里的影响
数组索引访问O(1)安全
哈希表查找O(1) 平均安全
哈希表最坏O(n)哈希冲突严重时
数组遍历O(n)看 n 多大
数组中间插入/删除O(n)要移动元素
队列头部删除O(n)经典错误（应用环形缓冲）
堆插入/取顶O(log n)安全
排序O(n log n)看 n，避免每帧排
嵌套循环O(n²)n 超过 1000 就危险
递归（无记忆化）可能指数级非常危险
字符串拼接（循环内）O(n²)必须用 table.concat
三个最常见的性能杀手 ① 嵌套循环做邻近查询
for i = 1, #units do
  for j = i+1, #units do
    if distance(units[i], units[j]) < R then ... end
1000 个单位 = 50 万次距离计算 = 必卡
解法：空间划分（页 12）

② 队列用 table.remove(t, 1)
每次出队都要移动后面所有元素——实测比环形缓冲慢 500 倍以上
解法：环形缓冲（页 03）

③ 循环内字符串拼接
local s = ""
for i = 1, n do s = s .. i end
每次 .. 都创建新字符串
解法：table.concat（实测快 16~22 倍）

三、怎么培养复杂度直觉

方法一：数循环嵌套的层数 快速判断法：
· 一层循环 → O(n)
· 两层嵌套 → O(n²)
· 循环里查哈希表 → 还是 O(n)（因为查找是 O(1)）
· 循环里遍历另一个数组 → O(n²)
· 循环里二分查找 → O(n log n)

注意"隐藏的循环"：
· table.remove(t, 1) 内部有循环 → O(n)
· s = s .. x 内部要复制 → O(len)
· FindObjectsOfType 内部遍历场景
· 看起来是一个函数调用，实际是 O(n)
方法二：把数据量乘 10 试试 最快的验证方式：把数据量放大 10 倍，看耗时怎么变。
· 耗时也×10 → O(n)
· 耗时×100 → O(n²)
· 耗时×12 → O(n log n)

为什么必须实测：因为常数因子可能很大。
一个 O(n) 但每步都做复杂计算的算法，可能比 O(n²) 但每步很简单的慢。

本站所有算法都做了实测对比——因为实测数据比理论分析更可靠。
方法三：先问"这个操作多久执行一次" 执行频率决定了优化优先级：
· 每帧执行（Update 里的逻辑）→ 绝对要优化
· 每秒执行→ 要小心
· 打开界面时执行→ 可以慢一点
· 加载时执行一次→ 基本不用优化

典型误判：
· 花大力气优化"加载配置表"的代码——但那只执行一次
· 忽略了"每帧查找组件"——看起来只是个小操作

判断顺序：先问频率，再看复杂度。高频 + O(n) 比低频 + O(n²) 更值得优化。
