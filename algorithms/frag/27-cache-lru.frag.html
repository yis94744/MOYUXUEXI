27 · 缓存策略与 LRU

缓存是优化性能最有力的手段，但它有个致命问题：内存只涨不降。这一页讲怎么给缓存加"上限"和"淘汰策略"。

这一页在路线中的位置 上一页（26）把缓存列为最有效的优化手段之一。这一页讲它的账单——没有上限的缓存就是内存泄漏。
关键衔接：LRU 需要"哈希表 + 双向链表"，正好是页 04（链表）与页 05（哈希）的组合应用；路径缓存、流场缓存都直接用到它。
下一页（28）位运算。从"省时间"转向"省空间"。
验证方式：本页的淘汰策略可以用同一组访问序列对比命中率，结论可复现。

一、缓存的三个必须解决的问题

问题不解决的后果方案
什么时候失效拿到过期数据时间/版本/手动失效
缓存多大内存爆掉容量上限
满了淘汰谁频繁淘汰有用的淘汰策略
没有上限的缓存 = 内存泄漏 这是最常见的性能 bug 之一：
cache[key] = value -- 只加不删
· 游戏运行 10 分钟没问题
· 运行 1 小时内存涨到 500MB
· 运行 3 小时崩溃

为什么难发现：短期测试看不出来，只在长时间运行时暴露。

解决：给每个缓存都设容量上限和淘汰策略。
这是"必须做"而不是"可选优化"。

二、四种淘汰策略的对比 ★★★

策略淘汰谁实现难度命中率
FIFO最早进入的易一般
LRU最久未使用的中好
LFU使用次数最少的难好（但可能淘汰新数据）
TTL过期的易看场景
LRU 的正确实现：哈希表 + 双向链表 LRU 需要 O(1) 完成两件事：
① 查找——某个 key 在不在缓存里
② 移动——把刚用过的移到"最新"位置

只用哈希表：能 O(1) 查找，但无法知道谁最久没用。
只用链表：能知道顺序，但查找是 O(n)。

组合起来：
· 哈希表：key → 链表节点（O(1) 定位）
· 双向链表：维护使用顺序（O(1) 移动）
· 访问时：把节点移到链表头部
· 满了时：删除链表尾部

为什么必须双向：单向链表无法 O(1) 删除已知节点（拿不到前驱）。

实战简化：Lua 里可以用一个表存顺序 + 一个表存数据，但完全 O(1) 需要额外维护索引。
如果缓存不大（几千项），简单实现就够。
Lua 里的简化 LRU 不需要真的实现双向链表——可以用"时间戳"近似：
cache[key] = { value = v, lastUsed = os.clock() }
· 访问时更新 lastUsed
· 满了时遍历找出 lastUsed 最小的淘汰
复杂度：淘汰是 O(n)，但淘汰不频繁（只在满时发生）。
适用：缓存规模几千项以内。

更简单的近似：随机淘汰一个。
看起来粗暴，但实测命中率只比 LRU 差一点——因为缓存通常是"热点集中"的。
如果实现成本高，随机淘汰是可行的折中。

三、游戏里的缓存应用

场景缓存什么策略
配置表索引id → 配置对象不淘汰（一次性）
路径缓存起点终点 → 路径LRU + TTL
寻路网格计算好的流场LRU
UI 图集加载过的贴图LRU
字符串格式化常用格式串FIFO
距离计算复杂表达式的值TTL（每帧清）
网络响应接口返回TTL
什么时候该加缓存 判断标准：同样的计算是不是发生了很多次？

值得缓存：
· 结果不变或很少变
· 计算有成本（复杂、IO、跨语言）
· 调用频繁

不值得缓存：
· 结果每次都不同（随机数）
· 计算很便宜（加两个数）——缓存查找本身也有成本
· 只调用一次

注意：缓存查找的成本可能比计算本身还高。
实测方法：加缓存前后各测一次，只看数据。
