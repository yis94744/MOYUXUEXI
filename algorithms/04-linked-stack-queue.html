    一、链表：为什么游戏里用得少

    链表在教科书里很重要，但在游戏里要谨慎使用。原因不是算法复杂度，而是缓存不友好。

    操作数组链表
    随机访问O(1)O(n)
    头部插入O(n)O(1)
    中间插入O(n)O(1)（已知位置）
    缓存友好优（连续）差（指针跳转）
    内存开销低高（每个节点要存指针）
    GC 压力低高（每个节点都是对象）
    为什么游戏里很少用链表 三个原因： ① 缓存不友好——遍历时每个节点的访问都可能缓存未命中，实测比数组慢 5~10 倍 ② GC 压力——每个节点都是一个独立对象，频繁增删会产生大量垃圾 ③ Unity 的序列化不支持——链表无法在 Inspector 里显示 替代方案： · 需要频繁中间插入 → 用数组 + 空闲位标记，或索引链表（用数组存 next 索引） · 需要 LRU → 用哈希表 + 双向索引链表（见算法站页 27） 结论：除非有明确的理由，否则用数组。链表的价值在"频繁中间增删且已知位置"的场景。

    二、栈：LIFO 的三个真实用途

    用途为什么用栈相关页
    UI 界面栈打开/关闭天然是后进先出Lua 站 16
    撤销功能要按操作顺序逆序撤销算法站 30
    表达式求值括号匹配、中缀转后缀编译器原理
    DFS 遍历深度优先天然是栈算法站 10
    对象池取出与归还顺序无关，栈最快算法站 26
    UI 界面栈是最典型的应用 场景：游戏中打开背包 → 打开道具详情 → 打开使用确认。 用栈的做法：push(背包) → push(道具详情) → push(确认框) 返回时 pop() 依次回到上一层——完全符合直觉。 用普通状态机的问题：你需要记住"打开详情前是什么界面"，还要处理任意层级的嵌套。 栈天然解决了"记住上一级"的问题——这就是为什么 UI 框架都用栈。

    三、队列：FIFO 的三个真实用途

    用途为什么用队列实现选择
    事件队列按发生顺序处理环形缓冲
    资源加载队列先请求先加载可扩展队列
    BFS 遍历广度优先天然是队列环形缓冲
    任务调度分帧执行，按顺序优先队列（堆）
    队列实现的性能陷阱 错误做法：用数组 table.remove(t, 1) 出队。 这会导致每次出队都要移动后面所有元素——O(n) 复杂度。 正确做法： · 用环形缓冲（本页演示的方式）——出队 O(1) · 或用头尾索引代替删除（不移动元素，只移动索引） · 或用反向数组（从尾部进出） 实测对比：10000 个元素的队列，用 table.remove(t,1) 逐个出队需要 约 0.40~0.50 秒；改用头索引（只移动 head，不搬元素）几乎测不出耗时（低于 os.clock 的分辨率）——差距在 500 倍以上。
    注意：环形缓冲和"头索引"是同一个思想的两种写法——出队时只改索引，不搬数据。
