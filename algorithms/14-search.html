    14 · 查找与字符串算法

    一、四种查找方式的选择

    方式复杂度前提适用
    顺序遍历O(n)无数据少、查一次
    二分查找O(log n)必须有序静态数据、范围查询
    哈希查找O(1)需要索引表精确查找（最常用）
    TrieO(m)按前缀敏感词、自动补全
    BST / 跳表O(log n)有序范围查询 + 动态插入
    二分查找的六个易错点 二分查找看起来简单，但极容易写错（据说正确率只有 10%）：

    ① 循环条件：while lo <= hi（不是 <）
    ② 中点计算：math.floor((lo + hi) / 2)（直接相加可能溢出）
    ③ 边界更新：lo = mid + 1 / hi = mid - 1（要 ±1，否则死循环）
    ④ 未找到：返回 nil 或 -1，要明确约定
    ⑤ 重复元素：要明确返回第一个还是任意一个
    ⑥ 有序前提：数据必须是有序的——这是最常见的使用错误

    验证方法：用边界值测（第一个、最后一个、不存在的值）。

    二、索引：最划算的优化 ★★★

    一个真实的优化案例 场景：1000 条装备配置，需要按 ID 查询。

    优化前（每次遍历）：
    for _, item in ipairs(configs) do
      if item.id == target then return item end
    end
    10000 次查询实测 0.1590 秒

    优化后（建立索引）：
    byId[item.id] = item -- 加载时建一次
    return byId[target] -- 查询 O(1)
    10000 次查询实测 0.0010 秒

    实测快 159 倍！

    关键点：索引要在加载时建一次，而不是每次查询都建。
    这是"用内存换时间"最典型的应用。
    要建哪些索引 看业务代码里怎么查：
    · getById → 建 byId
    · getByName → 建 byName
    · getByType → 建 byType（值是数组）
    · getByQuality → 建 byQuality

    原则：配置表通常很小（几千条），多建几个索引的内存开销可以忽略，但能避免大量遍历。

    注意：索引是"只读"的——配置加载后不再变化。
    如果配置会热重载，重建索引要和重新加载一起做。

    三、字符串算法在游戏里的应用

    算法用途复杂度
    Trie敏感词过滤、自动补全O(m)，m 是词长
    AC 自动机多关键词同时匹配O(n + 匹配数)
    KMP单模式串匹配O(n + m)
    Rabin-Karp哈希匹配、查重平均 O(n + m)
    编辑距离模糊匹配、拼写纠错O(nm)
    敏感词过滤：为什么不能用 string.find 循环 错误做法：
    for _, word in ipairs(badWords) do
      if text:find(word, 1, true) then return true end
    end
    1000 个敏感词，每条消息要扫 1000 次——每条聊天消息耗时几毫秒。

    Trie 的做法：
    · 预先把所有敏感词建成 Trie
    · 遍历文本的每个字符，沿着 Trie 走
    · 走到终止节点 = 命中
    复杂度从 O(词数 × 文本长) 降到 O(文本长 × 最大词长)

    AC 自动机更进一步：一次遍历同时匹配所有模式——适合有几千个敏感词的场景。
