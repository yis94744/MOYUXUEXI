    一、你已有的三个优势 ★★

    优势在后端的价值
    C# / .NET 熟练ASP.NET Core 就是 C#，语法零成本
    性能调优直觉后端同样吃性能：GC、连接池、SQL
    懂游戏业务最稀缺——纯后端不懂玩法
    懂网络同步状态同步/帧同步你做过
    懂客户端约束能设计出客户端好用的协议
    最大优势：能设计出「客户端愿意用」的接口 纯后端写的接口，客户端往往用起来很别扭：
    · 一个界面要发 5 个请求才能凑齐数据
    · 字段结构不符合客户端的数据模型
    · 没有考虑网络抖动时的体验

    而你两边都懂，能设计出「一个请求拿到一屏数据」的接口。
    这是纯后端给不了的价值，也是你转岗的谈判筹码。

    二、五个必须改掉的客户端习惯 ★★★

    习惯一：「崩了重进就行」→ 后端不能崩 客户端：崩了玩家重进游戏。
    后端：崩了所有玩家掉线 + 可能数据损坏。

    要改的地方：
    · 所有异常都要捕获（不能有任何未处理异常）
    · 关键路径加兜底
    · 状态要能恢复（进程重启后从数据库恢复）

    本页呼应页 15 的「房间状态机」——状态转移必须显式、可恢复。
    习惯二：「内存里存着就行」→ 后端要无状态 客户端：数据存在 MonoBehaviour 字段里。
    后端：进程重启数据就没了，而且多实例不同步。

    要改的地方（页 23）：
    · Session 放 Redis
    · 临时文件放对象存储
    · 定时任务状态放数据库（否则每台都跑一遍）

    判断标准：换一台机器，这个状态还在吗？
    习惯三：「每秒60帧」→ 后端看的是 QPS 和 P99 客户端：关心帧率（16.7ms/帧）。
    后端：关心QPS + P99 延迟。

    要改的地方（页 25）：
    · 看 P99 不看平均
    · 优化顺序：架构 → 数据库 → 算法 → 代码
    · 不要用「帧」的思维看后端

    客户端的 60 帧 = 每帧 16.7ms 预算；后端的 1000 QPS = 每请求 1ms 预算。
    习惯四：「本地算就行」→ 服务端必须权威 客户端：伤害、掉落都在本地算。
    后端：客户端算的一切都可以被改。

    要改的地方（页 19）：
    · 影响他人或经济的 → 服务端算
    · 客户端上报的数据 → 交叉校验
    · 判断标准：玩家改了会怎样？

    这一条是本路线最重要的转变。
    习惯五：「先跑起来再说」→ 后端要先想幂等 客户端：重复点击顶多放两个技能。
    后端：重复请求会重复发奖、重复扣钱。

    要改的地方（页 03、18）：
    · 所有写操作都要幂等
    · 用业务唯一键去重
    · 「已处理」要返回成功

    客户端的「重试」是必要行为，后端必须能承受。

    三、90 天上手计划

    阶段时间目标验收
    第 1~2 周基础页 03-06能写一个带鉴权的 CRUD
    第 3~4 周数据页 07-10能设计表 + 查优化
    第 5~8 周游戏后端页 11-15能跑通一个房间服务
    第 9~10 周全栈页 20-22能做一个运营后台
    第 11~12 周上线页 23-25能部署 + 压测
    一个现实的时间表 90 天能从「会客户端」到「能写生产后端」吗？
    能写，但不算精通。

    现实预期：
    · 1 个月：能写独立的小服务
    · 3 个月：能维护一个有状态服务
    · 1 年：能独立扛一个项目
    · 3 年：能设计架构

    转岗的现实：大概率是平薪或降薪（页 01）——但天花板更高。
