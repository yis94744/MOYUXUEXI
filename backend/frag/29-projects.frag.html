一、五个项目（难度递增）

#项目核心能力相关页时长
1游戏配置管理后台CRUD + 分页 + 权限20, 211 周
2玩家数据服务数据库 + 缓存 + 事务07, 08, 182 周
3登录与账号系统JWT + 刷新 + 防刷06, 191.5 周
4排行榜服务Redis ZSet + 分页 + 赛季08, 171.5 周
5小型对战服务器长连接 + 房间 + 同步11-154 周
三个必须避免的坑 ① 只做 CRUD，不做防护
很多人做后台只有增删改查，没有权限、没有审计。这些才是体现工程能力的地方。

② 直接上微服务
三张表的项目拆成五个服务 → 折腾一周还没跑起来。

③ 不做压测
接口"能用"和"能扛"是两回事。
怎么让项目值得写进简历 不是「我做了个后台」，而是：
· "实现了游戏配置管理后台，支持 6 种配置表、三级权限、全操作审计"
· "用 Redis ZSet 实现全服排行榜，10 万玩家下 P99 查询 5ms"
· "实现了带幂等的发奖接口，压测 5000 QPS 无重复发放"

区别在于：量化 + 技术决策 + 解决的问题。

二、每个项目都该有的骨架

要素为什么要求
分层结构展示架构能力Controller / Service / Repository
统一响应展示规范意识code/msg/data
错误处理展示健壮性全局异常中间件
日志展示可维护性结构化日志
测试展示质量意识至少核心逻辑有单测
README展示表达力架构图 + 关键决策
为什么这些"骨架"重要 因为面试官会问：
· "你的异常怎么统一处理？" → 全局中间件
· "怎么排查线上问题？" → 结构化日志 + traceId
· "改代码怎么保证不出错？" → 单元测试

这些问题答不好，会立刻暴露"只写过 demo"。
而这些骨架本身不难——每个半天就能搭好。

本章动手任务

本章过关标准：
① 有一个能完整跑起来的后端项目；
② 有分层结构和统一响应格式；
③ 有权限、幂等、参数校验；
④ 有压测数据（QPS 和 P99）；
⑤ 有 README 说明架构和关键决策。

第 ③ 和 第 ④ 条是简历上的硬通货——**它们证明你写的是"能上线的代码"**。
