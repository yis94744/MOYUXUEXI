    一、Lua 错误的三个特点

    特点表现应对
    错误位置可能不准报错行 ≠ 真正的错误行往上看几行
    静默失败多访问 nil 字段只是返回 nil主动加断言
    错误信息不完整只有一行，没有调用栈用 xpcall + traceback
    Lua 最常见的错误：attempt to index a nil value 这个错误占 Lua 报错的 80%。
    含义：你访问了一个 nil 值的字段。
    local obj = nil
    obj.field = 1 -- attempt to index a nil value (local obj)

    常见原因：
    · 对象已销毁但引用还在（→ 假 null，见 C# 站页 11）
    · 模块 require 失败（→ 返回 nil）
    · 配置表里没有这个 ID（→ 查表返回 nil）
    · 热更后引用失效

    排查方法：把报错行拆开，逐个打印中间变量。
    预防方法：关键位置主动断言：assert(obj, "obj 不应该为空")

    二、错误定位的四种手段

    手段用法适用
    print 大法打印关键变量最快，但污染输出
    assert 断言主动检查前置条件定位"谁传了 nil"
    xpcall + traceback获取完整调用栈复杂逻辑
    断点调试VS Code + 插件最强大
    assert 是最好的调试工具 assert 的价值不只是"检查"，而是"定位"。

    没有 assert 时：
    -- 在很远的地方报错
    attempt to index a nil value
    你要往上追溯好几层才知道谁传了 nil。

    有 assert 时：
    function setTarget(obj)
      assert(obj, "setTarget: obj 不能为 nil")
    end
    直接定位到"谁调用了 setTarget 并传了 nil"。

    建议：框架的公开接口都应该加参数校验。
    xpcall + traceback 获取调用栈 Lua 的默认错误信息没有调用栈——只有一行"哪里出错了"。
    获取完整堆栈：
    local ok, err = xpcall(func, debug.traceback)
    err 里会包含从调用点开始的完整调用链。

    实战用法：框架的顶层（UI 按钮回调、网络回调、定时器回调）都应该用 xpcall 包一层。
    这样任何回调出错都能拿到完整堆栈，而不是一行孤立的错误。

    更进一步：把堆栈上报到服务器，线上问题也能看到调用链。

    三、四个疑难问题库 ★★★

    问题一：只在真机上出现，编辑器里正常 常见原因：
    ① 时序差异——真机帧率低，某些竞态才暴露
    ② 代码裁剪——xlua 的生成代码没包含某个方法
    ③ 热更版本不一致——真机用的是线上脚本
    ④ 内存压力——真机内存少，GC 更频繁

    排查方法：
    · 先在真机上复现（不要试图在编辑器里"造"出来）
    · 用 adb logcat 抓完整日志
    · 对比"编辑器用的脚本"与"真机用的脚本"是否一致

    这类问题的价值很高——它往往暴露了真实的设计缺陷。
    问题二：内存只涨不降 常见原因：
    ① 事件订阅没取消——对象被事件系统持有（→ 页 16 的经典问题）
    ② 缓存没上限——资源缓存无限增长
    ③ 全局表累积——往全局表里塞数据，从不清理
    ④ 闭包持有大对象——闭包捕获了不需要的东西

    排查方法：
    · collectgarbage("count") 打印内存，观察趋势
    · 用 弱表试探：把可疑的引用改成弱引用，看对象是否被回收
    · 二分法：注释掉一半逻辑，看内存是否还涨
    问题三：热更后行为异常 常见原因：
    ① 旧引用指向旧模块（→ 页 09 的核心问题）
    ② 状态残留（→ 页 15、17）
    ③ 部分模块热更了，部分没有——依赖不一致

    排查方法：
    · 打印模块的版本号或哈希，确认全部更新了
    · 在模块顶部加一个标记：MODULE_VERSION = "2.1"
    · 对比"热更前后"的行为差异

    预防：热更清单要包含所有相关模块，不能只更一部分。
    问题四：随机崩溃，无法复现 排查顺序：
    ① 先拿到崩溃日志——没有日志就没法查
    ② 看崩溃位置——是 Lua 层还是 C# 层
    ③ 找共同的触发条件——都在做某个操作时崩？
    ④ 加日志缩小范围——在可疑位置打点

    最常见的根因：
    · 访问已销毁的对象（C# 对象被 Destroy 了，Lua 还持有引用）
    · 解决：持有时检查 ~= nil，或者监听销毁事件自动清理引用

    工具：Unity 的 Development Build + Log Stack Trace 能给出 C# 侧的堆栈。
