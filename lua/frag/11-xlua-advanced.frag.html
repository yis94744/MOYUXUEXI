一、跨语言调用的真实成本

先看一组实测数据（数量级参考，具体值因机器而异）。

操作相对开销说明
Lua 内部函数调用1x基准
Lua 调 C#（已生成代码）5~20x有栈切换成本
Lua 调 C#（反射）100x+必须避免
Lua 调 C# 并创建对象50~200x还有 GC 压力
C# 调 Lua（已生成代码）5~20x同样有切换成本
核心原则：减少跨语言的调用次数 不是"减少每次调用的开销"，而是"减少调用次数"。

反面例子（每帧调用 N 次）：
for i = 1, 100 do
  transform.position = Vector3(i, 0, 0) -- 100 次跨语言调用
end

正面例子（跨语言 1 次）：
local positions = {}
for i = 1, 100 do positions[i] = {i, 0, 0} end
batchSetter(positions) -- 1 次调用，批量设置

这是 xLua 优化的第一原则——把 N 次调用合并成 1 次。

二、GC 优化（xLua 的重灾区）

每一次跨语言调用都可能产生垃圾 垃圾来源：
① 参数装箱——Lua number 传给 C# 的 object 参数
② 临时对象——Vector3、Color 等 struct
③ 字符串拷贝——每次传 string 都复制
④ 委托创建——传 Lua function 给 C# 的 delegate 参数

优化手段：
· 缓存 Vector3：local tmpVec = CS.UnityEngine.Vector3.zero，用 Set 修改而不是 new
· 避免传字符串：用数字 ID 或缓存字符串引用
· 避免传函数：用事件 ID + 注册表代替直接传 delegate
· 用 xlua.struct：让 struct 在 Lua 侧以值语义传递
验证方法 Profiler 看 GC Alloc 列：
· 目标：Update 相关的 GC Alloc 降到 0 B
· 如果有分配，展开调用树，定位到具体哪一行

常见的高分配位置：
· transform.position 的读写
· Debug.Log 里的字符串拼接
· 每帧的 UI 文本更新

这些在纯 C# 项目里可能不是问题，但在 Lua + C# 的边界上，成本被放大了。

三、六个实战优化技巧

技巧做法收益
批量操作N 次调用合并成 1 次极大
缓存引用local go = CS.UnityEngine.GameObject中
缓存组件不要每帧 GetComponent大
避免反射标记 [LuaCallCSharp] 并生成代码极大
减少字符串用数字 ID 代替字符串中
分帧执行把耗时逻辑摊到多帧大
缓存引用的正确姿势 差的写法：
local go = CS.UnityEngine.GameObject() -- 每次都查 CS 表

好的写法：
local GameObject = CS.UnityEngine.GameObject -- 模块顶部缓存
local go = GameObject() -- 直接用缓存

但要小心：缓存的是"类引用"，不是"实例引用"。
实例引用如果指向已销毁的对象，会变成"假 null"（见 C# 站页 11）——用之前要检查 ~= nil。
