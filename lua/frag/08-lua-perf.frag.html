二、两个反直觉的实测结论 ★★★

反例一：缓存全局函数在 Lua 5.4 下没有收益 常见说法：「把 table.insert 缓存成 local insert = table.insert 会快很多」。
实测结果：两者耗时完全相同（1.00 倍）。

为什么：Lua 5.4 用数组存全局变量（不是哈希表），全局访问本身就是 O(1) 索引——和局部变量访问的差距远小于 LuaJIT 时代。

那什么时候还有用？
· 在 LuaJIT 下差异明显（JIT 为局部变量生成寄存器访问）
· 极热循环（每帧几百万次调用）
· 需要 API 稳定性时（把依赖固定，外部改动不影响）

结论：这不是优先优化项。先做收益大的（见表格第 1~5 项）。
反例二：ipairs 比数字 for 慢得多 常见说法：「遍历数组用 ipairs，比 for i = 1, #t 更快（因为缓存了长度）」。
实测结果：ipairs 慢了 2.6 倍。

为什么：ipairs 每次迭代都要调用一次迭代器函数——一次函数调用的开销。而数字 for 循环是虚拟机原生指令，没有函数调用。

正确的热路径写法：
local n = #arr
for i = 1, n do ... end

缓存长度确实有收益（3~4%），但要配合数字 for 使用，而不是 ipairs。

实战建议：非热路径用 ipairs（可读性好）；热路径用数字 for + 缓存长度。

三条最重要的原则 ① 先测量，再优化
不要凭直觉。本页就有两个反例说明"经验"可能是错的。

② 优化热路径，不是全部代码
80% 的时间花在 20% 的代码上。先用 Profiler 找到那 20%。

③ 可读性优先，除非测得慢
把变量名改成 a、b、c 确实快一点，但代价是没人看得懂。

项目节奏建议：
· 早期：不优化，先写清楚
· 中期：建立性能基线，定期测
· 后期：针对瓶颈做优化
· 永远：优化后再测一次，确认真的变快了
