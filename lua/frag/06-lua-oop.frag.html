06 · 面向对象与继承

Lua 没有 class 关键字。所有面向对象都是用 table + 元表手工实现的。这一页不只讲"怎么实现"，更要讲清为什么框架都那样写——以及那些写法背后的取舍。

这一页在路线中的位置 上一页（05）的闭包和这一页的元表，是 Lua 实现封装的两种手段——这一页会对比它们的优劣。
关键衔接：页 04 学的 __index 是继承的实现机制，这一页把它包装成可复用的 class 函数。
下一页（07）高级特性：协程、错误处理、GC。那里的状态机与错误对象都会用到这一页的 class。
实战意义：你在项目里遇到的 Lua 框架（xLua、ToLua、各种自研框架）都以这一页的 class 实现为基础。看懂它，才能看懂框架源码。

一、用元表实现 class ★★★

缺少代码样本06/oop
class 实现的"三件套"（背下来） ① cls.__index = cls——让实例可以通过元表查到类里的方法。
② setmetatable(cls, { __index = superClass })——让子类能查到父类的静态成员。
③ setmetatable(instance, cls)——把实例和类关联起来。

查找链：instance.foo → 实例自身没有 → 查 cls（因为 __index = cls）→ cls 自身没有 → 查父类（因为 setmetatable(cls, {__index = super})）。
这就是 Lua 的继承。
三个最容易写错的地方 ① 冒号与点号的混用
function Animal:getName() 等价于 function Animal.getName(self)。
调用时必须用 obj:getName()（冒号）——写成 obj.getName() 会漏掉 self，报"尝试索引 nil"。

② 调用父类方法必须显式传 self
Base.describe(self) —— 不能写成 Base:describe()，那样 self 会变成 Base 本身。

③ 构造函数名没有强制约定
Lua 不会自动调用 ctor 或 __init。必须自己在 new 里显式调用。
不同框架用的名字不同（ctor / __init / OnInit），读源码时先找这个。

二、私有成员：两种方案对比

下划线约定闭包实现
写法self._balance局部变量 + 闭包捕获
真实私有否 外部照样能改是 完全无法访问
内存占用小 方法共享大 每实例一份闭包
支持继承是困难
调试友好好 字段可见差 看不到内部状态
序列化可以很难
适用游戏逻辑（主流）模块级单例、工具类
游戏项目为什么主流用下划线约定 关键原因是"序列化和调试"：
• 存档需要遍历对象字段 → 闭包方案无法枚举出捕获的变量；
• 出 bug 时需要查看对象内部状态 → 闭包方案在调试器里看不到；
• 需要继承和对象池 → 闭包方案每实例一份方法，内存吃不消。

所以行业惯例是：用 _ 前缀表示"这是内部字段，外部别碰"，靠代码规范和 code review 保证，而不是靠语言机制。

三、性能：元表 vs 闭包（实测结论）

一个被广泛流传的错误结论 网上很多文章说"元表比闭包快"——但我实测的结果不是这样。

在 Lua 5.4 下跑 50 万次方法调用：
• 元表方式：0.018 秒
• 闭包方式：0.014~0.017 秒
• 两者几乎一样，闭包偶尔还更快

为什么：元表的 __index 查找本身也有成本，粗略抵消了它的理论优势。

那为什么框架还是用元表？真正的原因是内存和继承能力：
• 元表：1000 个实例只有 1 份方法代码
• 闭包：1000 个实例有 1000 份方法闭包
对象数量上万时，闭包方式的内存占用会非常可观。
选型依据 需要继承 且 实例数量多 → 用元表（框架标准做法）
只是单个简单对象 / 模块级单例 → 闭包也很合适，而且代码更简洁

不要为了"性能"这个错误的理由去选元表。选它是因为内存和继承。
