二、定时器模块

定时器的两种实现 方案一：每帧遍历（简单） · 维护一个列表，每帧检查每个定时器是否到期 · O(n) 每帧——定时器少时够用 方案二：最小堆（高效） · 用堆按"触发时间"排序（见算法站页 07） · 每帧只需检查堆顶是否到期 · O(log n) 插入，O(1) 检查 选择依据： · 定时器 < 100 个 → 方案一（更简单） · 定时器 > 1000 个（比如每个 Buff 一个）→ 方案二 实战中，方案二更常用——因为服务器端的定时任务数量往往很大。
定时器最容易出的三个 bug ① 定时器泄漏：对象销毁了，但定时器还在，回调时访问已销毁对象。 解决：把定时器绑定到对象，对象销毁时批量清理。 ② 同一帧触发多次：如果帧间隔大于定时器周期，可能一帧触发多次。 解决：明确设计——是"每次到期触发一次"还是"补足所有遗漏的触发"。 ③ 在回调里删自己：遍历中修改列表 → 索引错位。 解决：用快照遍历或标记删除（和页 13 的事件系统一样）。

三、配置表模块

配置表的三个设计要点 ① 索引优于遍历 加载配置时建立常用索引： · byId[id] = config · byName[name] = config · byType[type] = { config1, config2 } 把 O(n) 的遍历变成 O(1) 的查找。 ② 只读保护 配置加载后应该只读——防止业务代码意外修改。 用元表的 __newindex 实现（见页 04）。 ③ 支持热重载 开发期能重新加载配置而不重启游戏。这能大幅提升调试效率。 实现：重新解析文件 + 重建索引 + 通知订阅者刷新。
