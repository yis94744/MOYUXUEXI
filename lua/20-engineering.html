    一、Lua 代码规范

    方面规范为什么
    命名local 用小驼峰，类名大驼峰和 C# 保持一致
    模块一个文件一个模块，返回 table便于热更
    局部变量默认 local避免全局污染
    缩进统一 2 或 4 空格代码 diff 清晰
    注释公开接口必须有注释方便他人调用
    最容易犯的规范错误：忘记 local Lua 的一个设计特性：不加 local 就是全局变量。

    后果：
    · 全局命名空间被污染
    · 模块之间意外互相影响
    · 热更时全局变量状态残留（→ 页 15、17 的老问题）
    · 在沙箱环境下会直接报错（因为全局表被限制了）

    防护手段：
    ① 用静态检查工具（如 luacheck）——这才是主力手段，在 CI 里把 W111（setting a non-standard global）当错误
    ② 调试期给 _G 挂 __newindex 拦截： setmetatable(_G, { __newindex = function(_, k) error("禁止写全局: "..tostring(k), 2) end }) ——注意只能在调试构建里开，它会拖慢所有全局写入，而且会误伤那些故意写全局的第三方库
    ③ 代码 review 时重点看这个

    注意：常见写法里流传的 local _ENV = ... 并不能起到防护作用—— 模块被 require 时 ... 是模块名字符串， 把它赋给 _ENV 之后，模块里任何全局读写都会变成"对字符串取下标"而直接报错： attempt to index a string value (local '_ENV')。 真要限制环境，应该用 load(代码, 名字, "t", 环境表)（见页 07），而不是改模块自己的 _ENV。

    建议：在 CI 里跑 luacheck，把"未声明的全局变量"作为错误。

    二、与策划协作

    让策划能改配置，但改不了逻辑 目标：策划能自主调整数值和流程，但不会写出能崩溃游戏的代码。

    做法：
    ① 配置用数据格式（JSON / Excel / CSV），不用 Lua
    ② 需要写逻辑的部分，用受限的 DSL：
      · 只暴露安全的白名单 API
      · 不能访问文件系统、网络、反射
      · 用沙箱执行（→ 页 07 的 _ENV）
    ③ 提供编辑器工具（Excel 校验、可视化编辑）

    收益：策划改数值不用找程序，程序不用被打断。这是团队效率的巨大提升。

    三、CI 与自动化

    环节工具作用
    语法检查luac -p提前发现语法错误
    静态分析luacheck未声明全局、未使用变量
    单元测试busted核心逻辑回归
    打包脚本 + 版本号自动生成清单
    热更发布脚本 + 校验防止漏文件
    最值得做的三个自动化 按投入产出比排序：
    ① 语法检查——luac -p 一行命令，能拦住 60% 的低级错误
    ② 静态检查——luacheck 找出全局变量泄漏，能拦住 20%
    ③ 热更清单自动生成——防止"漏推文件"这类事故

    这三个加起来可能只要半天工作量，但能避免大量线上问题。
    这回到 C# 站页 19 的原则：同一个错误犯过两次，就该写工具防止第三次。
