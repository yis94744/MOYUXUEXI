18文件锁：二进制文件独占编辑

图片、PSD、3D 模型、Excel 表格这些二进制文件，两个人同时改就废了—— 它们没法像代码那样「一行一行合并」， 后提交的那个人会把前一个人的工作整个盖掉。 解决办法是加锁：我先把它锁上，别人就改不了，等我改完再放开。

为什么二进制文件必须靠锁，而不是靠合并

源码文件是纯文本，两个人的改动即使落在同一行，SVN 也能给你标出来、让你选留谁的。 这类文件天生可以「合并」。

但一张 PSD 文件是一堆二进制数据，没有「第几行」这个概念。 两个人同时改，SVN 完全没办法把两份改动拼起来—— 它唯一能做的就是判定冲突，让你二选一。

而现实往往更糟：很多人不会谨慎处理，直接一路点「用我的」， 另一个人改了一下午的东西就这么没了，而且没有任何提示。

所以对二进制文件，正确的思路不是「出了冲突怎么合」，而是「从一开始就别让两个人同时改」。 这就是锁的作用：加锁之后，文件被一个人独占，别人在机制上就改不了，从根本上避免了覆盖。

加锁：把这文件占为己有

◈Get Lock 对话框：声明「这个文件接下来归我改」GET LOCK
这个对话框很简洁，但每一项都有实际作用：

① 上方的文件列表——这一次要给哪些文件加锁。 如果你是在某个文件上右键的，这里就显示那一个文件； 如果在文件夹上右键、并且勾了要包含的内容，这里就可能列出多个文件，可以逐条勾选。
列表里的勾选框让你精确控制「只锁其中哪几个」，批量加锁时很有用。

② Message · 备注框——给这次加锁写一句说明。 别人在文件上尝试加锁、或者查看锁定状态时，能看到你这句备注。
强烈建议填，而且要写具体：比如 我要调整首页banner的配色，大约两小时后释放。
一句好备注能省掉无数次「这个文件谁锁的、要锁多久、我要不要等他」的追问。
不填也能锁上，但别人就只能看到一个「有人锁了」，看不见原因—— 这时候大多数人会直接来找你问，反而更费时间。

③ Steal the locks · 抢锁——把锁从别人手里抢过来，归自己。
这个选项平时是灰的，只有当文件已经被别人锁住时才有意义。 勾上它并确认，那个人的锁会被强制解除，文件归你。
这是一个破坏性操作：对方可能正开着这个文件在改，毫无预兆的锁被抢走， 他保存的时候就会失败，甚至丢失未保存的修改。 详细说明见下面橙色警告框——这一项要慎之又慎。

④ Get 按钮 / Cancel——点 Get 执行加锁，点 Cancel 放弃。
加锁成功后，这个文件的角标会变成黄色的小锁，同时文件从只读变成可以编辑（如果它之前因为属性设置而只读的话）。
注意：加锁会立刻在服务器上留下记录，不需要提交。
LOCK加锁的完整步骤
准备动手改之前，先加锁（不是改完再加） 顺序很重要：先加锁，再打开编辑。 如果先打开改了半天才发现锁不上（别人已经锁了），那半天就白干了。
养成「动手前先锁」的条件反射，是使用二进制文件的基本功。
在文件上右键，打开加锁对话框 TortoiseSVN → Get lock...
菜单名带省略号，表示会弹出对话框。
确认要锁的文件，写清备注 看一眼文件列表是不是你要锁的那些。 然后在 Message 里写清楚你要做什么、大概多久。
「改一下」这种备注等于没写，能写多具体就写多具体。
如果提示「已被他人锁定」，先去找人 对话框会告诉你是谁锁的、什么时候锁的、备注写的是什么。
正确做法是去沟通，而不是抢。 对方可能马上就改完了。
点 Get，确认角标变化 加锁成功后黄色小锁的角标会出现。 这时候再打开文件编辑——一切正常。
改完之后... 别急着走，两步不能漏 先提交——把你的改动存入版本库。
再释放锁——右键 → TortoiseSVN → Release lock，把锁交还给团队。
很多人在提交的对话框里会看到一个「保留锁」的选项——除非你还要接着改，否则别勾它。
确认锁真的释放了 释放后黄色小锁消失。 如果你临时有事要先走，一定要记得释放， 否则这个文件会一直锁在你名下，别人干等。
实在来不及处理，至少在备注或群里说一声「我锁着 XX 文件，明天继续」。
Steal the locks 会破坏别人的工作，非必要不要碰

这个选项的存在是为了应对真实发生的意外（比如同事离职了、他的电脑坏了、锁挂在某个再也联系不上的人名下）， 而不是用来「我要改，你别挡路」。

抢锁之后会发生什么：

  • 对方的锁在毫无预警的情况下消失。他可能正开着这个文件在改，完全不知道已经失去控制权了。
  • 他保存时会被拒绝，或者更糟——如果软件不做检查，他会保存成功但提交失败， 白改一场。
  • 最坏的情况：他保存的内容把仓库里的覆盖了，或者他意识到后只能从头再来。 这已经不是浪费时间的问题了，是实实在在的工作损失。

正确的顺序永远是：先看备注 → 先问人 → 实在联系不上、而且确实紧急，才考虑抢锁。

抢完之后也建议跟对方说一声——毕竟从对方视角看，他的锁是「凭空消失」的，被蒙在鼓里的体验很差。

不忘记加锁的秘诀：让文件默认就是只读的

「先加锁再改」说起来简单，做起来经常忘—— 尤其是临时要改一张图的时候，往往是双击打开、改完保存、提交，全程没想起来有锁这回事。

针对这个「人会遗忘」的问题，SVN 提供了机制层面的解决办法：让文件一检出就是只读的。

◈svn:needs-lock 属性：用只读强制你想起加锁这件事PROPERTIES
这是个属性，不是每次手动操作。它是上一节讲的属性之一， 通过属性对话框设置（右键 → TortoiseSVN → Properties → New...）， 设好之后对这个文件、以及所有更新到它的人长期生效。

它做了什么：给文件设上这个属性之后，任何人检出或更新这个文件，拿到的都是「只读」的—— 双击能打开、能看，但一旦尝试保存，就会提示失败或者让你另存为。

为什么这样反而更好用：你正改得顺手、点了保存，结果被拒绝—— 这一下强力提醒了你「这个文件必须先加锁」。 于是你去加锁，然后文件自动变成可写的，继续改就行。
它把「记住要加锁」这件需要靠自觉的事，变成了一个「不做就干不下去」的硬性流程。 对容易忘事的人来说，这比任何提醒都管用。

加锁之后会自动变可写——这是这个机制设计得最舒服的地方： 你不需要手动去改文件属性，加锁成功的瞬间，SVN 会把这个文件变成可编辑状态；释放锁之后，它又变回只读。

怎么给一批文件设上：一般是在目录上设，并且勾上「递归应用」， 让整个目录树里的文件都继承这条规则。 但要注意：它会对目录下所有文件生效，包括那些其实可以合并的文本文件—— 所以更常见的做法是只在存放图片、设计稿、文档的这些专门目录上设，而不是整个项目根目录。
怎么快速判断「这个文件该不该设 needs-lock」

一个很好用的判断标准：这个文件能不能「打开来看见里面的文字」，并且改动能不能被一行一行地合并？

  • 能（源码、配置、说明文档）——不要设，让它保持可写，大家随便改，冲突了用合并工具解决。
  • 不能（图片、PSD、模型、Excel、压缩包）——设上，用只读强制大家先加锁。

还有一个更实际的判断法：如果两个人同时改了这个文件，会不会导致其中一方的成果彻底丢失？ 会，那就该设锁。

看图说话：锁和只读长什么样

LockedIcon · 黄色小锁 这个角标表示文件已经被加了锁。如果锁是你自己加的，说明你可以放心改；如果是别人加的，你就不应该去动它，动了也提交不上去。看到这个图标，先弄清楚「是谁锁的、为什么锁」。
ReadOnlyIcon · 只读标记 表示这个文件当前是只读的、不能编辑。在 SVN 里最常见的原因是：它设了 needs-lock 属性、而你还没有加锁。看到它别去手工改文件属性「解锁」——正确做法是走加锁流程，加锁后它会自己变成可写。
绕过只读去编辑，是最典型的错误操作

有人发现文件是只读的，保存不了，于是做了这件事： 在文件上右键 → 属性 → 把「只读」的勾去掉 → 然后照常编辑、提交。

这样做看起来「解决了问题」，实际上把所有保护都绕过去了：

  • 你没有加锁，所以别人也可能同时在改这个文件——锁机制完全失效了。
  • 真要出现两人同时改，结果依然是一方的工作被覆盖，而且是那种悄无声息的覆盖。
  • 你手工改的这个只读标记只是本地文件系统的事，和 SVN 的锁没任何关系； 下次更新，你的本地设置可能又被改回去，白折腾。

看到只读的正确反应只有两个：

  • 我要改它 → 老老实实走加锁流程（右键 → TortoiseSVN → Get lock...），加锁后它就变可写了。
  • 我不该改它（别人锁着 / 这不是我的活） → 别动它。

「和锁机制对抗」永远比「按流程加个锁」麻烦得多，而且后果更严重。

哪些文件该加锁，哪些不该

文件类型该不该锁理由
PSD / 设计稿 必须锁 Photoshop 文件完全是二进制，图层改一下整个文件就变了，没有任何合并的可能。 两人同时改必然丢工作。建议连同 needs-lock 属性一起设，从机制上强制。
Unity 场景 / 预制体 必须锁 游戏引擎的场景文件内部结构极其复杂，指一下鼠标都可能产生几百行变化。 两个人同时改一个场景，合并是根本不可能的事，只能二选一。
Excel / Word 文档 建议锁 虽然新版的 Office 文件格式在理论上能看出一些结构差异，但实际合并的结果通常没法看。 表格里两个人各填几行，合出来的东西经常是乱的。需要多人协作的数据，用共享的方式来管，不要靠版本库合并。
图片资源（png/jpg 等） 看情况 如果是美术实际会去改的源文件（比如需要重新裁切、调色的），该锁。 如果只是「导出的成品图、基本不会动」，那不用锁，锁了反而增加流程负担。
音视频素材 看情况 体积大、改动少的一般不用锁；需要反复剪辑加工的工程文件则该锁。
普通源码（.cs / .java / .js 等） 不要锁 这是最重要的「不该锁」的一类。 文本文件天生可以合并，冲突了用工具解决就行。 如果给每个源码文件都加上锁，就等于退回「同一时刻只能一个人改这个文件」的工作方式—— 团队效率会被严重拖慢，而且大家会因为「懒得等锁」而互相干扰。版本控制的优势正在于「大家同时改，最后合并」，别把它关掉。
配置文件 / 项目文件 不要锁 虽然偶尔会因为格式问题产生冲突，但冲突了慢慢合就行。锁了会让大家没法同时推进工作。
锁是有生命周期的，用完记得释放

锁不是「设置一次就一直有效」的开关，它是一条有开始、也该有结束的记录。 加锁 → 改文件 → 提交 → 释放锁，这才是一个完整的循环。

忘记释放的后果很直接：

  • 这个文件一直锁在你名下，别人想改也改不了，而且没人知道你要锁到什么时候。
  • 同事们会来问你、等你，或者干脆绕开这个文件去改别的——进度就这么被拖住了。
  • 更糟的是你自己也忘了。过了两周别人受不了去抢锁，你可能才发现自己还锁着好几个文件。
  • 锁会跟着工作副本走。如果你换了一台电脑、或者重新检出， 之前锁的文件仍然挂在服务器上——它不会因为你本地的工作副本删了而自动消失。

几个实用习惯：

  • 提交后就顺手释放。别想着「等会儿再放」——等会儿你就忘了。
  • 提交对话框里的「保留锁」选项，默认别勾。 那个选项的意思是「提交完继续锁着」——只有你确实还要接着改才需要它。
  • 备注里写上大概的时间。万一你真忘了，别人看到「大约两小时后释放」至少心里有底，知道该等还是该找人。
  • 定期自查。可以浏览一下仓库，看看有没有数量异常多的锁项还挂在自己名下，顺手清理掉。尤其是休假前、换任务前。
加锁这一节的要点
  • 二进制文件只能靠锁，不能靠合并——同时改必然有一方的工作被覆盖。
  • 加锁：右键 → TortoiseSVN → Get lock... → 写清备注 → Get。 动手改之前就锁，别改完才想起来。
  • 解锁：右键 → TortoiseSVN → Release lock。提交完就释放，别拖着。
  • 自动锁：给文件设上「默认只读」的属性，检出即只读，逼你先加锁再改，加锁后自动变可写。用它解决「总忘记加锁」的问题。
  • 源码不要加锁——那是自废武功，会让整个团队没法并行干活。
  • 抢锁是破坏性操作，先沟通、再考虑，别当成常规手段。

到这里，SVN 的日常操作就基本走完一轮了： 从检出、更新、提交，到冲突处理、分支、合并、忽略、属性、加锁。 把这几节练熟，团队协作里九成以上的场景都能应付。
