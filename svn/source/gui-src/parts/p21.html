21备份与恢复：图形界面操作

版本库里装着团队全部的代码和全部的历史——每一行代码是怎么来的、谁在什么时候改的、当时为什么改，都只存在这一个地方。 服务器硬盘坏了、误删了仓库、中了勒索病毒，丢的不只是当前代码，而是过去几年所有的改动记录。 这一节在 VisualSVN Server Manager 里把备份配起来，全部是点鼠标。

关于备份的三个基本认知
  • 备份必须自动。靠「记得手动点一下」的备份，等于没有备份——忙起来一定会忘。正确做法是配一个每天自动跑的定时任务，配一次管几年。
  • 备份必须在别的地方。和仓库放在同一块硬盘、同一台机器上的备份，硬盘一坏就一起没了，起不到保护作用。
  • 备份必须验证过。没恢复过的备份文件，你并不知道它是不是完整的。这一点本节最后会用红框专门强调。

手动备份一个仓库

平时靠定时任务，但遇到「我要改一下仓库结构」「准备升级服务器」这类操作前，手动做一次备份最踏实。整个流程就是一个向导。

BACKUP手动做一次仓库备份
在仓库节点上右键 左边树里 Repositories 下面找到要备份的那个仓库，在它上面右键。备份是一个一个仓库做的，没有「一键备全部」的按钮——仓库多的时候，用定时任务一次建多条更省事。
走 All Tasks 子菜单 点 All Tasks → Backup Repository...。仓库相关的运维操作（备份、恢复、校验）都收在这个子菜单里，找不到某个运维功能时先翻它。
选择备份类型 向导里有备份方式的选择。第一次备份、或者准备做重大改动前，选全量；日常的例行备份可以选增量，省空间也更快。两种方式的差别见下面的对比表。
选择备份文件存到哪 在 Backup File Name 里选目标路径和一个文件名，强烈建议指到另一块硬盘、另一台机器或网络存储上，不要留在仓库所在的盘上。
完成，看进度 点 Finish 后会有进度显示。仓库大的话可能要跑一会儿，这期间别去关窗口或重启服务器。完成后到目标路径确认文件存在、大小正常。
做重大改动前，先手动备一次再动手 要改仓库名、迁移服务器、升级版本之前，先手动全量备份一次，把它复制到别的地方，再进行操作。这一步花几分钟，万一出事能救回来。

两种备份方式怎么选

备份方式耗时占用空间适用场景
全量备份
Full		 慢，随仓库总大小增长，大仓库可能几十分钟 大，每次都是一份完整拷贝 恢复最省事——一个文件就是全部。适合：第一次备份、重大改动前、每季度做一次留底、给异地存储发一份。
增量备份
Incremental		 快，只处理上次之后的改动，日常几乎无感 小，只存变化的部分 适合：每天自动跑的例行任务。缺点：恢复时要按顺序把增量一个个叠上去，所以需要一个可靠的全量做基准。
推荐的组合：全量打底 + 增量日常

两种不是二选一，而是搭配着用：每周（或每月）一次全量作为基准放在异地存储上；每天一次增量，攒到下一个全量为止。恢复时先恢复最近一次全量，再把之后的增量按时间顺序叠上去，就能回到最近的状态。

如果团队规模不大、仓库也就几百兆，那全量每天跑一次也完全可以接受，还省去叠加的麻烦。按你们的实际体积定。

配置定时备份，让它自己跑

这才是备份真正起作用的方式。配好之后服务器每天自动备，你不需要记得任何事。

JOB建一个每天自动备份的任务
在 Jobs 节点上右键 左边树里找到 Jobs（定时任务节点），右键 → New → Backup Job...。如果里面已经有别的任务（比如日志清理），也可以在这里一起管理。
选择要备份哪些仓库 任务对话框里勾选要包含的仓库，可以一次勾多个——这样一条任务就能把整个团队的仓库都覆盖掉。新加仓库后记得回来把它也勾上。
设置备份目标位置 指定一个和仓库不同盘、最好是网络位置的目录。网络共享路径、外接硬盘、NAS 都可以。这一项是整节里最关键的一次选择，位置选错，后面全白做。
选择备份类型（全量还是增量） 日常任务建议选增量；如果你希望每个备份文件都能独立恢复，就选全量，代价是每天多花些时间和空间。
设定运行时间 安排一个没人用服务器的时间点，比如凌晨两三点。选好开始的日期和重复周期（每天 / 每周）。避开大家提交的高峰，备份更完整、也不影响别人。
完成，然后第二天来检查一次 任务建好后会出现在 Jobs 下面。第二天务必回来确认它真的跑了、文件真的生成了——配好就不管，是备份最常见的翻车方式。
顺便考虑：老备份怎么清理 备份只增不减，半年就把盘塞满了。定一个保留策略（比如本地留 7 天、异地留 30 天），按策略定期把过期的删掉。可以在任务属性里设置保留份数，也可以人工周期性清理。

从备份还原一个仓库

还原的时机：硬盘出问题、仓库被误删、或者你想把某个历史状态在一台测试机上复原出来看看。整个操作也是向导。

RESTORE把仓库从备份里恢复出来
在 Repositories 节点上右键 注意是在 Repositories 这一层，不是在某个具体仓库上——因为你要恢复的这个仓库可能已经被删掉了，它下面根本没有对应的节点。
走 All Tasks → Restore Repository 点 All Tasks → Restore Repository...，弹出恢复向导。
选择备份文件 浏览到存放备份的目录，选中那个备份文件。是增量备份的话，要按顺序把全量和后续增量都挂上，才能在向导里还原到想要的状态。
给恢复出来的仓库起名 如果原仓库还在、你只是想看看历史状态，一定要换个不同的名字（比如 MyProject-restore）。重名会把现有的仓库覆盖掉，那就从「摔了一跤」变成「伤筋动骨」了。
恢复完成后在仓库浏览器里验一遍 恢复完，右键新仓库 → Repo-browser，展开看看目录结构对不对、日志列表里版本号到不到你预期的位置。能看到完整的提交历史，才算真的恢复成功。
确认无误后再处理旧的 如果是为了替换损坏的仓库，先让新的跑通、同事能正常更新提交，确认几天之后，再决定要不要清理旧的那份。顺序永远是「先确认新的好用，再删旧的」。

恢复之后：怎么确认「真的恢复了」

恢复向导点完 Finish 不代表事情结束。必须打开仓库浏览器亲眼验一遍——这是区分「备份文件存在」和「数据真的可用」的唯一办法。

◈仓库浏览器（Repo-browser）：恢复后验收主战场REPO-BROWSER
恢复完成后，右键新仓库选 Repo-browser，就打开这个窗口。它是直接读服务器上的仓库，不依赖你本地任何工作副本，所以最适合做验收。三块内容挨个看：

① 左栏：目录树
从仓库根往下展开，确认 trunk / branches / tags 三个目录都在，位置没串。图里还带了一个 Bookmarks 折叠项，那是你自己收藏的地址，和仓库数据无关。
如果这里少目录、或者层级明显不对，说明恢复没成功。

② 右栏：文件列表
四列是 File（文件名）、Extension（扩展名）、Revision、Author（最后修改者）、Size（大小）、Date（时间）。重点看 Revision 和 Date 两列——它们能反映每个文件最后一次改动是什么时候。文件名后面带 / 的是文件夹，可以用工具栏按钮切换成「每个文件夹占一行」的视图。

③ 顶部：地址栏与版本框
左边是当前路径，右边 Revision 默认显示 HEAD，表示看最新状态。你也可以把它改成某个具体的版本号，或直接点 Show log，去看完整的提交历史。

验收时具体核对这几项：
核对项在哪里看合格标准
版本号到没到位 点 Show log，看最大的版本号 应该等于备份那一刻的版本号。差得远 = 恢复了旧的备份
提交历史完不完整 日志列表往下翻，看最早的版本 能一直翻到仓库创建时的第一个版本，说明历史没断
目录结构对不对 左栏目录树展开各级 trunk / branches / tags 齐全，深层目录都在
最近一次提交在不在 日志列表第一条 时间、作者、日志内容都对得上。少了最后几次 = 增量链断了
能不能正常检出 换台机器，用 SVN Checkout... 检验出一次 能完整拉下来、文件和预期一致。这一步最有说服力
能不能正常提交 在检出的工作副本里改个文件、提交一次 提交成功。能写才是真的活的仓库
验收口诀：能看、能检、能提

恢复一个仓库到底行不行，三步就能确认：

  1. 能看——在 Repo-browser 里能看到完整的目录和日志历史。
  2. 能检——在另一台机器上把代码完整检出下来。
  3. 能提——往里面提交一次，服务器正常接受。

三步都过，这次恢复才算真的成功。只做了第一步就宣布「恢复完成」，是运维里最常见的自欺欺人。

一套够用的备份策略
  • 本地留 7 天——服务器旁边的另一块盘或 NAS。出事当天就能就近恢复，速度最快。
  • 异地留 30 天——另一栋楼、另一个机房，或者云端存储。这一层防的是「机器连同备份一起没了」：火灾、被盗、勒索病毒加密整个网络。
  • 每季度做一次恢复演练——建一个测试仓库，从备份真的恢复一次，看看能不能打开、历史完不完整。这一步最能暴露问题：备份文件损坏、路径写错、权限不对，都会在这时候现出来，而不是在真出事那天。
  • 备份文件不要和生产环境用同一套账号密码——勒索病毒专门找有写权限的共享目录下手。
没验证过能恢复的备份，等于没有备份

这句话在运维圈被反复讲，是因为它永远在发生：

  • 任务配了两年，从来没人打开过那个目录——结果路径早就失效了，一个文件都没生成。
  • 每天生成的文件看着都在，实际上文件是空的或者中断的，恢复时才发现打不开。
  • 备份是好的，但恢复步骤没人会。真出事那天，全公司盯着你研究向导怎么点，压力比平时大一百倍。
  • 增量备份链某一天断了，后面所有的增量都叠不上去，只能退回最后一次全量。

所以：把「每季度恢复演练」当成一条硬性任务写进你们的运维清单，谁负责、什么时候做，写清楚。十五分钟的演练，抵得过事后的一切努力。

备份做完，你应该能回答这四个问题
  • 备份在哪？给出确切路径，且这个位置和仓库不在同一块盘上。
  • 多久备一次？有一条每天自动跑的定时任务，并且你验证过它真的跑了。
  • 保留多久？本地多少天、异地多少天，谁来清理，过期备份怎么处理，都有约定。
  • 怎么恢复？自己亲手恢复过一次，知道从哪个菜单点、选哪个文件、大概要多久。

四个都能答上来，你的团队就比较稳了。答不出来的那个，就是下一步要去补的。
