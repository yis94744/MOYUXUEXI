10冲突处理：两人改了同一处

两个人同时改同一个文件的同一行，后提交的那个人就会撞上冲突。 这一节讲清楚冲突长什么样、怎么一步步解决，以及怎么让它少发生。

冲突是正常现象，不是错误

很多人第一次看到红色警告就以为「我把项目搞坏了」。其实并没有——冲突只说明一件事： 你要改的这段内容，别人也改过了，SVN 不知道该听谁的。

它不删文件、不覆盖代码，只是把两种改法都保留下来，交给你决定。 这是 SVN 在保护你的工作：如果它自作聪明选一个，你可能就丢了别人的改动。

处理冲突是 SVN 使用中的常规动作，每个团队每周都会遇到几次。

冲突是怎么产生的

起因冲突发生的典型经过
你和同事各自更新到了同一个版本 假设都是 r1200。此时你们手上的文件完全一样。
同事先改并提交 他改了文件里的某一行，提交成了 r1201。此时服务器上已经是新版，但你本地还是旧的 r1200。
你又改了同一处，然后更新 你改的是同一行（或紧挨着的几行），还没提交就点了 SVN Update。
撞车点就在这：SVN 想把 r1201 合并进你的工作副本，却发现这一处你和你同事各写了一个版本，它没法自动挑。
更新对话框里出现红色提示 进度窗口会用亮红色把那个文件标出来，提示这个文件处于冲突状态，需要人工处理。其他没撞车的文件照常更新成功，只有一个文件被拦下。
哪些情况会撞车，哪些不会
  • 会冲突：改同一行、改紧邻的几行（SVN 划定的同一区块）。
  • 通常不冲突：两人改同一个文件，但改的是相隔较远的不同位置——SVN 能自动把两边改动合并到一起，你根本不会察觉。
  • 不一定冲突但要注意：一个改内容、另一个删文件或改名——这会产生树冲突，见下文。

结论：冲突和「文件被几个人改」没关系，只和「改的位置是否重叠」有关。

冲突长什么样

信号一：更新对话框里的红色文件名
  • 更新进度窗口里，冲突的文件名用亮红色显示，和其他文件明显不同
  • 窗口底部的统计信息里会出现 Conflicts 字样和数量
  • 如果一眼扫过去是绿的，说明这次更新很干净，没事
信号二：文件角标变成黄底红叹号
  • 资源管理器里这个文件的图标变成 黄色底 + 红色叹号
  • 这是冲突的专属标记，和普通的「已修改」红叹号不一样
  • 只要角标还是黄的，就说明冲突还没解决，提交会被拦住
Conflicted 黄底红叹号。看到它就必须处理，处理完才会变回绿色对勾。
Modified 普通的红色叹号，只表示「改了还没提交」，不会拦你提交。
Added 蓝色加号，新增待提交的文件。
Normal 绿色对勾，本地和服务器一致，一切正常。

处理流程：五步解决一个冲突

CONFLICT从发现到提交
发现冲突：更新时看红色文件名 看到亮红色的文件，先把它的名字记下来。更新可以继续完成，冲突文件会停在冲突状态等你处理。
打开冲突文件，找到标记 用你平时的文本编辑器打开它（VS、VS Code、记事本都行）。在冲突的位置会看到成对的标记行，它们把两个版本清楚地隔开，见下方表格。这些标记是 SVN 加进去的，不是谁的手误。
手工解决：决定这段代码到底要什么 读完两段内容，自己写出最终正确的版本，并且把那些标记行全部删掉。
这一步需要你动脑子：不是简单选一边，有时候两边各有可取之处，要把它们合成一个正确的版本。拿不准就问同事——对方是谁，日志里一查就知道。
告诉 SVN「已解决」 编辑完保存，回到资源管理器，对着这个文件右键 → TortoiseSVN → Resolved。
这一步不能省：文件内容改好了，但 SVN 还不知道你已经处理完，角标会一直是黄的，提交也会被拦。点了它，角标才变回绿色。
提交，并在说明里写清楚 SVN Commit... → 在 Message 里写明白，比如 解决 XX 模块冲突：保留双方的校验逻辑。如果和同事商量过，顺手在群里说一句，让他更新后确认一下你合并得对不对。

看懂冲突文件里的三种标记

冲突文件里会出现三组标记行，它们像书签一样把文件分成几段。认识这三行，你就知道该删什么、该留什么。

标记行含义你要做什么
<<<<<<< .mine 从这里开始，是我的改动 它下面紧跟的内容，是你本地改成的样子。.mine 就是「这份文件的我的版本」的意思。
======= 分界线 它把上面的「我的」和下面的「别人的」分开。这行本身没有任何代码含义，是纯标记。
>>>>>>> .r123 别人的改动到这里结束 这行上面的内容，是服务器上那个版本的样子。后面的数字说明它来自哪个版本，想查是谁改的，就拿这个版本号去 Show log 里搜。
冲突文件看起来是这样
  • 标记行包裹起来的，就是两边打架的那一段
  • 从上到下读顺序是：标记 → 我的改动 → 分界线 → 别人的改动 → 标记
  • 一个文件里可能有好几组这样的标记，每一组都要单独处理
  • 标记之外的内容没冲突，不用动
处理时你要做的
  • 逐组查看，决定最终保留哪些行
  • 把三行标记全部删掉——包括 <<<<<<<、=======、>>>>>>>
  • 结果应该是一份语法正确、能正常编译的普通代码
  • 保存 → 右键 Resolved → 提交
格式一定要核对

处理完冲突后，一定要把文件打开再通读一遍，尤其确认两点： ① 标记行确实一行不剩；② 拼起来的内容语法完整（比如大括号成对、语句没被截断）。

冲突区域往往在代码块的中间，少删一行标记会让整段代码无法编译； 多删一行代码则可能悄悄改了逻辑，编译能过但运行出错——这种问题最难查。

用对话框解决：合并冲突对话框

如果不想手工读文件里的标记，也可以让 TortoiseSVN 弹出一个专门的对话框来处理。 在冲突文件上右键 → TortoiseSVN → Edit conflicts，就会出现它。

◈合并冲突对话框（点击图可放大）Merge Conflict Callback
这个对话框把「两个版本」摆出来，每个按钮就是一种态度。按钮名字都是英文，但意思很直白：

• Postpone——先放着，稍后再处理。你还没想清楚、或者要先问同事时用它， 对话框关掉，文件保持冲突状态，角标仍是黄的。新手看到一堆按钮时先点这个，最安全。
• Accept base——用「基础版本」。也就是放弃你这次的改动， 回到你俩开始改之前的那个原始内容。
• Accept incoming——用别人的版本。同事的改动留下，你这一处被覆盖。
• Reject incoming——拒绝别人的版本。你这一处保持自己的写法。
• Accept incoming for conflicts / Reject conflicts——批量处理： 一次把所有冲突处都按「接受对方」或「拒绝对方」处理完。文件里冲突很多、而且你确定一律听某一方的时候， 用这两个最快。
• Mark as resolved——声明已经解决完了。相当于右键菜单里的 Resolved， 点完角标才会变绿。
• Edit——打开编辑器手工改。想自己逐行斟酌时用它， 会跳到合并工具或文本编辑器。

用法建议：冲突很少时，直接按上面几个按钮一个个决定；冲突多且交织在一起时， 点 Edit 用合并工具更省心（见第 11 节）。

树冲突：不是内容打架，是「文件本身」打架

还有一种冲突叫树冲突（Tree conflict）。它和内容无关，而是文件或文件夹的存在状态对不上： 一方改了文件，另一方把文件删了或者改名了，SVN 不知道该保留哪个。常见情形有：

  • 你改了文件，同事把这个文件删了——你的改动无处可去。要么接受删除（放弃你的改动），要么把文件恢复回来。
  • 你改了文件，同事把它改名了——你的改动落在了「旧名字」上，而服务器上只剩「新名字」，需要把改动挪到新名字的文件上。
  • 两个人都改同一个文件的文件名/位置——移动方向不一致，SVN 无法自动决定最终路径。
  • 你要提交一个新文件夹，服务器上已经有人建了同名文件夹——路径撞车，需要决定用哪一份。
  • 你在改一个文件夹里的东西，同事把整个文件夹删了——涉及整棵树，处理时通常要连带决定里面所有文件的去向。
◈树冲突对话框Tree Conflict Callback
树冲突的对话框和内容冲突长得很像，但它问的问题完全不同：内容冲突问的是「这段文字用谁的」， 树冲突问的是「这个文件/文件夹到底还要不要」。

对话框会先用文字描述冲突的性质——比如「本地修改了文件，但该文件在仓库中已被删除」， 这一段说明一定要读完，它直接告诉你选择的分量。

然后同样是一组按钮，常见的是接受对方的处理（删除/改名）或拒绝对方的处理（把文件恢复回来）。 如果拿不准，先点 Postpone 放着，去和同事确认清楚再决定—— 树冲突往往涉及「这个文件到底该不该存在」的判断，问一句比猜一个省事得多。
避免冲突的最佳实践
  1. 开工第一件事：更新。每天打开电脑先 SVN Update，拿到同事昨晚的改动再动手。
  2. 改之前先更新。准备改一个文件前，单独对它更新一次。尤其是你打算大改的文件——先把最新的拿到手。
  3. 改完尽快提交，小步提交。改了三天再提交，别人早就改过同一块了。一次提交只干一件事，提交越勤，撞车窗口越小。
  4. 提交前再更新一次。把冲突留给自己处理，而不是让下一个更新的人替你承担。
  5. 别在公共文件上做长时间实验。要试一个新方案，先问一句，或者建个分支自己折腾（见第 12 节）。
  6. 一次别改太宽。顺手把一个文件整体重排格式，会让别人所有改动都撞车；这类改动单独提交，并在说明里写清楚。
新手最常犯的三个错误
  1. 忘了删冲突标记就提交。标记行是 SVN 加的，不是代码的一部分。留着它们会让程序直接编译失败， 或者把奇怪的字符带进最终产品。做法：解决完先搜一遍 <<<<<<< 这个符号，确认一个都不剩，再提交。
  2. 文件改好了，却忘了点 Resolved。内容是对的，但 SVN 还认为这个文件处于冲突中， 角标仍是黄底红叹号，提交会被拦住。看到这个角标就知道：还差一步「已解决」没做。
  3. 用手工删除文件的方式「解决」冲突。直接在资源管理器里按 Delete 删掉冲突文件、 或者删掉 .mine / .rXXX 之类的辅助文件，只会让 SVN 的状态更加混乱—— 它以为文件还在，但文件已经不见了。正确做法：老老实实走「编辑 → Resolved → 提交」这条流程； 真要删文件，用 TortoiseSVN → Delete，让 SVN 知道你在删什么。
处理冲突的标准顺序（记这五步就够了）

① 看红色文件名 → ② 打开文件读标记 → ③ 写出最终版本并删掉标记 → ④ 右键 Resolved → ⑤ Commit。

整个过程里，只有第 ③ 步需要动脑子，其余都是点几下鼠标。拿不准第 ③ 步怎么选时， 去看 Show log 里那次提交的说明和作者，直接去问人——这是最快也最不容易出错的解法。
