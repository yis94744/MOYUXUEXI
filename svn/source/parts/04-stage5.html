11分支的本质：一次廉价的复制

如果你只从 Git 过来，SVN 的分支概念会让你困惑三分钟，然后突然豁然开朗。 核心只有一句话：SVN 里的分支就是一个普通目录，复制它只花 0 字节。

「复制」在 SVN 里意味着什么

传统理解里，复制一个 5GB 的目录要占 5GB 空间、花几分钟。 但在 SVN 里，svn copy 创建分支是瞬间完成的，仓库几乎不增长。为什么？

◈图 11-1　廉价复制：分支为什么不占空间Cheap Copy
一句话总结：SVN 的分支就是仓库里多了一个目录，内容是原目录的「快捷方式式引用」。 这解释了两个常见疑问：① 为什么建分支要联网，因为要在服务器上提交一次； ② 为什么分支多了仓库也不膨胀，因为没改的文件共享同一份数据。
分支和标签，在 SVN 里技术上完全一样

这是一个必须点破的事实：SVN 的 tag 不是特殊对象，它就是一个用 svn copy 复制出来的目录。 和 branch 唯一的区别是——约定上你认为它是「发布快照」而不该再改。

SVN 不会阻止你往 /tags/v1.0/ 里提交代码，它照样接受。 想真正实现「标签只读」，得靠 authz 权限控制（第 19 节会给完整配置）。

创建分支

bash建分支的五种写法
# 【推荐】服务端直接复制，一次提交就完成，不需要工作副本
svn copy https://svn.example.com/repo/trunk \
         https://svn.example.com/repo/branches/feature-login \
         -m "从 trunk 创建 feature-login 分支"

# 【更短】在工作副本内用 ^ 表示仓库根
svn copy ^/trunk ^/branches/feature-login -m "创建分支"

# 【从历史版本建分支】—— 修复老版本的 bug 时很常用
svn copy ^/trunk@520 ^/branches/hotfix-crash -m "基于 r520 创建热修分支"

# 【本地复制 + 提交】需要工作副本，多一步
cd wc
svn copy ^/trunk ^/branches/feature-local
svn commit -m "创建 feature-local 分支"

# 【直接用 mkdir 建空分支】（不推荐，没有历史关联）
svn mkdir ^/branches/empty-branch -m "建空分支"

# 验证分支建好了
svn list ^/branches

switch：一个工作副本切成两个分支

svn switch 是 SVN 里非常巧妙的一个命令：它保持本地文件不动， 只把「这个目录对应服务器上哪个 URL」这件事改掉，然后把差异同步过来。

bashswitch 的用法
# 切到分支
cd wc
svn switch ^/branches/feature-login

# 切完整 URL（等价）
svn switch https://svn.example.com/repo/branches/feature-login

# 切回主干
svn switch ^/trunk

# 切到某个历史版本（不是切分支，是把时间指针往回拨）
svn switch ^/trunk@520

# 只切换某个子目录（局部切换）
svn switch ^/branches/feature-login/src src/

# 常用选项
svn switch --ignore-ancestry ^/other-branch    # 忽略祖先关系直接覆盖内容
svn switch --relocate OLD_URL NEW_URL           # 仓库搬家了，改 URL 而不改内容
svn switch --accept postpone                    # 冲突策略

# 验证当前在哪个分支
svn info --show-item relative-url
svn info | grep URL
实测输出：switch 到分支再切回

$ svn info | Select-String 'URL|Relative URL'

Committing transaction...
Committed revision 6.       ← 提交进了分支，trunk 完全不受影响

# 切回主干（本地未提交的改动会自动带过去，可能产生冲突）
$ svn switch file:///E:/repo/trunk

$ svn info | Select-String 'URL'
URL: file:///E:/repo/trunk
switch 前务必把手头改动处理掉

如果工作副本里有大量未提交的修改，直接 switch 会让 SVN 试图把这些改动带到目标分支上。 如果两边差异大，会产生一堆莫名其妙的冲突。

正确姿势：switch 之前先 svn status 确认干净， 或者 svn commit / svn revert 处理掉。

另外，实测证实：工作副本处于「混合版本」状态时执行 merge 会直接被拒绝 （E195020: Cannot merge into mixed-revision working copy）， switch 之后紧接着 merge 也容易踩这个坑，记得先 svn update 拉平。

13合并全流程与 mergeinfo 机制

合并是 SVN 里最容易出错、也最能体现集中式设计的部分。 它的核心难点在于：SVN 必须记住「哪些提交已经合过了」，否则每次合并都会重复应用同样的改动。 这个记忆装置叫 svn:mergeinfo。

mergeinfo：SVN 怎么知道该合什么

◈图 13-1　mergeinfo 属性：合并的「记账本」Mergeinfo
核心记忆点：svn:mergeinfo 是一个目录级属性， 格式是 /路径:版本区间。它不是给人看的，是给 svn merge 自己看的。 你不需要手动维护它，但你必须理解它，才能解释「为什么这次合并什么都没做」。

合并的标准流程（实测走通）

MERGE从分支合并回主干的六步
① 切到目标分支（要合进哪里） cd wc-trunk && svn switch ^/trunk
② 更新到最新 —— 这一步绝对不能省 svn update。 实测教训：如果工作副本处于混合版本，merge 会直接报 E195020: Cannot merge into mixed-revision working copy 拒绝执行。
③ 确认工作副本干净 svn status 应该无输出。有未提交改动就先 commit 或 revert。
④ 先干跑一遍，看清楚要合什么 svn merge --dry-run ^/branches/feature-login。 --dry-run 不会改动任何文件，只告诉你「将要做什么」。
⑤ 正式合并，处理冲突 svn merge ^/branches/feature-login。 遇到 C 冲突就按第 10 节的方法解决；处理完 svn resolve。
⑥ 提交 —— mergeinfo 就是这一步写进去的 svn commit -m "合并 feature-login 分支到 trunk"。 不提交，这次的合并记录（mergeinfo）就不会保存，下次会重复合并。

merge 的四种用法

bashmerge 进阶
# ---- 用法 1：同步分支（最常用）----
# 从 源URL 合并到 当前目录，SVN 自动算区间
svn merge ^/branches/feature-login

# ---- 用法 2：只合并特定的几个提交 ----
svn merge -c 5,7,9 ^/branches/feature-login        # 挑着合（cherry-pick）
svn merge -c -10 .                                # 反向合并（撤销，见第 9 节）

# ---- 用法 3：合并指定版本区间 ----
svn merge -r 5:9 ^/branches/feature-login
svn merge -r 9:5 .                                # 反向区间 = 撤销

# ---- 用法 4：两个 URL 之间的差异，不涉及祖先关系 ----
svn merge ^/trunk ^/branches/other-branch .
# 甚至可以把两个不相关的目录的差异打进当前目录
svn merge --ignore-ancestry ^/trunk ^/vendor/lib .

# ---- 关键选项 ----
svn merge --dry-run ^/branches/f            # 预演，不改动任何文件（强烈推荐先用）
svn merge --reintegrate ^/branches/f        # 1.8 前的「重新整合」，把分支整个合回并结束它
svn merge --accept postpone ^/branches/f    # 冲突策略
svn merge --record-only ^/branches/f        # 只记 mergeinfo，不改文件（高级技巧）
svn merge --depth infinity .                # 递归深度
svn merge --ignore-ancestry                 # 忽略祖先关系，纯内容 diff 后覆盖
svn merge -x --ignore-space-change ^/b      # 传给内部 diff 的参数
--dry-run 是保命选项

合并是个复杂操作，永远先跑 svn merge --dry-run。 它会完整地输出「将要做什么」（U / C / G / D 标记），但不修改任何文件。

如果 dry-run 的输出里出现你意料之外的 C，说明这次合并会冲突—— 先去了解一下为什么，别硬着头皮上。

merge 冲突的辅助文件命名与 update 不同

实测发现的细节差异：

场景辅助文件命名标记里的三栏
svn update 冲突 .mine / .r2 / .r3 <<<<<<< .mine ／ ||||||| .r2 ／ >>>>>>> .r3
svn merge 冲突 .working / .merge-left.r4 / .merge-right.r7 <<<<<<< .working ／ ||||||| .merge-left.r4 ／ >>>>>>> .merge-right.r7

含义完全对应：.working = 我的，.merge-left = 共同祖先，.merge-right = 要合进来的源。 解决方式和 update 冲突一模一样，只是文件名不同，别被绕晕。

# 【删除标签】打错了

用 authz 强制标签只读

前面说过 SVN 不会阻止你改标签。想真正锁死，靠 authz 权限文件—— 这是 SVN 相对 Git 的一个优势：目录级权限。

iniconf/authz　标签只读配置
[groups]
admins = alice, bob          # 只有这两个人能改标签
devs   = carol, dave

# 仓库根：默认无权限，逐条放开
[/]
* =
@admins = rw

# 主干：开发全员可读写
[/trunk]
@devs = rw
@admins = rw

# 分支：开发可读写
[/branches]
@devs = rw
@admins = rw

# 标签：所有人只读，只有 admins 能写
[/tags]
* = r
@admins = rw

发布管理的实践建议

标签命名要能排序

用零填充让版本号能按字典序正确排序：

✓ v1.0.0 / v1.0.1 / v1.10.0
✗ v1 / v1.2 / v1.10
   （字典序里 v1.10 < v1.2，会排错）

语义化版本 v主.次.修 是目前最通用的约定。

标签里别再提交

一旦打了标签，就该视为冻结的化石。发现 bug 怎么办？

  • 从该标签创建修复分支：svn copy ^/tags/v1.0.0 ^/branches/hotfix-1.0.1
  • 在分支上修，打完补丁再打新标签 v1.0.1
  • 这样 v1.0.0 永远是「当时发出去的那份」，可复现
发布构建的标准脚本片段
bash从标签构建发布包
#!/usr/bin/env bash
# 从指定标签导出并构建发布包
set -euo pipefail

TAG="${1:-v1.0.0}"
REPO="https://svn.example.com/repo"
BUILD="./build-${TAG}"

# export 而非 checkout：产物里不含 .svn，可直接打包
svn export --force "${REPO}/tags/${TAG}" "${BUILD}" \
  --username build-bot --password "${SVN_PASS}" --non-interactive

# 记录构建来源，便于事后追溯
cat > "${BUILD}/BUILD-INFO.txt" <<EOF
tag          : ${TAG}
built_at     : $(date -Iseconds)
built_by     : $(whoami)
svn_revision : $(svn info --show-item revision "${REPO}/tags/${TAG}")
EOF

tar czf "${TAG}.tar.gz" -C "${BUILD}" .
echo "发布包已生成: ${TAG}.tar.gz"
