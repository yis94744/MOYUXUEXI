22补丁与导出：不走仓库传代码

绝大多数时候，代码的流转都是「提交 → 更新」这一条路。但总有些场合不适合走仓库： 你还没有账号、只想给同事看一处改动、要给客户发一份干净的代码、要把一批现成的文件一次性放上服务器。 这一节讲四个不依赖提交流程的传代码方式：补丁、应用补丁、导出、导入。

四种方式的定位

补丁（Patch）——把你的改动变成一个很小很轻的文本文件发给别人。对方能看到你改了哪几行、再决定要不要采纳。适合「我还没有提交权限」或者「这个改动先给别人过一眼」。

导出（Export）——从仓库里拷出一份干净的代码，不带任何 SVN 痕迹。适合交给客户、打包发布、部署上线。

导入（Import）——把一个现成的目录一次性放上仓库，不需要先检出。适合把老项目、外包交付的文件搬进版本库。

检出（Checkout）——本篇前面都在讲的那个，带版本控制能力的完整工作副本。放在这里一起对比，是因为它和 Export 长得像、用途完全不同。

创建补丁：把改动变成一个文件

补丁文件本质上是一段记录了差异的纯文本：「第几行原来是这个、改成了那个」。它只有几 KB，用邮件、聊天工具、工单系统都能发，对方拿到后一键应用。

PATCH把手上的改动做成补丁
先确认你改了什么 对着工作副本文件夹右键 → SVN Check for modifications，看看列表里有哪些文件是「已修改」。做补丁之前先看清楚范围，别把调试用的临时改动也包进去。
在文件夹上右键，打开创建补丁 在你改过的文件夹上右键 → TortoiseSVN → Create patch...。也可以只对单个文件做——右键那个文件用同一个命令。想一次包含多个文件，就在它们的共同父文件夹上操作。
在文件列表里勾选要包含的改动 弹出的对话框里列出了所有有改动的文件，每个前面都有勾选框。只勾要做进补丁的那些，不想给别人的（本地配置、调试代码）把勾去掉。
保存成一个 .patch 文件 点 OK 后选择保存位置和文件名。对话框里能直接选择保存成 .patch 或 .diff 格式，内容基本一样，挑一个就行。把它和你的说明一起发出去。
发的时候附上说明 补丁文件本身不包含「为什么改」，只有「改了什么」。发出去的时候一定配一句话讲清楚背景，否则对方只能靠读代码猜。好的做法是在聊天里写清：改哪个模块、解决什么问题、要按哪个版本应用。
补丁最适合的三个场景

① 还没有提交权限。新人、外包、临时支援的同学，改完做成补丁发给负责人，由有权限的人应用后再提交——比开账号更轻，也更安全。

② 改动需要先被评审。先做成补丁发给同事，他看清楚每一行再决定要不要收，相当于一次小型代码评审。

③ 环境对不上时的应急交付。对方那边的版本和你这边不完全一致，发整个文件夹不现实，一个只含差异的小补丁是最合适的载体。

应用补丁：把别人发来的改动合进来

APPLY把收到的补丁应用到工作副本
先更新到最新，再应用 对着工作副本右键 → SVN Update，把本地拉到最新。补丁是按行号定位的，如果本地代码和做补丁时的版本差太多，就可能对不上，提前更新能大幅降低失败概率。
在目标文件夹上右键，选择应用补丁 在你要应用改动的那个目录上右键 → TortoiseSVN → Apply patch...。应用位置要选对：补丁里记录的是相对路径，根目录选错了会提示找不到文件。
选中那个 .patch 文件 在文件对话框里浏览到补丁文件，选中打开。工具会立刻读一遍内容，把里面包含的文件列出来。
逐项预览再决定 列表里每个文件都能双击查看差异——这一步别跳过，你是在把别人写的代码放进自己项目，值得看一眼。不要的文件可以在勾选框里去掉。
点应用，然后检查结果 应用完成后回到资源管理器，看角标：被改过的文件应该变成红色叹号。打开文件通读一遍改动是否符合预期，再提交，并在 Message 里写清「应用自某某人的补丁」。
如果有文件提示失败、打了叉 说明这一处的上下文和本地对不上（对方改的那几行你这边已经变过）。这时会出现类似冲突的标记，处理方式和第 10、11 节完全一样：打开文件或用合并工具逐处决定，改完右键 Resolved。

导出：拿一份干净的代码出来

导出和检出长得非常像——都是从一个地址把代码拉到本地一个文件夹。区别就一个，但这个区别决定了它们的用途：导出出来的副本里没有 .svn 目录，也不受版本控制。

EXPORT从仓库导出一份干净代码
在要放导出结果的位置右键 可以是一个普通文件夹，不需要是工作副本——这一点和检出不同，检出是在空文件夹上做的。
选择导出命令 走 TortoiseSVN → Export...，弹出导出对话框。在 Repo-browser 里浏览仓库时，对某个目录或文件同样能找到这个命令。
填 URL 和导出目录 在 URL of repository 里填仓库地址（可以精确到某个子目录，比如只导出 /trunk），在下面的 Export directory 里选本地目标文件夹。
选择要导出哪个版本 对话框下方是版本选择。日常发布就保持在最新状态；如果要给客户发「和上次发布完全一致的那一版」，就选中具体版本号，或者按日期选。这是导出相比手工复制最大的价值：能精确定位到某一版。
确定，检查导出的内容 完成后打开那个文件夹：能看到代码文件，看不到任何 .svn 隐藏目录，文件图标上也没有绿色对勾之类的角标，这就是一份干净的代码。打包压缩发给客户即可。
◈Export 导出对话框Export
① URL of repository · 导出源——要从哪里导。可以填仓库根、某个项目、甚至具体到某一个子目录。它会自动记住你上次使用的地址，所以连续的发布操作会很快。

② Export directory · 导出到哪——本地目标文件夹。如果目标文件夹已经存在并且里面有东西，工具会提示覆盖，操作前先确认里面没有你要留的文件。

③ Export revision · 导出哪个版本——这是这个对话框里最容易被忽略、也最有价值的一项。默认是最新版本；下拉里可以选具体版本号或按日期。给客户的每一份交付，都建议在这里锁定成一个明确的版本号，这样将来出问题，你能一口气说清「发给客户的到底是哪一版」。

④ Revision 旁的 Show log 按钮——点它可以先打开日志看一遍，确认哪个版本才是你要的那一版，再回来填版本号。先看日志再选版本，比凭记忆填数字靠谱。

⑤ Export unversioned files too——如果导出源里混着一些尚未纳入版本控制的文件（灰色问号的那些），勾上这个能一并导出。一般不勾，因为没纳入版本控制的东西本来就不该出现在交付物里。

⑥ Omit externals——外部引用是指「从别的仓库目录挂过来的内容」。勾上它就不去拉这部分。大多数项目没有用到外部引用，这一项保持默认即可。
常见用途为什么用 Export 而不是直接复制怎么做
给客户发代码工作副本里混着你的本地改动、调试文件、.svn 目录，直接打包发出去既不专业也可能漏了不该给的东西。从仓库导出指定版本的 /trunk，压缩后发送。
打包发布发布要用服务器上确定的某一版，不能用手上正在改的本地副本，否则出的包和别人看到的代码对不上。导出发版那一版，再走你们的打包流程。
部署到服务器部署机器上不需要做版本控制，多出来的 .svn 目录只是累赘，还会暴露仓库地址信息。导出到部署目录，直接替换旧内容。
做备份留底想要一份「某个时间点长什么样」的快照，看得见摸得着。按日期导出，文件夹名带上日期，归档保存。

导入：把现成的目录一次放进仓库

手上有一堆早就写好的文件，没有任何版本历史，想一次性搬上服务器。这时不需要先检出——直接导入就行。

IMPORT把一个本地目录传进仓库
整理好要导入的目录 把要传的文件都放到同一个文件夹里，先去干净里面的临时文件、编译产物、.svn 残留目录。导进去容易，导错了要一个一个删。
在本地那个目录上右键 对着要上传的本地文件夹右键（不是在仓库上），走 TortoiseSVN → Import...，弹出导入对话框。
填仓库里的目标地址 这是最关键的一格：填的是它在仓库里的落脚点。想把内容放进主干，就填到 .../MyProject/trunk 这一层；填成仓库根的话，你文件夹里的东西会直接堆到 trunk 旁边，结构就乱了。
确认目标目录不存在 导入要求目标路径在仓库里还不存在（或者是个空目录）。先用 Repo-browser 看一眼，确认你要填的位置是干净的。位置已经用了，就先删除或换一个路径。
填提交说明，确定 在 Message 里写清这是什么——比如「导入项目初始版本（来自旧共享盘）」。导入会产生一次提交，这句话就是整份初始历史的第一条记录，值得写明白。
导入完，把本地目录变成工作副本 注意：导入只把文件传上去了，你本地这个文件夹还是没有版本控制的普通文件夹。想继续开发，就在旁边建一个空文件夹做一次检出，或者对着这个文件夹就地检出、把服务器内容拉下来对上。两种方式都要保证以后的工作副本是那个检出出来的。
◈Import 导入对话框Import
① URL of repository · 传到哪去——仓库里的目标位置。这一格填错是导入最常见的错误：填得太浅，内容会散落在不该在的层级；填得太深，你要的位置上会凭空多套一层文件夹。填之前先用 Repo-browser 把目标路径看一遍。

② Import Message · 说明文字——这次导入的提交信息。写得具体一点，将来别人查历史时能看懂这批东西的来历。

③ 上方的 Import directory 提示——它告诉你当前要从哪个本地目录导入内容。确认这个目录选对了：它是你在资源管理器里右键的那一个。

④ Include ignored files——默认情况下，被「忽略属性」排除掉的文件（编译产物、临时文件）不会被导进去，这正是你想要的。只有在你确实想把它们也传上去时才勾选。

⑤ Depth 深度选项——决定导进去多少层。一般保持完整递归（把整个目录树都传），除非你只想导入最外面一层。

⑥ 完成之后的进度窗口——导入会像提交一样显示一个进度列表，每个文件前面有 A（新增）之类的标记。看到全部完成、没有错误行，才算真的传上去了。
导入之后别忘了做检出

新手最容易卡在这里：导入成功了，于是在原来那个文件夹里继续改代码，结果怎么改都提交不了——因为那个文件夹从头到尾都不是工作副本，SVN 只是借用它把文件读了一遍传上去而已。

正确的做法二选一：① 在旁边建个新文件夹，对着仓库地址做一次检出，以后就在那个检出目录里干活（目录名可以带个后缀区分，比如 MyProject-wc）；② 就地检出——在那个文件夹上直接对同一地址做检出，把服务器上的内容拉下来覆盖对齐，之后它才变成真正的工作副本。

Checkout / Export / Import 到底差在哪

✗ 常见误解

「导出和检出不是一样吗？都是把代码拉到本地。」——不一样。导出的副本不受版本控制：没有角标、没有右键菜单、改完也不能提交。它只是一个快照。

「导出比检出快，那平时都用导出好了。」——导出出来的东西改不了、也更新不了，你在里面写一天代码，最后没有任何办法安全地送回服务器。

「导入就是把文件夹复制到服务器上。」——导入只会传上去，你本地那个文件夹不会因此变成工作副本，它在 SVN 眼里仍然是「外人」。

「补丁那么麻烦，不如直接把整个文件夹发过去。」——发整个文件夹对方没法看出你改了什么，也没法只收一部分，而且容易把本地乱七八糟的东西一起发出去。

✓ 正确理解

Checkout = 领一份带管控权的工作副本。你要长期在这里干活，改、更、提都在里面发生。

Export = 取一份定格的快照。它是一次性的交付物，给出去之后和仓库再无关系。用完就归档，不要在里面开发。

Import = 单向送货上门。只负责把本地的既成内容放上服务器，放完还要另外检出才能继续开发。

Patch = 只发送差异。体积小、可审阅、可挑选，是「没有权限」和「需要评审」两种场景的标准做法。

对比项Checkout 检出Export 导出Import 导入
方向仓库 → 本地仓库 → 本地本地 → 仓库
结果带版本控制吗带。有角标、有右键菜单、能提交更新不带。就是个普通文件夹上传后就结束了，本地不会因此被管控
有 .svn 目录吗每个文件夹里都有没有，完全干净不涉及（是往上传）
能选版本吗能，可检出某一版或某一分支能，而且强烈建议锁定版本不适用（就是当前这份内容）

用完还要做什么直接开始改代码别在里面改，它是交付物，改了就白导另外做一次检出，才能继续开发
我的目的该用哪个操作备注
我要长期在这个项目上写代码Checkout在空文件夹上做，得到工作副本。
我要给客户发一份代码Export选好版本号，导出的绝对干净。
我要打一个发布包Export从发版那一版导出，再走打包流程。
我要把一批现成的文件传上服务器Import不用先检出，但导完要另外检出。
我改了代码，但还没有提交权限Create patch把补丁发给有权限的人代为提交。
同事发来一个补丁，我要合进来Apply patch先 Update，再预览，最后应用。
我只想看看别人改了什么，不动本地Show log / Repo-browser纯查看，不产生任何本地变化（第 8 节）。
我要回到某个历史版本Update to revision不是导出也不是检出，见第 9 节。
什么时候用哪个：一句话版本

要在这里干活 → 检出（Checkout）；要交出去一份 → 导出（Export）；要把现成的搬上库 → 导入（Import）；只想传我改的那几行 → 补丁（Patch）。

记住这四句，日常遇到的场景基本都能对上号。分不清的时候回来把上面的表看一眼就行。
