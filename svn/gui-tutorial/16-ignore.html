16忽略文件：让编译产物别再烦我

编译出来的二进制文件、跑出来的日志、IDE 自动生成的配置——这些东西不该进版本库（体积大、每次编译都变、两个人一提交就打架）， 但它们会一直冒出来，赖在你的待提交列表里烦你。 这一节教你怎么让它们永久闭嘴。

为什么这些文件不能提交

刚接触版本控制的人常常想「全都提上去不就完了」。但有几类文件提上去纯粹是给自己和团队找麻烦：

  • 编译产物（bin、obj、target 这类目录）—— 它们是由源代码生成的，只要有源码，谁都能重新编译出来，没必要存一份。 而且体积往往比源码大很多，会让仓库飞速膨胀。
  • 更麻烦的是：它们每次编译几乎都会变。 于是每个人的编译产物都不一样，你一更新就冲突，一冲突就是一堆没法合并的二进制文件，纯属浪费生命。
  • IDE 的本地配置（.vs、.idea、*.user）—— 这些文件里存的是你自己的个人设置：窗口布局、最近打开的文件、本机的调试路径。 它本来就不该共享，提到了服务器上，别人一更新就被你的设置覆盖。
  • 运行时的日志和临时文件——程序跑一遍就变一次，提交它们等于把垃圾往仓库里倒。

判断标准很简单：这个文件是不是「人能手工写出来的」？ 是——进版本库；不是（机器生成的）——忽略它。

忽略规则到底是什么

忽略有两种用法，区别只在影响的范围有多大：

方式影响范围什么时候用
Add to ignore list
单个文件		 只影响当前这个目录（和规则里写的范围） 在某个文件上右键用它，忽略这一个文件； 或者在目录里右键用它，忽略这个目录下的某类文件。规则写在当前目录上，不往下管。
Add to ignore list (recursively)
目录及所有子目录		 当前目录 + 它下面所有层级的子目录 在目录上右键用它，这一整棵树里同名的东西都被忽略。 适合「凡叫 bin 的目录、不管在哪一层，一律别烦我」。

菜单里点忽略时，通常会让你选忽略什么范围——是忽略这一个具体文件， 还是忽略「所有这种扩展名的文件」。这个选择很关键，选错了要么没效果，要么误伤。

「忽略这个文件」和「忽略这种扩展名」怎么选
  • 一个特定文件（如 build.log）——选「忽略这个文件」。 规则只会匹配这名字，不会影响别的。
  • 某一类文件（如所有 .log）——选「忽略这种扩展名」。 这样以后新冒出来的日志文件也自动被忽略，不用一个个加。日志、临时文件用这种。
  • 某个目录名（如 bin）——用带 recursively 的那种。 这样不管 bin 出现在项目里哪一层，都会被忽略掉。

拿不准就先忽略「这个具体的文件」，影响面最小，不会误伤。

实际操作步骤

IGNORE让这些文件从待提交列表里消失
先在提交对话框里看清「烦人的是谁」 右键 → SVN Commit...，在弹出的提交对话框里看未版本控制的文件列表。 那些你每次都不想看见的名字，就是要忽略的目标。
先看清楚再动手，比事后一条条清理规则省事。
关闭提交对话框 这一步只是「侦察」，别真提交。取消掉对话框，回到资源管理器。
方法一：在具体文件上右键，忽略单个文件 直接在那个烦人的文件上右键 → TortoiseSVN → Add to ignore list。
菜单展开后通常会有几个选项：忽略这个具体的文件，或者 忽略所有这种扩展名的文件。
这一步只影响当前目录，不会牵连别处。
方法二：在目录上右键，整个目录树一起忽略 在那个目录（比如 bin）上右键 → TortoiseSVN → Add to ignore list (recursively)。
注意菜单名后面带 (recursively)，表示这个规则会覆盖当前目录和它下面所有层级的子目录。
适合「凡是编译输出目录，不管在哪一层都别烦我」这种需求。
看文件角标的变化 忽略生效后，那些文件会变成「已忽略」的状态， 在提交列表里不再出现。
如果文件多，可能需要刷新一下资源管理器（按 F5）才能看到角标更新。
检查一下规则去重 如果你反复对同一类文件点忽略，可能会攒下好几条重复或互相包含的规则。 打开属性看一眼（见下面截图说明），太乱就编辑一下、合并成一条。
规则不是越多越好，能覆盖需求的最少几条最舒服。
提交这次属性改动 这一步很多人会漏。 忽略规则本身也是一次改动，必须提交到服务器， 才能对团队所有人生效。
提交时文件夹会显示「已修改」状态——那是因为属性变了，正常现象。

面对面看：忽略规则存在哪儿

◈属性标签页：忽略规则的本质是一条属性PROPERTIES
怎么打开它：在文件夹上右键 → TortoiseSVN → Properties（或者 Show properties）。 打开的窗口里有一排标签页，其中一个是属性（properties）标签页。

① 属性列表区——这里列出这个文件夹上所有附着的信息。 忽略规则不是「一个开关」，而是一条实实在在的记录，名字叫 svn:ignore。 所以你在忽略时看到的那些选项，本质是在帮你写这条记录的内容。

② svn:ignore 那一行——点中它，下面的区域会显示它的值， 也就是具体被忽略的名字列表（一行一个名字，或者用通配符写的模式）。
看这里就能确认「到底忽略了什么」——比靠记忆猜靠谱得多。

③ 上方的操作按钮：
  • New...——手工新增一条属性。 高级用法：如果你要忽略的东西很多，与其一个个右键点，不如直接在这儿手工写一条 svn:ignore， 一次性把名字都列上。
  • Edit...——修改选中的属性。 用来删掉忽略列表里已经不需要的那几行，或者补上漏掉的。
  • Remove——彻底删掉这条属性， 也就是「取消忽略」，之后那些文件又会重新出现在待提交列表里。

④ 别忘了它也要提交——属性改了之后，文件夹会显示成「已修改」。 这不是文件内容变了，是属性变了。 必须提交，规则才会分享给团队。
关键认知：忽略了什么，就存在这条属性里

理解了「忽略 = 一条属性」，很多事情就顺了：

  • 它是跟着版本走的。属性可以提交、可以更新、有历史记录—— 你能查到「是谁在什么时候加了这条忽略规则」。
  • 它是分目录的。属性写在哪个目录上，就只管那个目录（或者按你选的递归范围管下去）。 这也解释了为什么在子目录里忽略，根目录那边看不出变化。
  • 可以用 Edit... 直接改。不想一条条点右键的时候， 打开属性直接编辑那个名字列表，效率高得多。
  • 取消忽略就是删掉这一条。不是「勾掉」，而是用 Remove 把属性删掉。

常见项目该忽略什么

下面这份清单可以直接照着抄。原则都是同一条：机器生成的东西不进版本库。

项目类型建议忽略为什么
C# / .NET bin、obj、*.user、.vs bin/obj 是编译输出；*.user 存的是个人调试设置； .vs 是 Visual Studio 的本地缓存目录。这些每次都变，提交了必然天天冲突。
Java target、.idea Maven 等构建工具的输出在 target； .idea 是 IntelliJ IDEA 的个人配置。注意：团队如果共享统一的项目配置，可以只忽略里面部分子目录——这类项目建议先和团队确认。
Node.js node_modules、dist node_modules 是最典型的必须忽略项——动辄几万个文件、几百兆， 而且装了哪些包完全由配置文件决定，别人自己装一遍就行。dist 是打包产物。
Python __pycache__、.venv __pycache__ 是解释器自动生成的字节码缓存， 一运行就变；.venv 是本机的虚拟环境目录，绝对不能提交（里面的路径是本机专属的）。
通用 · 编辑器 .vscode（视团队约定） 如果团队不用它统一管理配置，就忽略掉。 有些团队会特意保留部分配置文件来统一开发环境——这种情况要先问清楚。
通用 · 临时文件 *.log、*.tmp、*.bak 日志和临时文件没有共享价值，而且一直在变。用扩展名的方式一次忽略掉整类。
通用 · 编译产物 *.dll、*.exe、*.pdb、*.class、*.o、*.obj（C++） 由源码编译得到的二进制。但注意：如果项目里有第三方提供的、没有源码的库文件，那些是必须提交的—— 它们是「别人给你的成品」，不是「你自己编译出来的」。
经典坑：目录名千万别带结尾斜杠

这是忽略功能里最容易踩、又最不容易发现的坑。

要写 build，不要写 build/。

为什么？因为忽略规则里的名字是按「文件或目录的名字」来匹配的， 而不是按路径。你写 build/ 的时候， SVN 会去找一个名字字面就叫做「build/」的东西—— 而实际上没有任何文件或目录的名字里带斜杠，所以这条规则永远匹配不上任何东西。

最坑的地方在于：它不会报错。 你写完规则，看着挺正常，那个目录照样出现在待提交列表里。 很多人会以为是软件没生效，反复重启、重装，其实只是多打了一个斜杠。

正确的写法与错误的写法对比：

✗ 错误写法

build/

obj/

看起来像「目录路径」，但匹配不上任何东西。规则静默失效，你还找不到原因。

✓ 正确写法

build

obj

只写名字，不带任何路径符号。这才是能匹配上的形式。

同理，也别画蛇添足写完整路径（比如 src/build）——如果要限定某层目录， 正确做法是在那个目录上单独设置忽略规则，而不是在名字里写路径。

忽略规则本身也要提交，否则只在你本机生效

很多人以为「点了忽略就万事大吉」，然后发现同事的待提交列表里照样一堆垃圾文件。原因很简单：

忽略规则是一条属性，它和文件内容一样，需要提交才能分享出去。

不提交的后果：

  • 只有你自己这台机器上的工作副本知道「这些东西要忽略」。
  • 同事那边该烦还是烦，每个人都要自己再点一遍忽略。
  • 更糟的是——别人很可能就顺手把那些编译产物提交上去了。 因为他们不知道这是该忽略的东西，看到待提交列表里有，就一起提了。 仓库从此开始膨胀。

正确做法：设置好忽略规则之后，在文件夹上右键 → SVN Commit...， 在说明里写清「添加忽略规则，忽略编译输出目录」，连同规则一起提交上去。 这样一条规则惠及全团队，一步到位。

如果文件已经被 Add 过了，忽略是不起作用的

这是另一个高频问题：你明明忽略了 bin 目录，可它还在待提交列表里赖着不走。

原因：忽略规则只对「还没被版本控制认领」的文件有效。 一旦一个文件或目录已经被加入（Add）到版本控制里，它就属于版本库管了—— 忽略规则管不到已经纳管的文件。

判断方法：看文件角标。已经纳管的文件有正常的版本控制角标（而不是灰色的「未版本控制」问号）。 如果那个目录图标是绿的、带对勾的，说明它早就在版本库里了。

解决顺序（先移除，再忽略）：

  1. 先把文件或目录从版本控制里移除—— 在它上面右键，找到删除（把内容从版本库里去掉）的那一项，执行它。
  2. 这时候本地文件还在你的磁盘上，只是版本库不再管它了（这一步通常不会真删你的物理文件，但稳妥起见先备份一份）。
  3. 然后再按这一节的方法设置忽略规则。
  4. 提交——把「移除」和「忽略规则」一起提交上去。

顺序不能颠倒：先忽略后移除是没用的，因为规则对已纳管的文件不生效。 正确的顺序永远是「先移除、再忽略、最后提交」。

这一节的要点回顾
  • 机器生成的东西不该进版本库——编译输出、日志、IDE 个人配置，提交了只会制造冲突和体积。
  • 两种忽略方式：单个文件的、和递归管整个目录树的（菜单名带 recursively）。
  • 规则的本质是 svn:ignore 属性，可以在属性标签页里看、改、删。
  • 目录名不要带结尾斜杠——写 build 而不是 build/，否则规则静默失效。
  • 规则一定要提交，否则只在你本机生效，别人照旧把垃圾提上去。
  • 已经 Add 过的文件忽略不了——要先把它从版本控制里移除，再设置忽略。

下一节换个角度看同一件事：忽略规则只是众多「属性」里的一个。 属性还能控制文件的很多其他行为——比如换行符怎么处理、要不要默认加锁。
